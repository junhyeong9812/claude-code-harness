# OVERVIEW: {작업명}

> 목적: 이 구현의 **추상 진입점** — 무엇을 하고 어떤 순서·분기로 도는가를 한눈에 보고, 거기서 딥다이브로 내려간다. **추상 → 딥다이브** 산출물 피라미드의 꼭대기.
> 4문서 경계 (core §3.5): **OVERVIEW = 추상 지도(주요 포인트 + 워크플로우)** / TECHNICAL = 왜 그렇게 동작(메커니즘·불변조건·실패모드) / changelog = 이번 diff의 선택과 이유 / learned = 사용·확인한 요소 카탈로그. 같은 내용을 두 곳에 쓰지 않는다 — OVERVIEW는 "무엇/순서/분기", 아래 문서는 "왜/어떻게".
> 트리거: 코드 구현이 있는 작업의 기록 단계 (changelog·learned·TECHNICAL과 동일 — 문서-only 제외). 작성 시점: 검증 종료 후·최종 응답 전. 다단계 작업은 페이즈별.

## 주요 포인트 (3~7)

이 구현을 처음 여는 사람이 30초에 잡아야 하는 것. 각 줄: **무엇을 하는가 / 핵심 메커니즘은 무엇인가 / 어디가 까다로운가**, 끝에 딥다이브 포인터. **메커니즘은 이름·위험 키워드만 쓰고 설명은 TECHNICAL로 보낸다**(여기서 동작 원리를 풀면 TECHNICAL과 중복).

- (예) PTY로 자식 프로세스를 띄워 시그널을 중계한다 — 핵심은 SIGWINCH 전파. → 메커니즘 `TECHNICAL §동작 방식`
- (예) 편집 저장은 md 왕복으로 원본 포맷을 보존한다 — 손실 지점은 표 정렬. → 선택 이유 `changelog J3`

## 워크플로우 (절차 + 분기)

요청/진입 → 단계 → 결과의 **전체 흐름**. 조건 분기·실패 분기·페이즈 분할을 명시한다 — 정상 경로만 그리면 추상 지도가 거짓말을 한다. ASCII 텍스트 다이어그램(절차는 박스/화살표, 분기는 라벨 붙은 갈래).

```
(진입)
  │
  ▼
[단계 A] ── 조건 X? ──┬─ 예 ─▶ [단계 B] ──▶ (결과 1)
                      └─ 아니오 ─▶ [단계 C] ──┬─ 실패 ─▶ (실패 처리 / 결과 2)
                                              └─ 성공 ─▶ (결과 3)
```

> 박스 하나하나가 **왜 그렇게 동작하는가**는 여기 쓰지 않는다 — TECHNICAL 메커니즘 산문으로 보낸다(딥다이브 인덱스 참조).

## 딥다이브 인덱스

| 알고 싶은 것 | 문서·절 |
|---|---|
| 왜 그렇게 동작하나 (메커니즘·불변조건·실패모드) | TECHNICAL |
| 이번에 왜 그렇게 바꿨나 (선택·대안·근거) | changelog (J/M/G ID) |
| 무슨 요소를 어떻게 썼나 (라이브러리·함수·패턴·제약) | learned |
| 리뷰에서 무엇이 지적되고 어떻게 해소됐나 | review-log (있을 때) |
