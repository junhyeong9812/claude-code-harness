## 2. 접근 방식

### 2.1 파이프라인 재설계 (B/A/C 공통 패턴)

기존 파이프라인 사이에 모델 교차 검증 단계와 research.md 산출물을 삽입한다. B(기능 구현) 파이프라인 기준:

```
[B1. 리서치]                  Claude 코드/문서 조사
   ↓
[B1.5 외부 큐레이션]          Claude WebSearch + codex 외부 큐레이션 → 통합
   ↓
[B1.6 모델 교차 검증]         Claude 분석 vs codex 분석 교차 보고
   ↓
[B1.7 research.md 작성]       교차 검증 결과 통합 산출물 (신규)
   ↓
[B2. 방향성 점검]             ★ 사용자 게이트 ★ — research.md 기반 사용자 피드백
   ↓
[B3. 계획]                    plan.md / context.md / checklist.md + codex로 plan 검토
   ↓
[B4. 구현]
   ↓
[B5. 테스트]                  실행 테스트 + codex로 변경분 교차 검증
   ↓
[B6. 피드백]                  learned.md (codex 응답 흔적 포함) + project-overview.md 업데이트
```

A(버그) 파이프라인과 C(리팩토링) 파이프라인도 동일 패턴 적용:
- A: A1 조사 → A1.5 외부 큐레이션 → A1.6 모델 교차 검증 → A1.7 research.md → A2 진단 보고/방향 점검 → A3 수정 계획+codex 검토 → A4 수정 → A5 테스트+codex 검증 → A6 피드백
- C: C1 현상 분석 → C1.5 외부 큐레이션 → C1.6 모델 교차 검증 → C1.7 research.md → C2 목표 정의 → C3 계획+codex 검토 → C4 단계적 변환 → C5 회귀 테스트+codex 검증 → C6 피드백

### 2.2 codex 호출 실패 정책 (사용자 #6 반영)

- 호출이 토큰/세션/네트워크 오류로 실패 → **자동 스킵** (작업 중단하지 않음)
- 스킵하더라도 research.md 또는 plan.md에 **"codex 호출 실패: {사유} / 시각: {timestamp}"** 기록 의무
- 사용자가 명시 재시도 요청 시 다시 호출

### 2.3 codex 호출 표준 프롬프트 (사용자 #5 반영)

`templates/codex-prompt.md`에 단계별 표준 프롬프트 5종을 정의:
1. **외부 큐레이션용** — 작업 요구사항·키워드 전달 → 비주류/최신 자료 위주 수집 요청
2. **모델 교차 분석용** — Claude의 분석 요약 + 원본 컨텍스트 전달 → 사각지대 지적 요청
3. **계획 검토용** — plan.md 전달 → 함정·놓친 의존성·트레이드오프 지적
4. **진단 검토용 (버그 전용)** — 진단 보고 전달 → 오진 가능성 지적
5. **테스트 검증용** — 변경 diff + 테스트 코드 전달 → 누락 엣지케이스 지적

### 2.4 결과 흔적 보존 (사용자 #9 반영)

- 단계별 codex 응답의 **핵심 지적**을 research.md(리서치 단계)에 기록
- 작업 완료 후 learned.md에 **"모델 교차 검증 기록"** 섹션으로 누적 — 학습 자료화

### 2.5 codex 능력 사전 검증 (구현 직전 1회 수행 — codex 지적 #3 반영)

본 절차가 깔고 있는 전제 — "codex가 외부 큐레이션을 수행한다" — 의 사전 검증:

1. `codex exec` 환경에서 **web access / URL fetch 가능 여부** 확인 (예: "오늘 날짜 기준 가장 최신 X 라이브러리 버전과 출처 URL을 알려줘" 호출로 테스트).
2. **검색 가능**한 경우: codex 외부 큐레이션 = 자체 검색 + 자료 큐레이션.
3. **검색 불가**한 경우: codex 외부 큐레이션 역할을 **격하** → "Claude의 WebSearch 결과를 검토하고 비주류 옵션 발굴" 또는 "내부 추론 기반 다른 관점 제시"로 정의.
4. 검증 결과를 `templates/codex-prompt.md`의 외부 큐레이션 프롬프트(첫 번째 프롬프트)에 반영.

### 2.6 호출 기록과 재진입 규칙 (codex 지적 #6 반영)

- 호출별로 **호출 ID + 입력 해시(sha256 앞 12자)**를 checklist.md "단계별 codex 호출 기록" 표에 기록.
- 동일 입력 해시가 이전 행에 있으면 캐시 응답 재사용 가능, 새 호출 안 함.
- 작업 중단 후 재개 시 "호출 여부 = ✅" 행은 건너뛰고 미완 행만 재호출 → 중복 호출 방지.

### 2.7 보안 게이트 (codex 지적 #7 반영)

codex 프롬프트 전송 전, 입력 텍스트에 대해 **패턴/데이터 유형 기반 스캔** 수행. 파일명(`.env`) 기반이 아니라 **내용 패턴** 기반.

상세 패턴/키워드 표는 7.3.5 참조 — `orchestration-impl.md` 5.7절 본문에 정착.

## 4. 참고 코드 스니펫

> 본 작업의 변경 대상은 코드가 아니라 마크다운 오케스트레이션 문서다. 따라서 "사용된 메서드/함수"는 마크다운 구조 요소·문서 패턴으로, "문법/언어 기능"은 마크다운 문법 요소로, "동작 방식"은 문서가 절차로 해석되어 실행될 때의 의미적 흐름으로 분석한다.

### 4.1 현행 B1.5 외부 큐레이션 절 — 확장 대상

**출처: `/home/jun/project/claude_study/orchestration-impl.md:325-347`**

```markdown
#### B1.5 외부 큐레이션 (External Curation) — ★ 필수 ★

**목표**: LLM의 다수결 편향을 사람의 외부 큐레이션으로 보정한다. 모델이 만든 1·2·3 옵션 메뉴 안에서만 결정하면 "4번 옵션"은 영영 사각지대로 남는다. 외부 큐레이션이 그 사각지대를 메운다.

**수행 내용**:
- `WebSearch` / `WebFetch`로 작업 키워드 + **최신 1년 범위**로 검색을 **최소 1회** 수행한다.
- 결과 중 비주류/혁신/새 라이브러리/논문/실험적 접근이 있으면 **plan.md의 "참고 코드 스니펫" 또는 "트레이드오프"** 섹션에 출처와 함께 기록한다.
- 첫 검색에서 의미 있는 결과가 없으면 — 검색어를 한 번 다른 각도로 바꿔 재시도한다.

**의무 / 생략 기준**:
- **의무**: 새 라이브러리/패턴/도메인을 다루거나, 작업 키워드가 변화 빠른 영역(AI/검색/분산/UI 프레임워크 등)인 경우.
- **생략 가능**: 도메인 지식이 충분히 깊고, 단순 수정/리팩토링이며, 외부 변화의 영향이 없는 경우.
- 생략하는 경우 **plan.md에 "외부 큐레이션 생략 사유: ..."를 명시한다.** 사유 없는 자동 생략 금지.
```

**코드 분석:**

**사용된 메서드/함수 (마크다운 구조 요소):**
| 요소 | 소속 (마크다운 명세) | 역할 | 결과물 |
|------|---------------------|------|--------|
| `#### B1.5 ...` (헤딩 4단계) | CommonMark §ATX heading | 단계 식별자 + 표시명 | TOC 진입점 |
| `**...**` (강조) | CommonMark §emphasis | "★ 필수 ★", "의무", "수행 내용" 같은 메타 표지 | 시각적 위계 |
| `WebSearch` / `WebFetch` (인라인 코드) | CommonMark §code spans | Claude Code 내장 도구 이름 지칭 | 도구 호출 트리거 어휘 |
| `- ` (불릿 리스트) | CommonMark §list | "수행 내용" 단계 나열 | 절차 항목 |

**문법/언어 기능 설명:**
- ATX 헤딩(`####`)의 깊이는 파이프라인 단계 위계를 나타낸다. `### 4.B`(파이프라인) → `#### B1.5`(단계)의 2단 위계.
- 강조(`**...**`)는 절차상 **강제력의 표지**다. "의무"·"생략 가능"·"필수" 같은 단어를 강조해 둠으로써 LLM(나)이 문서를 읽을 때 게이트 조건으로 인식한다.
- 인라인 코드 스팬(`` `WebSearch` ``)으로 도구 이름을 감싸 일반 텍스트와 구분 — 이 표기가 있으면 LLM은 "이건 호출 가능한 액션"으로 해석한다.

**동작 방식:**
- LLM이 파이프라인 진입 시 이 절을 읽으면 → "B1.5 = WebSearch 1회 이상 의무" 규칙으로 내재화.
- 변경 후에는 같은 위치에 "WebSearch + codex 외부 큐레이션, 결과 통합" 패턴이 들어가야 LLM이 두 신호원을 모두 호출하도록 행동.
- 즉 이 절의 **구조**(수행 내용·의무/생략 기준·생략 사유 명시 의무)는 유지하고, **수행 내용 본문만 확장**한다. 구조가 깨지면 LLM이 게이트로 인식하지 못할 위험.

### 4.2 현행 B2 이해 확인 게이트 — 의미 확장 대상

**출처: `/home/jun/project/claude_study/orchestration-impl.md:348-366`**

```markdown
#### B2. 이해 확인 (Understanding Gate) — ★ 필수 게이트 ★

**목표**: 리서치 결과를 사용자에게 보고하고, 이해가 맞는지 확인받는다.

**⚠️ 이 단계를 건너뛰고 계획으로 넘어가지 않는다. 예외 없음.**

**보고 형식**:
```
[이해 확인]
1. 요구사항 요약: (내가 이해한 것)
2. 기존 코드 현황: (현재 관련 코드의 상태)
3. 구현 방향: (어떤 접근으로 구현할 것인지 — 간략하게)
4. 질문 사항: (불명확한 점 — 있으면)
```

**진행 조건**:
- 사용자가 이해에 **동의**하면 → B3(계획)으로 진행한다.
- 사용자가 이해를 **수정**하면 → 수정 사항을 반영하고 다시 보고한다.
- 사용자가 "진행해"라고 하면 → B3(계획)으로 진행한다.
```

**코드 분석:**

**사용된 메서드/함수 (마크다운 구조 요소):**
| 요소 | 소속 | 역할 | 결과물 |
|------|------|------|--------|
| `#### B2. ... — ★ 필수 게이트 ★` | CommonMark §ATX heading + 강조 | 게이트 단계 식별 | LLM에 "여기서 멈추고 사용자 확인" 신호 |
| 펜스 코드 블록 (` ``` ` ~ ` ``` `) | CommonMark §fenced code | 사용자에게 출력할 **보고 템플릿** 고정 | 일관된 보고 포맷 |
| `**진행 조건**:` (강조 헤더) | CommonMark §emphasis | 분기 규칙 정의 | LLM 의사결정 트리 입력 |
| `→` (화살표 문자) | 일반 텍스트 | 흐름 표현 | "다음 단계" 표기 관용구 |

**문법/언어 기능 설명:**
- 펜스 코드 블록 안의 "[이해 확인] / 1. 요구사항 요약 ..."은 LLM에게 **출력 템플릿**으로 작동한다. 코드 블록으로 감싸면 LLM이 이 형식을 그대로 재현하려는 경향이 강해진다 (instruction-tuning 효과).
- "★ 필수 게이트 ★" 같은 시각 기호는 일반 강조보다 강한 priority 신호다 — `★` 문자가 다른 절에 거의 안 쓰여서 희소성으로 강제력을 얻는다.
- "예외 없음" 같은 절대 표현은 LLM의 자기 합리화(예: "이번엔 간단하니까 건너뛰자") 시도를 차단하는 어휘 선택이다.

**동작 방식:**
- LLM이 이 절을 읽으면 → B1 완료 후 B3로 바로 가지 않고 펜스 블록 형식대로 보고 → 사용자 응답 대기. 이게 게이트의 핵심.
- 변경 후 B2는 입력 자료가 **Claude의 이해**가 아니라 **research.md(Claude 분석 + codex 분석 통합)**으로 바뀐다. 즉 게이트의 입력 산출물이 달라지지만 게이트 자체의 구조(보고 형식 + 진행 조건)는 유지.
- 펜스 블록 안의 항목 4개를 5개로 늘리고 "5. 모델 교차 검증 요약" 추가. 항목 순서는 의도적: 사용자가 위에서 아래로 읽으며 점점 깊이 들어가는 흐름.

**사용된 메서드/함수 (마크다운 구조 요소):**
| 요소 | 소속 | 역할 | 결과물 |
|------|------|------|--------|

**동작 방식:**
- 변경 후: `## 6. 구현 순서` → `## 7. codex 검토 결과` (신설) → `## 승인 상태` 순서.

- 호출 실패 시에는 표 대신 "호출 실패 시 사유" 블록에 사유와 시각 기록 — 절차가 막히지 않도록 fallback path 제공.

#### 7.3.4 (지적 6 반영) 호출 기록 강화

`templates/checklist.md`의 "단계별 codex 호출 기록" 표 컬럼을 보강:

| 단계 | 호출 ID | 입력 해시 (sha256 앞 12자) | 호출 여부 | 호출 시각 | 응답 요약 / 스킵 사유 |
|------|---------|--------------------------|-----------|----------|-------------------|

- **호출 ID**: 작업명 + 단계 + 순번(예: `codex-cross-validation/B3/001`). 재시도 시 `/002`로 증가.
- **입력 해시**: 동일 입력 중복 호출 방지용. 입력이 동일하면 캐시된 응답 재사용 가능 명시.
- **재진입 규칙**: 작업이 중단되었다 재개될 때 — 표를 보고 `호출 여부 = ✅` 행은 건너뛰고 미완 행만 재호출.

#### 7.3.5 (지적 7 반영) 보안 게이트를 패턴/데이터 유형 기반으로 정의

`orchestration-impl.md` 신설 5.7절 본문에 다음 정책 포함:

> **codex 프롬프트 전송 전 차단 패턴 (정규식 + 키워드 기반)**:
>
> | 분류 | 패턴 / 키워드 예시 | 차단 동작 |
> |------|---------------------|---------|
> | 시크릿 키 | `[A-Za-z0-9_-]{32,}=`, `BEGIN (RSA\|EC\|OPENSSH) PRIVATE KEY`, `xox[a-z]-`, `sk-`, `ghp_`, `AKIA[0-9A-Z]{16}` | 자동 마스킹 또는 호출 중단 |
> | 환경 변수 본체 | `\.env(\.\w+)?$` 파일 내용, `process\.env\.\w+` 값 부분 | 키 이름만 남기고 값 redact |
> | 비밀번호/토큰 어휘 | `password\s*[:=]`, `token\s*[:=]`, `secret\s*[:=]`, `Authorization:\s*Bearer\s` | 값 부분 redact |
> | PII | 이메일·전화·주민/사업자번호 정규식 | redact |
> | 스택 트레이스 | 내부 절대 경로 + 호스트명 노출 | 경로 anonymize |
> | 비공개 식별자 | 사내 이슈 ID 규약(`PROJ-\d+`), 비공개 URL | redact 또는 사용자 확인 |
>
> 절차: 프롬프트 조립 후 → 위 패턴 매칭 스캔 → 매칭 발견 시 사용자에게 보고 후 redact 또는 호출 중단. 자동 통과는 매칭 0건일 때만.
