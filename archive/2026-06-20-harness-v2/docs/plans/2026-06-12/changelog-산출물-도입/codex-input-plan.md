# 검토 요청: 하네스에 changelog.md 학습 산출물 도입 계획

너는 다른 모델(GPT)로서 독립 교차 검증자다. 계획의 허점·기존 규칙과의 충돌·집행 공백을 지적하라. 한국어로.

## 배경 (현행 체계)

Claude Code 작업 하네스. 작업마다 작업 폴더(docs/plans/날짜/작업명/)에 task.md(정의·계획·검증·기록)를 산출. 기존 학습 산출물:
- **learned.md**: 학습 가치 트리거 시만(새 라이브러리·패턴/비직관 버그/테스트 전략 변경) 풀 작성, 그 외 task.md 안 5줄 요약. 사용자 공부용 제품.
- **문서 인용 규칙**: 코드 블록은 실파일에서 복사 — 메모리 재현 금지, placeholder·"...(생략)" 금지, 작성 직전 재읽기.
- **리뷰 렌즈 4레벨**(playbooks/review.md): API 예외 전파 / 메서드 내부 알고리즘·자원·속도 / 네이밍 도메인 직관성 / ORM 쿼리·실행계획.
- 문서 헌법: 규칙 하나=위치 한 곳, 템플릿·playbook은 트리거 시에만 읽음.

## 변경 계획 (사용자 결정 — 뒤집지 말 것)

목적: **사용자가 코드 리뷰 능력을 기르기 위한 학습 산출물**. 각 구현의 근거를 명시해 "왜 이렇게 짰나"를 추적 가능하게.

- 트리거: **코드 구현이 있는 작업마다** (코드·스크립트·스키마 등 실행 산출물 — 문서-only 제외). stakes 무관.
- 위치: 작업 폴더 `changelog.md` (task.md 옆).
- 작성 시점: 검증 통과 후 기록 단계 (스니펫은 최종 코드에서 복사).
- 내용 — 판단이 개입된 변경 전부, 변경 단위마다:
  ① 무엇을 (file:line + 한 줄 요약)
  ② 왜 (근거 — spec/불변식/렌즈와 연결, 검토한 대안과 기각 사유)
  ③ 코드 스니펫 (실파일 복사) + **주석으로 줄/블록별 근거 설명**
  ④ 리뷰 연습 포인트 — "이 코드를 리뷰한다면 무엇을 봐야 하나" (렌즈 4레벨 중 해당 질문 1~3개, 사용자 훈련용)
  기계적 변경(import 정리·단순 rename)은 1줄 목록만.
- 배선: templates/changelog.md 신설(형식 단일 출처) + core.md §3.5(기록 단계 의무)·§7(트리거 표) — playbook은 필요 시 포인터 1줄.

## 질문

1. learned.md와의 역할 경계가 실제 운용에서 흐려질 지점은? (같은 작업에서 둘 다 나올 때 중복 작성 위험)
2. "판단이 개입된 변경"의 판정 기준이 모호해 자의적으로 축소·팽창될 여지는? 집행 가능한 기준선을 제안하라.
3. 주석으로 근거를 다는 방식이 기존 "코드 주석은 왜만, 구현 중 주석 금지" 규칙(implementation playbook)과 충돌하나? (changelog 스니펫 안 주석 vs 실코드 주석)
4. 작성 시점(검증 후)·작성자(구현자=메인)의 문제 — 사후 합리화로 변질될 위험과 방지책은?
5. 그 밖의 집행 공백·문서 충돌. 신뢰도 높은 지적만, 심각도와 구체 수정안 포함.
