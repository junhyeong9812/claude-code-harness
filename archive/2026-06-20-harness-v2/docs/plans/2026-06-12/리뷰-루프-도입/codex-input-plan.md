# 검토 요청: 코드리뷰 하네스 정책 변경 계획

너는 다른 모델(GPT)로서 독립 교차 검증자다. 아래 계획의 허점·충돌·집행 공백을 지적하고, 질문 2에 구체안을 제시하라. 한국어로 답하라.

## 배경 (현행 체계)

Claude Code용 작업 하네스. 검증 강도는 stakes(낮음/중간/높음) 비례.
- 현행 높음 stakes 리뷰: 구현자와 분리된 Claude 워커가 "페이즈 diff + spec"만 입력받아 spec compliance 리뷰 → codex(GPT CLI)가 findings를 adjudicate(오탐 판정).
- 가드레일: finding은 file:line 인용 + 현재 diff/spec 불일치에 귀속 증명, 불명확하면 "범위 밖". 페르소나 다수결은 타 모델 독립 신호를 대체 못함.
- 절단 계약: 테스트 설계는 구현 diff 열람 금지. 리뷰는 구현자와 컨텍스트 분리. codex 입력은 보안 스캔 후 발췌.
- 문서 헌법: 규칙 하나=위치 한 곳(단일 출처), playbook ≤80줄, 조건부 문서는 트리거 시에만 읽음.

## 변경 계획 (사용자 결정 사항 — 뒤집지 말 것, 보완 지점만 지적)

높음 stakes 리뷰를 다음 루프로 교체. 중간/낮음은 기존 유지.

```
[구현 완료·페이즈 커밋]
→ ① Opus 워커 리뷰 ∥ codex 리뷰 (병렬, 동일 입력: 페이즈 diff + spec)
→ ② 메인(Claude)이 두 결과 종합 — 중복 병합, 근거 품질 재평가, 채택/기각
→ ③ 종합본을 codex에 1회 피드백 (누락·오판 지적받기)
→ ④ 수정 → 테스트 (기존 verification playbook)
→ ⑤ 재리뷰 (①로 복귀)
종료: 신규 finding 0이면 종료. 최대 3루프 — 초과 시 미해소 finding을 사용자 보고.
```

판단 기준 (신설 playbooks/review.md에 4레벨 렌즈로 문서화, 리뷰는 diff 기반이되 판단은 이 레벨들로):
- **API 단위**: 전체 프로세스에서 발생 가능한 예외와 전파 경로 (입력 오류·권한·의존 실패·타임아웃·부분 실패)
- **메서드 내부**: 알고리즘 설계·최적화(복잡도, 서버 자원 사용·속도), 정상/예외 흐름 분리, 예외 처리 적절성
- **네이밍**: 메서드명이 도메인을 직관적으로 드러내는가
- **리포지토리/쿼리**: ORM이 생성하는 쿼리·SQL이 사용 DB의 실행계획·옵티마이저를 고려해 처리되는가 (예: JPA의 N+1·인덱스·페이징) — 범용 표현, JPA는 예시

변경 파일: playbooks/review.md 신설(≤80줄) / core.md §5 리뷰 행 높음 열을 포인터로 교체 + §7 트리거 표 등록 + 변경 이력 / orchestration.md §4 codex 행 보완 / verification.md §4 포인터.

## 질문 1: 계획 검토

위 루프·문서 배선에서: (a) 무한루프·교착 등 절차 결함 (b) 기존 절단 계약·가드레일과의 충돌 (c) 단일 출처 위반이나 트리거 미폐쇄 (d) 루프 각 단계에서 입력 스코프(누가 무엇을 보나)의 모호함 — 구체적으로 지적하라. 사소한 표현 문제는 제외, 집행 가능성에 영향 주는 것만.

## 질문 2: 알고리즘 자원·속도 판단 기준 설계 (사용자가 너와 논의해 정하라고 지시)

"메서드 내부" 렌즈에서 알고리즘의 서버 자원 사용·속도를 리뷰할 때, 리뷰어가 쓸 판단 기준을 제안하라. 조건:
- diff만 보고 판단 가능해야 함 (프로파일링 결과 없음)
- 조기 최적화 강요와 진짜 문제 방치를 모두 피하는 기준선 — "언제 지적하고 언제 넘어가나"
- 체크리스트 5~8문항 (예: 입력 크기 상한이 코드/스펙에 명시되나, 루프 내 I/O·쿼리, 메모리 적재 방식 등 — 네가 더 좋은 항목으로)
- finding으로 보고할 때 요구할 증거 형식 (예: 복잡도 추정 + 입력 규모 가정 명시)
