# 검토 요청: LLM 코딩 하네스의 "개발 차원 지도" 설계

당신은 독립 검토자다. 아래 설계를 비판적으로 검토하고, 각 질문에 구체적으로 답하라.
동의보다 반증·누락 발견에 비중을 둬라. 근거 없는 칭찬 금지.

## 배경

LLM 코딩 에이전트(Claude Code)용 작업 하네스를 운영 중이다. 현재 체계(v2):
- 작업은 [탐색 중] ↔ [정의됨] 두 상태. 정의 게이트 = 명확도 6칸(목표/경계·불변식/기준소스/금지영역/검증방법/stakes).
- 검증 강도는 stakes(낮음/중간/높음) 비례. stakes = 손실 × 낯섦 × 모호성 × 불가역.
- 컨텍스트 비용은 1급 제약: 상시 선독은 1문서(~200줄). 나머지는 트리거 시 조건부 로드.
- 과거 v1의 실패: 균일 의무(작업당 외부 검증 6~10회)·상시 선독 50k 토큰 → 체크박스 연극과 비용 폭증으로 폐기.

문제의식: v2는 "언제/얼마나 검증하나"는 정교하지만 "무엇을 보나"(도메인 점검 기준)가 얇다.
사용자(백엔드 개발자)가 시니어의 점검 기준 18개를 정리했고, 이를 하네스에 기준화하려 한다.

## 18개 항목

1 기능 요구사항 / 2 입력 검증 / 3 권한 경계 / 4 데이터 정합성 / 5 동시성 / 6 예외 처리 /
7 변경 가능성 / 8 성능 / 9 장애 복구 / 10 운영 가능성 / 11 보안 / 12 API 설계 /
13 테스트 가능성 / 14 도메인 규칙 / 15 데이터 모델링 / 16 비용 / 17 사용자 경험 / 18 협업 가능성

## 제안된 설계

### A. 성격 4분류
- 게이트 재료 (1, 14): 정의 게이트 그 자체 — 차원 아님
- 조건부 차원 (2,3,4,5,6,8,9,10,11,12,15,17 — 12개): "이 변경이 X를 건드리는가?" 트리아지 가능
- 상시 렌즈 (7, 13, 18): 모든 변경에 해당 → 트리아지 무의미, 리뷰에 상시 인라인
- 판정 입력 (16): stakes·스코프 결정의 입력

### B. 실행 구조: "전수 스캔은 의무(저비용), 깊은 검증은 선별(고비용)"
- 정의 게이트에서 조건부 차원 12개 전수 트리아지: 각각 해당/비해당 + 근거 1줄 (비해당에도 근거 의무 — 체크박스 연극 방지)
- 활성 차원만 계획(설계 결정 질문)→개발(구현 렌즈)→검증(차원별 분리 리뷰)에서 가동. 강도는 stakes 비례
- 지도 본체는 차원 × 단계 매트릭스 1문서, 정의 단계 진입 시에만 조건부 로드
- 비해당 판정한 차원이 나중에 등장하면 승격 + 측정 로그 기록 (트리아지 오판 데이터 → 지도 개정 근거)

### C. stakes 도출
트리아지 활성 차원에서 stakes 하한을 기계적으로 도출 (예: 동시성·장애복구 활성 → 중간 이상,
권한·보안·불가역 활성 → 높음). 단 낯섦·모호성 축은 차원과 무관하므로
칸6 = max(트리아지 도출 하한, 낯섦·모호성 판단).

### D. 경계선 판정 4건
- 6 예외 처리: 조건부 차원으로 (내부 리팩토링·조회엔 비활성) — 반론: 거의 항상 활성이라 상시 렌즈가 맞다?
- 3 권한 / 11 보안: 분리 유지 (질문이 다름: 접근 경계 통과 vs 공격 표면 생성)
- 17 UX: 조건부 차원 ("사용자 가시 동작이 바뀌는가") — 반론: 대부분 비활성이라 행 가치 낮다?
- 13 테스트 가능성: 상시 렌즈 축소형 (테스트 설계 분리 패스가 이미 구조로 강제하므로)

## 질문 (각각 답하라)

1. **성격 4분류의 타당성**: 이 절단이 맞나? 다른 절단축이 더 나은 항목이 있나? 특히 D의 4건에 대한 당신의 판정은?
2. **체크박스 연극 위험**: 12행 전수 트리아지 + "비해당에도 근거 1줄"이 LLM의 형식적 통과(전부 '비해당 — 해당 없음' 류)를 실제로 막을 수 있나? 더 강한 설계가 있나? (예: 근거에 변경 파일/경로 인용 의무 등)
3. **stakes 기계 도출의 부작용**: C 설계로 과잉 승격(매번 중간 이상)이나 과소 승격이 생길 수 있는 경로는? "하한 + max" 구조의 허점은?
4. **누락 차원**: 업계 정본(Google SRE Production Readiness Review, AWS Well-Architected, OWASP ASVS, 12-factor 등) 기준으로 이 18개에 빠진 차원이 있나? 백엔드 위주 목록이라 빠졌을 영역(데이터 파이프라인·배치·프론트엔드·인프라)은 트리아지에 어떻게 수용하나?
5. **컨텍스트 비용**: 차원×단계 매트릭스 1문서(조건부 로드) 구조가 v1 회귀(선독 비대화)로 가는 경로가 있나? 지도 크기의 상한 기준을 어떻게 둬야 하나?
6. **운영 리스크**: 이 구조가 6개월 후 실패해 있다면 가장 그럴듯한 원인 3개는?

출력: 질문별 번호로, 각 지적은 [동의/반박/보완] 태그 + 근거. 마지막에 "가장 중요한 지적 1개"를 명시하라.
