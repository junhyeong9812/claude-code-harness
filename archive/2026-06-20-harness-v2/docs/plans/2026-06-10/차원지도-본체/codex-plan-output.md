## 1. [보완] 겹침은 허용되지만, “소유 차원” 기준이 부족하다

같은 변경이 여러 차원을 동시에 활성화하는 것은 맞다. 예를 들어 신규 `POST /orders`는 보통 `2/3/4/5/6/10/12/14/17`이 동시에 켜진다. 문제는 중복 자체가 아니라, 각 차원이 무엇을 독점적으로 묻는지 경계가 흐린 부분이다.

구체 사례:

- `write 경로`: `4 데이터 정합성`, `5 동시성`, `6 예외 처리`, `10 운영 가능성`이 모두 활성이다. 이때 `5`는 “동시 실행으로 같은 리소스가 깨지는가”에 한정한다고 명시해야 한다. 지금은 `활성: write 경로`라서 거의 모든 write가 자동 중간이 된다.
- `외부 API 호출`: `6 예외`, `9 장애복구`, `10 운영`, `12 API 계약`, `17 가시성`이 겹친다. `9`는 “내가 제어하지 않는 의존성의 실패 전파/재처리”로 좁히는 것이 낫다.
- `PII 응답 필드 추가`: `11 보안`, `12 API 계약`, `17 가시성`은 잡지만, 개인정보 처리 목적/최소수집/보존 같은 프라이버시 규칙은 F7에만 명시되어 백엔드/API 변경에서 빠질 수 있다.
- `라이브러리 업그레이드`: `16`의 “새 의존성 도입”은 있지만 기존 의존성 버전 변경, 보안 패치, transitive dependency 변화는 빠진다. 공급망은 infra I8에만 있어 일반 앱 코드 변경에서 누락 가능하다.
- `일회성 데이터 보정 스크립트`: 스케줄/ETL이 아니면 배치팩 감지가 안 될 수 있다. 하지만 실제로는 `4/6/8/9/14/15/B1/B2/B5` 성격을 가진다. surface detector에 “일회성 대량 데이터 수정/재처리”를 넣어야 한다.

## 2. [보완] max 규칙은 맞지만 `낮음↑` 표기가 알고리즘을 흐린다

`4 정합성=중간`, `5 동시성=중간`은 같은 write 변경에서 충돌하지 않는다. 둘 다 활성이라면 하한 max는 중간이고, 돈/불가역/공개 표면이면 높음으로 올라간다.

문제는 `활성=낮음↑`이다. 칸6이 기계적으로 `max`를 요구하는데 `낮음↑`는 값이 아니라 판단 지시다. 예를 들어 신규 endpoint는 `6 활성=낮음↑`, `10 활성=낮음↑`, `17 활성=낮음↑`인데, 공개 API면 `12=높음`으로 해결되지만 내부 API나 운영 도구에서는 리뷰어마다 다르게 잡을 수 있다.

완화책:

- stakes 값은 `낮음/중간/높음` 중 하나로 쓰고, 조건부 승격은 별도 문장으로 둔다.
- `낮음↑`를 유지하려면 “기본 하한은 낮음, 조건 충족 시 중간 이상”이라고 명시해야 한다.
- `5 활성: write 경로`는 너무 넓다. “같은 리소스에 중복/동시 실행이 실제 가능한 write”로 좁히지 않으면 대부분의 write가 자동 중간이 된다.

## 3. [보완] light 활성은 집행 구멍이 있다

현재 정의는 “P/I/V 질문에 답만 기록, 분리 리뷰 생략”인데, 최소 산출물 기준이 없다. 그래서 다음처럼 빠져나갈 수 있다.

- `light`로 표시하고 P/I/V에 “해당 없음”만 적음
- 불확실성을 light로 올렸지만, 나중에 확인 후 active/inactive로 재판정하지 않음
- light 차원이 stakes max에 포함되는지 불명확함
- “분리 리뷰”의 의미가 불명확해서 실제 검증 없이 통과 가능

집행 가능하게 하려면 light 규칙을 더 딱딱하게 해야 한다.

- light도 stakes 하한에는 포함한다. 단, 증거로 inactive 전환하면 제외 가능.
- light 행은 `불확실한 이유`, `확인할 증거`, `P/I/V 답변`을 필수로 둔다.
- 종료 전 light는 `활성 유지 / 비활성 전환` 중 하나로 재판정한다.
- P/I/V 답변은 “해당 없음” 단독 금지. 부적합이면 보정 루프로 보내야 한다.

## 4. [보완] 확장팩은 “추가” 원칙은 맞지만 중복 금지 문구가 위험하다

`I3 secrets`와 `11 보안`, `B2 부분 실패`와 `9 장애복구`, `F1 상태 동기화`와 `4/17`, `F7 프라이버시`와 `11`은 의도적으로 겹쳐야 한다. 그런데 frontend 문서의 “2 입력검증·17 가시성은 기본 차원에서 이미 다룸 — 중복 점검 금지”는 잘못 읽히면 기본 차원을 끄는 근거가 된다.

충돌 사례:

- `I3 secret 전달 경로 변경`: `11 보안`도 반드시 활성이어야 한다. I3만 보면 앱 로그/응답 누출을 놓칠 수 있다.
- `B2 부분 실패`: `9 장애복구`는 외부 의존 실패, B2는 N건 중 일부 실패 처리다. 둘 다 켜질 수 있다. “대체 아님”은 좋지만, 연결 규칙이 필요하다.
- `F7 analytics + PII`: F7만 켜고 11을 비활성 처리할 위험이 있다. PII 포함이면 `11 자동 light/active`가 필요하다.
- `I8 공급망`: 일반 앱의 의존성 업그레이드에는 적용되지 않는다. 공급망을 11 또는 16에도 얇게 넣어야 한다.

“중복 점검 금지”는 “같은 질문을 두 번 쓰지 말고, 기본 차원은 계약/보안/가시성 관점으로 유지한다” 정도로 바꾸는 것이 낫다.

## 5. [반박] 164줄 로드는 감당 가능하지만, 트리아지 전용 얇은 표는 필요하다

매 작업 정의 시 164줄은 치명적 비용은 아니다. 문제는 읽는 양보다, 트리아지 순간에 P/I/V와 정비 규율까지 섞여 있어 판정자가 필요한 신호를 빠르게 찾기 어렵다는 점이다.

분리는 유효하다.

- `dimensions-triage.md`: ID, T, 활성 신호, 비활성 신호, stakes, 자동 연동만 포함
- `dimensions.md`: P/I/V 질문, 보정 루프, 정비 규율
- 확장팩도 동일하게 triage 블록과 P/I/V 블록을 나누기

단, 단일 출처 원칙을 유지하려면 파일을 둘로 복제하면 안 된다. 같은 문서 안에서 “트리아지 표”를 앞에 두고, 뒤에 P/I/V 상세를 두는 방식이 더 안전하다.

## 6. [동의] 경량 경로 폐지는 운영 부담이 크다

모든 정의됨 작업에 `task.md + 14행 트리아지`를 요구하면 1줄 오타, 주석 수정, 테스트명 수정 같은 작업에서 준수율이 떨어질 가능성이 높다. 규칙이 과하면 실제 운영에서는 빈 행, 복붙 근거, 형식적 비활성이 늘어난다.

사용자 결정대로 “task.md 생략 허용”을 폐지하더라도 완화책은 필요하다.

- `micro task.md` 템플릿 허용: 14행은 유지하되 근거를 한 줄 diff 범위로 압축
- 명백한 문서/오타 전용 fast triage: `활성 없음`을 금지하지 말고, 14행 비활성 증거를 파일 범위 하나로 묶는 방식 허용
- “정의됨 작업”의 하한을 명확히 둔다. 예: 빌드 산출물 정리, 공백 수정, typo-only는 task.md 대상인지 별도 결정 필요
- 자동 생성 보조가 필요하다. 사람이 매번 14행을 손으로 쓰면 규칙이 먼저 무너진다.

## 가장 중요한 지적 1개

`light 활성`이 현재 가장 큰 집행 공백이다. 불확실하면 light로 올리라는 원칙은 맞지만, 종료 전 재판정·stakes 포함 여부·필수 증거가 없어서 “검토 생략용 중간 상태”로 악용될 수 있다. `light도 stakes에 포함하고, 종료 전 active/inactive로 재판정한다`는 규칙을 추가해야 한다.
