## 0. 배경 — 이 설계가 나온 흐름

`/insights`(2026-05-09~06-08) 최대 마찰이 `wrong_approach`(27)·`misunderstood_request`(23)였다. 토론(09 문서)에서 두 마찰의 뿌리를 **"무엇이 항상 참이어야 하는가(본질적 복잡성)를 코드 작성 전에 명시하지 않은 것"**으로 진단했다. Naur(theory building)·Brooks(essential vs accidental complexity)·실무 검증 연구가 모두, 개발의 본체는 타이핑이 아니라 *경계의 불변식·계약·실패의미론을 정의하는 사고*임을 가리킨다.

현재 시스템(orchestration-impl.md)은 성숙하지만, 이 "정의"를 **명시적으로 강제하는 게이트가 없어 누락되기 쉽다**(codex 보정 — "완전 부재"가 아니라 "강제 안 함"). 본 설계는 그 빈 곳을 메운다.

---

## 1. 요구사항 (사용자 확정)

1. 기능 개발 *이전에* **토론으로 기능을 정의**(경계의 불변식·계약·실패의미론)하고, 그 정의를 바탕으로 구현하도록 유도한다.
2. **애매한 것들을 전부 결정으로 못 박는** 가드레일을 둔다. 애매성이 남으면 구현으로 진입하지 못한다.
3. 이 "정의하는 행위와 그 산출물"이 **학습/자산화**되어야 한다 — 매번 머릿속에서 재발명하지 않도록.

## 3. 선택지 비교 (사용자 결정 반영)

### 3.1 정의 단계의 위치

| 선택지 | 장점 | 단점 | 결정 |
|--------|------|------|------|
| **둘 다 (브리지 + 게이트)** | 토론 모드에서 definition을 만들고(discuss→impl 브리지 산출물), impl B2.5 게이트가 "정의 충족 + 애매성 해소"를 강제. 사용자 의도("토론으로 정의 완료 후 구현")와 기존 브리지 구조에 모두 부합 | 게이트 1개 추가(약간의 무게) | **✅ 채택** |
| impl 게이트만 | 가벼움 | "구현 전 토론으로 정의"라는 의도 약화 | |
| discuss 브리지만 | 유연 | 강제력 약 — 누락 위험(현 문제 재발) | |

### 3.2 학습화 방식

| 선택지 | 장점 | 단점 | 결정 |
|--------|------|------|------|
| **방법론 + 경량 카탈로그** | ① 반복 방법(템플릿+체크리스트+예시) ② domain-contracts.md에 승격 기준 통과 불변식만 누적 | 카탈로그 갱신 규율 필요 | **✅ 채택** |
| 방법론만 | 가장 가벼움 | 도메인 불변식 재사용은 매번 수작업 | |
| 카탈로그 중심 | 자산 풍부 | codex 경고 — 낡는 문서 함정 | |

## 4. 결정 사항 (D1~D7)

### D1. 정의 게이트 = impl `B2.5` 신설 (방향성 B2 ↔ 계획 B3 사이)

기능 구현 파이프라인에 **B2.5 정의 게이트**를 끼운다.

```
[B2. 방향성 점검] ★게이트★   ("어떤 접근으로?")
   ↓
[B2.5 정의 게이트] ★게이트★   ("이 경계를 넘을 때 무엇이 항상 참인가, 실패하면 어떻게 되는가?")  ← 신설
   ↓
[B3. 계획]                    ("어떤 파일을 어떤 순서로?")
```

- **B2.5 통과 조건**: 규모별 정의 강도(D3)가 채워졌고, **애매성(open question)이 전부 결정으로 해소**되었을 것. 미해소 시 B3 진입 금지(D5 가드레일).
- 훅 호환: B2.5는 `stage-transition.sh` 상으로 `1.research` 단계 내부(B2와 동일 구간).

### D2. 브리지 산출물 = `definition.md` (discuss→impl 전환 시)

토론 모드에서 구현으로 넘어갈 때(orchestration.md §3.1), 토론 결과를 `definition.md`로 남긴다. impl 진입 시 B2.5는 이 브리지 산출물이 있으면 **검증·임포트**하고, 없으면(곧장 impl 시작) **인라인으로** 규모별 정의를 작성한다.

- 저장: 대상 프로젝트 `docs/plans/{날짜}/{작업명}/definition.md` (research.md·plan.md와 같은 폴더).

### D3. 규모별 정의 강도 (과설계 방지 — codex 핵심 보정)

별도 문서를 모든 작업에 강제하지 않는다. **깊이만 조절**한다.

| 규모 | 정의 강도 | 산출물 |
|------|-----------|--------|
| **소** (1~2파일, 위험영역 아님) | plan/경량기록 안에 `불변식 / 실패 시 동작: 1~3줄 또는 N/A` | 별도 문서 없음 |
| **중** (3~10파일) | 변경 *경계별* 계약·실패의미론을 plan 전에 짧게 | plan.md 내 "정의" 섹션 또는 경량 definition |
| **대 / 위험 승격** (데이터·동시성·외부 I/O·마이그레이션·인증·결제·DB스키마) | **별도 `definition.md` 게이트 필수** + 대/고위험은 codex 발굴 | `definition.md` 풀 |

> 위험 승격 트리거는 1.2의 기존 목록을 그대로 재사용한다(동기화). "별도 definition 필수" = "최소 중규모 승격"과 같은 영역.

### D4. `definition.md` 필수 항목 (codex 4번 보강 반영)

```
0. 작업 정보 (작업명 / 규모 / scale_decider)
1. 경계 목록            — 이 기능이 닿는 모든 경계 (API · DB tx · 서비스간 · 이벤트 · 외부 I/O)
2. 경계별 불변식        — 각 경계에서 "항상 참"이어야 하는 것
3. 경계별 계약          — pre/postcondition, 입력/출력 형식·범위
4. 실패 의미론          — 재시도 가능 여부 · 중복 처리 · 부분 성공 · resume 기준
                          · 사용자에게 보이는 상태 · rollback vs forward-fix
                          · consistency boundary · idempotency 단위
5. 빠뜨리기 쉬운 4축    — 관찰가능성 / 보안·권한 경계 / 동시성 / 시간·순서 의존성
                          (각 "해당 없음" 명시 가능, 단 빈칸 금지)
6. 외부 경계 최소 체크  — (외부 I/O 있을 때) rate limit · timeout · stale read · schema drift · 감사 로그
7. 애매성 해소          — open question → 결정 (★가드레일: 미결정 항목이 있으면 B3 진입 불가)
8. 검증 매핑            — 각 불변식 → 어떤 테스트/검증 명령으로 증명하나 (X4-T 입력 · 6.6 연동)
9. 카탈로그 승격 후보   — domain-contracts.md로 올릴 불변식 표시 (D6 기준)
```

### D5. 가드레일 — 애매성 미해소 시 진입 금지

- §7(애매성 해소)에 **미결정(open) 항목이 하나라도 있으면 B2.5를 통과하지 못한다.**
- 결정이 필요한 항목은 `AskUserQuestion`으로 사용자에게 선택지를 제시해 **결정으로 전환**한다.
- "일단 구현하면서 정하자"를 금지한다. 이게 `misunderstood_request`의 직접 차단 장치다.

### D6. 학습화 — 경량 횡단 카탈로그 `domain-contracts.md`

- **위치**: 대상 프로젝트 `docs/domain-contracts.md` (project-overview.md 옆 — 프로젝트 단위 횡단 자산).
- **승격 기준(codex, 셋 중 하나 이상)**: ① 2회 이상 재사용됨 ② 깨지면 장애/데이터 손상 ③ 테스트 기준으로 쓰임.
- **항목 형식**: `경계 / 불변식 / 계약 / 실패의미론 / 최초 정의 출처(plan 폴더) / 검증 위치 / 마지막 확인일`.
- **재사용 규율**: definition.md 작성 *직전에* domain-contracts.md를 **먼저 읽고** 해당 경계의 기존 계약을 재사용/확장한다(재발명 금지).
- **낡음 방지(codex 경고 대응)**: 전수 카탈로그를 만들지 않는다. 승격분만. 각 항목 "마지막 확인일" 기록, 관련 작업 시 갱신. (5.9 `review-ledger.md` 승격 철학과 동일 — 일회성을 자산화하되 전수화 금지.)

### D7. A(버그)·C(리팩토링) 경량 적용 — 흡수 방식

정의 게이트의 주 대상은 **B(기능) + 위험 승격**이다. A·C는 별도 게이트 신설 대신 기존 게이트에 흡수한다.

- **A 버그**: "위반된 불변식 식별"이 곧 정의 — A2(진단 보고)의 원인 분석에 *"어떤 불변식이 깨졌는가 + 수정 후 그 불변식을 어떻게 보장·검증하는가"*를 1줄 추가. 새 게이트 없음.
- **C 리팩토링**: "동작 불변"이 곧 불변식 — C2(목표 정의)의 "동작 불변 약속"을 *"보존할 불변식·계약을 명시"*로 강화. 새 게이트 없음.

## 5. 설계 결과 — 파이프라인 배선

### 5.1 기능 구현(B) 다이어그램 (B2.5 삽입)

```
[B1. 리서치] → [B1.5 외부큐레이션] → [B1.6 codex 교차검증] → [B1.7 research.md]
   ↓
[B2. 방향성 점검] ★게이트★
   ↓
[B2.5 정의 게이트] ★게이트 — 신설★
     · 브리지 definition.md 있으면 검증·임포트, 없으면 규모별 인라인 작성(D3)
     · D4 항목 채움 (불변식·계약·실패의미론·4축·외부경계)
     · §7 애매성 → AskUserQuestion으로 전부 결정화 (D5 가드레일)
     · 대/고위험: codex로 "빠진 경계·불변식·실패모드" 발굴 (모델교차분석 프롬프트 재사용)
     · domain-contracts.md 먼저 읽고 재사용 (D6)
   ↓
[B3. 계획]  ← definition의 불변식·검증매핑이 plan의 완료조건·검증명령의 상위 입력
   ↓
[B4. 구현] ∥ [B4-T 테스트 설계]  ← ★ 테스트 기준 = definition의 불변식(§2·§8), 구현 아님
   ↓
[B4.5 리뷰] → [B5 테스트(+codex)] → [B6 피드백]  ← 피드백에서 domain-contracts.md 승격 판정
```

### 5.2 기존 장치와의 관계 (충돌 해소)

| 기존 | 관계 |
|------|------|
| B2 방향성 | 유지. B2.5는 B2의 "방향"을 "정의"로 한 층 내린다 (접근 → 불변식). |
| plan `완료조건` | definition §2 불변식 + §8 검증매핑이 완료조건의 **상위 입력**. 완료조건은 "이 정의를 만족하면 done"으로 도출. |
| 6.6 데이터 특칙 | definition §8 "검증 매핑"의 **한 구현 사례**로 흡수. 데이터 작업이면 불변식=count/orphan/padding, 검증=6.6 표. 정의 게이트가 6.6을 앞단으로 끌어올림. |

## 6. 구현 시 주의사항 (구현 모드 전환 시)

1. **변경은 한 번에 하나** (CLAUDE.md 반복실패방지 1). orchestration 문서 수정은 위험 승격 영역 → 페이즈로: ① definition 템플릿 신설 → ② impl B2.5 절 추가 → ③ discuss 브리지 절 추가 → ④ domain-contracts 절 + 셀프체크. 각 단계 후 사용자 확인.
2. **소규모 질식 금지** — D3 표를 정확히 지킨다. 1~2파일 단순 작업에 definition.md를 강제하면 안 된다(과설계, codex 1차 경고).
3. **가드레일은 "결정 강제"이지 "분석 마비"가 아니다** — 애매성을 AskUserQuestion으로 빠르게 결정화하는 게 목적. 무한 정의로 구현이 막히면 안 된다.
4. **카탈로그 전수화 금지** — domain-contracts.md는 승격 기준 통과분만. 낡으면 가치 < 비용(codex 경고).
