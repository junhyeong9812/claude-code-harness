## 0. 한 장 요약 (TL;DR)

- **개발의 본질은 타이핑이 아니라 사고다.** 개발자는 시간의 ~70%를 코드 *이해*에 쓰고, 순수 타이핑은 하루 수 분~수십 분이다. 코드는 머릿속 이론(theory)의 손실 많은 표현일 뿐이다.
- **LLM은 Brooks의 "우발적 복잡성"(문법·보일러플레이트·배관)을 거의 0으로 만들지만, "본질적 복잡성"(무엇을 만들지 정의·설계)은 못 줄인다.** AI에도 은탄환은 없다.
- 그래서 병목이 **생성(generation) → 평가/검증(verification)** 으로 이동한다.
- **개발자(특히 백엔드)의 역할 = 각 경계(boundary)를, 그 경계를 넘을 때 보존되어야 할 불변식(invariant)·계약(contract)·실패 의미론(failure semantics)과 함께 정의하는 것.** 흐름(flow)은 그 정의들의 골격이고, 불변식·실패의미론은 그 골격에 흐르는 피다.
- "잘 쓴다" = 더 빨리 타이핑하는 게 아니라, **외주 준 사고·판단·검증을 관리하되 통제권을 잃지 않는 능력**이다.
- 단, "병목 = 검증 시스템"이라는 결론은 **리뷰를 없애지 않는다.** 리뷰의 *대상*이 "코드가 맞나"에서 "이게 옳은가·경계를 침범하지 않는가"로 올라갈 뿐이다. 그리고 되돌리기 어려운 실패(데이터 오염·권한 누출·PII)에선 *배포 후 탐지(canary/rollback)*보다 **배포 전 증명(proof)·dry-run**이 우선이다.

## 1. 리서치 종합 (3주제)

### 1.1 2026년 LLM과 AI Agent란

- **LLM의 재정의**: "다음 토큰 예측기"가 아니라 추론(reasoning)·확장 사고(extended thinking)·도구 사용이 내장된 추론 엔진. thinking 모드가 기본 동작으로 통합됨.
- **Agent의 정의 — 통제권의 위치**(Anthropic 기준):
  - 워크플로(workflow): LLM·도구가 *사람이 짠 코드 경로*로 조율 → **당신이 배관을 소유**
  - 에이전트(agent): LLM이 *스스로* 프로세스·도구 사용을 동적으로 지휘 → **모델이 배관을 소유**
  - Agent = LLM(두뇌) + **agentic loop**(목표→인식→추론→계획→행동→관찰→메모리). ReAct(2022)의 decide→act→observe 확장형.
- **주요 흐름**: agentic coding CLI(Claude Code=품질·휴먼인더루프 / Codex=자율성), MCP(도구 연결), multi-agent/sub-agent, computer use.
- **한계 — 신뢰 문제**: 에이전트 특유 환각(도구 호출 거짓 성공, 받지 않은 승인 주장), 실행 추적 검증의 원리적 한계, 보상 해킹. → **단일 모델 자기평가보다 교차 모델 검증이 더 신뢰적.**

> **codex 보정**: 컨텍스트 "100만~1000만 토큰"은 과장(1000만은 실험·평가 맥락). MCP는 유력하나 "사실상 표준"은 단정 과함(네이티브 tool API·벤더 SDK 병존). multi-agent는 *패턴*이지 표준 아님(조율 비용·책임 추적·실패 전파 문제). "우발적 복잡성을 0으로"도 과장 — 프롬프트·컨텍스트·검증·툴체인이라는 **새 복잡성이 생긴다.**

### 1.2 잘 쓰는 사람들의 사용법

- **수렴 워크플로**: `Research → Plan → Execute → Review → Ship`. "코딩에 바로 뛰어들면 잘못된 문제를 푼다." 구성: spec-first, 검증 루프(pass/fail 신호로 루프를 닫음), 휴먼인더루프(틀리면 즉시 교정), sub-agent fan-out.
- **Prompt → Context engineering**: "프롬프트 문구 다듬기"가 아니라 "추론에 들어가는 토큰 집합 전체를 매 턴 큐레이션". 컨텍스트는 **유한 자원**이라 길어지면 **context rot**으로 정확도 하락(일부 모델 95%→60%).
- **잘 쓰는 사람 vs 못 쓰는 사람**: 차이는 *검증과 신뢰 보정*. 개발자 96%가 수동 개입 없이는 AI 코드를 신뢰하지 않음. 잘 쓰는 사람은 스코프를 좁히고("로그인 버그 고쳐" ❌ → "세션 타임아웃 후 토큰 리프레시 실패, src/auth 확인, 재현 테스트 먼저" ✅), 검증을 강제하고, 신뢰를 로그 데이터로 보정.
- **안티패턴**(over-batching·맹신·검증 생략·무한 탐색)은 전부 **"사람이 검증 루프를 안 닫은 것"의 변형.**

### 1.3 LLM 잘 쓰는 법 + '개발'이라는 행위의 본질

- **개발은 타이핑이 아니다 (고전)**:
  - **Naur, Programming as Theory Building (1985)**: 프로그램의 본질은 *공유된 정신 모델(theory)*. 코드는 그 이론의 **손실 많은(lossy) 표현**. 코드·문서만으로 이론을 복원 못 한다.
  - **Brooks, No Silver Bullet (1986)**: **본질적(essential) 복잡성**(무엇을 만들지 정의·설계) vs **우발적(accidental) 복잡성**(문법·보일러플레이트·배관). **도구는 우발적만 깎는다.**
- **행동 빈도 — 타이핑은 작은 꼬리 (측정)**: 개발자는 시간의 **~70%를 코드 이해**에 씀(Minelli 2015). 읽기:쓰기 10:1 이상(Clean Code). 순수 타이핑은 하루 수 분~수십 분.
- **LLM 시대의 귀결**: LLM은 우발적 복잡성을 강하게 공격하지만 본질적 복잡성은 그대로 → 병목이 **생성 → 평가/검증**으로 이동. "잘 쓴다"=사고·판단·검증의 외주화를 관리하되 통제권을 잃지 않는 것.

출처:
- [Peter Naur, "Programming as Theory Building" (1985)](https://pages.cs.wisc.edu/~remzi/Naur.pdf)
- [Fred Brooks, "No Silver Bullet" (1986)](https://www.cs.unc.edu/techreports/86-020.pdf)
- [Minelli et al., 70% 이해 시간 (2015)](https://www.researchgate.net/publication/293813040_I_Know_What_You_Did_Last_Summer_--_An_Investigation_of_How_Developers_Spend_Their_Time)
- [Why AI coding tools shift the bottleneck to review — LogRocket (2025)](https://blog.logrocket.com/ai-coding-tools-shift-bottleneck-to-review/)

## 2. A. 진단 — 내 마찰은 "본질적 복잡성을 건너뛴" 것이다

`/insights` 최대 마찰 두 가지:
- `wrong_approach` **27회** — 여러 변경을 한 번에 묶어 빌드를 깸 (예외+상속+데드코드+폴더이동 동시).
- `misunderstood_request` **23회** — 잘못된 소스/repo/스코프를 잡고 오래 진행 (CSV 마이그레이션 코드에 매달림, DB를 프로덕션으로 오인, credential 전체 grep).

이론 대입 — 둘은 **같은 뿌리**:

1. **over-batching = 본질적 복잡성을 정의하지 않고 우발적 복잡성부터 처리.**
   변경을 묶었다는 건 "이 리팩토링이 *무엇을 보존해야 하는가*(= 불변식)"를 확정하지 않고 타이핑부터 시작했다는 뜻. 빌드가 깨진 건 LLM의 능력 부족이 아니라 **"한 번에 하나, 각 단계 후 빌드 통과"라는 검증 루프가 닫히지 않은 채 풀어준 것.**

2. **잘못된 소스/스코프 = Naur의 theory를 전달하지 않음.**
   "어느 것이 canonical source인가"라는 머릿속 이론이 컨텍스트에 없었음. 코드는 거기 있었지만 "무엇이 정답인가"라는 이론은 코드에 안 적혀 있다(코드는 이론의 손실 표현). → CLAUDE.md "작업 전 기준 소스를 먼저 확정한다" 규칙이 정확히 이 손실을 메우는 장치.

**대응이 옳았던 이유**: 두 경우 모두 *즉시 끊고 교정*(course-correct early) → 잘 쓰는 사람의 핵심 행동. **문제는 교정 능력이 아니라, 교정이 필요해지기 *전에* 본질(불변식·기준소스)을 앞단에서 못 박는 습관의 부재.**

> 한 줄: 내 마찰은 LLM이 멍청해서가 아니라, **"무엇이 항상 참이어야 하는가"를 코드 작성 전에 명시하지 않아서** 생긴 것.

## 3. B. "개발 = 사고"가 *내 실무*에서 구체적으로 뭔가

| 작업 | 타이핑(우발적, LLM이 함) | 사고(본질적, 내가 줘야 함) |
|------|------------------------|--------------------------|
| **마이그레이션** (트레이드마크 1.2M행) | ETL 루프, MySQL/ES 커넥션, CSV 파서 | "zero data loss"의 정의 = source count == target count AND 모든 child row가 올바른 parent에 연결 AND international_code 패딩 보존 AND nice_classes 페어링 유지 |
| **RBAC/인증** | JWT 발급, 토큰 리프레시 핸들러 | 토큰 폐기가 *반드시* 반영되어야 할 시점, sliding token 만료 불변식, 동시 요청에서 권한 변경의 일관성 경계 |

- `lastrowid` 버그로 671행이 오연결된 건 타이핑 실수가 아니라 **불변식("부모-자식 연결은 항상 정확하다") 위반**. row-count 검증이 그 불변식을 사후에 잡아냄.
- **결론**: LLM에게 줘야 하는 건 코드가 아니라 **"무엇이 항상 참이어야 하고, 깨지면 무슨 일이 일어나는가"라는 이론.** LLM이 코드를 잘 짤수록 내 부가가치는 *코드 쓰는 쪽*이 아니라 *불변식을 정의하고 위반을 검증하는 쪽*으로 100% 이동.

## 4. 명제 정립 — "역할 = 통신의 흐름을 설계·정의하는 것"

원 명제(내 직관): **"결국 역할은 각 통신의 흐름을 설계하고 정의하는 것."**

세 의견을 합친 최종형:

> **개발자(특히 백엔드)의 역할 = 각 경계(boundary)를, 그 경계를 넘을 때 보존되어야 할 불변식·계약·실패 의미론과 함께 정의하는 것.**
> 흐름은 그 정의들의 골격이고, 불변식·실패의미론은 그 골격에 흐르는 피다.
> LLM은 골격을 그리고 살을 채우지만, *피(무엇이 참이어야 하는가)*는 내가 공급해야 한다.

검증 과정에서 갈린 지점:
- **Claude**: "흐름의 *그림*(A→B→C)은 쉽고 LLM도 잘 그린다. 진짜 본질은 *흐름의 선*이 아니라 각 경계의 불변식·실패의미론" → "흐름 < 불변식"으로 이분.
- **codex 반박(채택)**: "흐름을 너무 낮게 보지 말라. 흐름을 *시간·재시도·순서·중복·부분 실패·관찰가능성*까지 포함하면 그 자체가 본질적 복잡성. **흐름 < 불변식이 아니라, 좋은 흐름 설계는 불변식과 실패 의미론을 *품은* 흐름 설계.**" → 내 이분법이 과했음을 인정. 원래 단어 "흐름을 설계하고 *정의*"가 이미 codex 쪽에 가까웠음.

**codex가 추가한, 프레임에 빠졌던 핵심 2개**:
1. **idempotency + consistency boundary**: "이 작업은 몇 번 실행돼도 안전한가? 어디까지가 하나의 일관성 단위인가? 실패 후 재개 기준은?" 키워드: idempotency, transaction boundary, outbox/inbox, retry semantics, schema evolution, reconciliation.
2. **불변식의 강제 vs 보정 결정**: 모든 걸 강한 invariant로 만들면 시스템이 경직된다. "어떤 불변식은 코드로 *강제*하고, 어떤 것은 감시·보정(reconciliation)·운영으로 처리할지 *결정*하는 것"까지가 역할.

## 5. "병목은 리뷰가 아니라 신뢰 가능한 배포 체계"

### 5.1 전개

- 병목 이동 3단계: **생성 → 평가/리뷰 → 신뢰 가능한 배포 체계.**
- 왜 *인간 리뷰*가 최종 답이 아닌가: (a) 인간 리뷰는 생성량에 비례해 확장 안 됨, (b) 인간은 그럴듯한 코드 속 불변식 위반을 잘 못 잡음(trust-then-verify gap).
- 해법: B에서 정의한 불변식을 **실행 가능한 검증**(test·type·contract·property test·invariant monitor)으로 인코딩 + 안전한 배포 메커니즘(canary·feature flag·rollback·observability). → 인간의 일은 "검증 수행"에서 "검증 시스템 설계"로 이동.

### 5.2 codex 보정 (둘 다 채택)

**보정 1 — "리뷰가 병목이 아니다"는 과하다.**
> 인간 리뷰가 최종 답은 아니지만, 리뷰는 코드 검증을 넘어 **의도·아키텍처·보안 경계·운영 리스크를 확인하는 마지막 인간 판단**으로 여전히 핵심.

→ 정확히는 **리뷰의 *대상*이 바뀐다**: "코드가 맞나"(시스템이 검증) → "이게 옳은가·경계를 침범하지 않는가"(인간이 검증).
(주의: 자주 인용되는 `리뷰 4.3분 vs 1.2분` 수치는 1차 연구가 아니라 블로그성 인용 — 강한 근거로 쓰지 말 것.)

**보정 2 — canary/rollback로 안 되는 실패가 있다.**
> canary/rollback은 *운영 장애*엔 강하나 **데이터 오염·권한 누출·PII 노출처럼 "되돌리기 어려운 실패"엔 불충분.** 이런 고비용 작업은 *배포 후 탐지*보다 **배포 전 증명(proof)·dry-run**이 우선.

→ 내 일(마이그레이션·RBAC)은 대부분 **되돌리기 어려운 실패** 카테고리 → "배포하고 모니터링" 모델이 부분적으로만 맞음.

### 5.3 내 도메인에 맞춘 구체화 (codex)

- **마이그레이션**: row-count + 샘플 diff로는 부족. → **idempotency, resume 가능성, chunk 단위 검증, checksum/aggregate reconciliation, dual-read/shadow-read, rollback 또는 forward-fix 계획.**
- **RBAC**: 테스트 몇 개가 아니라 **`role × resource × action × ownership/tenant` 매트릭스**, deny-by-default, negative test, privilege escalation property test.
- **로그/모니터**: 단순 에러율이 아니라 **비즈니스 불변식** — 마이그레이션 후 orphan row 수, 권한 없는 접근 시도, role별 접근 분포 변화, 테넌트 경계 위반 시그널.
- 핵심: "AI 코드 검증"이 아니라 **"변경이 시스템 경계를 침범하지 않는다는 증거를 자동으로 남기는 것."**

### 5.4 가장 날카로운 경고

> 테스트·모니터가 좁게 설계되면 "검증 시스템이 있으니 안전하다"는 **허위 확신**이 생긴다. 특히 **AI가 만든 코드와 AI가 만든 테스트가 같은 오해를 공유**할 수 있다.

→ "검증 시스템 설계자" 역할의 함정: *검증 시스템 자체는 누가 검증하나?* 그래서 **불변식은 AI가 아니라 도메인 이론 보유자(나)가 정의**해야 하고, 가능하면 코드와 테스트의 출처를 분리해야 한다.

### 5.5 과잉이 되는 경우

- 작고 되돌리기 쉬운 내부 변경에까지 canary/rollback을 붙이면 **속도보다 절차 비용**이 커진다 → 위험도에 따라 rigor 조절.
- 이 프레임은 correctness/safety엔 강하지만 **"이 기능이 맞는가·정책 해석이 옳은가·사용자에게 해로운가"는 대체 못 한다.** 그건 여전히 인간 판단.

## 6. 실천 결론 (내가 가져갈 것)

1. **코드 작성 전에 "불변식·기준소스·실패조건"을 먼저 못 박는다.** (CLAUDE.md "기준 소스 확정" 규칙을 "불변식·실패조건 확정"으로 확장 — 후속 작업 후보.)
2. **변경은 한 번에 하나, 각 단계 후 빌드/검증으로 루프를 닫는다.** (이미 규칙화돼 있음 — 본질적 근거가 보강됨.)
3. **검증은 "수행"이 아니라 "시스템 설계"로 승격한다.** row-count 하니스를 매 작업 즉흥 구축이 아니라 상시 harness로.
4. **되돌리기 어려운 작업은 배포 전 증명·dry-run을 우선한다.** (마이그레이션·권한 변경·삭제·PII.)
5. **검증 시스템 자체를 의심한다.** 불변식은 내가 정의하고, AI 코드와 AI 테스트가 같은 오해를 공유하지 않도록 출처를 분리한다.
6. **리뷰를 버리지 않는다 — 대상을 올린다.** 코드 정합성은 시스템에, 의도·아키텍처·보안 경계·정책 해석은 인간에게.
