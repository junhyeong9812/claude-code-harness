## 1. 배경 — 왜 이 문서인가

하네스 v2는 **"언제, 얼마나 세게 검증하나"(프로세스 제어)는 정교하지만 "무엇을 보나"(도메인 판단 기준)는 얇다.**
칸2의 5축(실패 의미론/외부 경계/시간·동시성/보안·권한/관찰가능성)이 압축형으로 존재할 뿐,
시니어 개발자가 변경을 볼 때 도는 점검 차원들이 명시돼 있지 않다.

사용자가 정리한 18개 항목이 그 본체다:

1. 기능 요구사항 / 2. 입력 검증 / 3. 권한 경계 / 4. 데이터 정합성 / 5. 동시성 /
6. 예외 처리 / 7. 변경 가능성 / 8. 성능 / 9. 장애 복구 / 10. 운영 가능성 /
11. 보안 / 12. API 설계 / 13. 테스트 가능성 / 14. 도메인 규칙 / 15. 데이터 모델링 /
16. 비용 / 17. 사용자 경험 / 18. 협업 가능성

### 핵심 설계 논쟁과 합의

- **선별(판단) vs 전수(기준화)**: "이 변경에 어떤 차원이 해당하나"를 매번 판단에 맡기면
  회상(recall) 누락이 발생하고, 누락 사실 자체가 기록에 남지 않는다 (사용자 지적: "경우의 수가 너무 많다").
- 반대로 18개 전수 심층 점검을 균일 의무화하면 v1 실패(50k 선독·체크박스 연극)를 재현한다.
- **합의된 구조: 전수 스캔은 의무(싸니까), 깊은 검증은 선별(비싸니까).**
  - 트리아지: 정의 게이트에서 조건부 차원 전수 스캔 — 각 차원에 해당/비해당 + **근거 1줄** (비해당에도).
  - 활성 차원만 계획·개발·검증에서 렌즈 가동, 강도는 stakes 비례.

## 2. 성격 분류 — 18개는 같은 종류가 아니다

18개를 단계에 일렬로 꽂으려 하면 어긋난다. 네 가지 성격으로 먼저 갈라야 한다.

| 종류 | 의미 | 해당 항목 | 하네스에서의 자리 |
|------|------|----------|------------------|
| **게이트 재료** | 차원이 아니라 정의 게이트 그 자체 | 1 기능 요구, 14 도메인 규칙 | 명확도 6칸의 칸1(목표)·칸2(불변식)가 이미 수행 |
| **조건부 차원** | "이 변경이 X를 건드리는가?"로 판정 가능 → 활성 시에만 하류 렌즈 가동 | 2 입력검증, 3 권한, 4 정합성, 5 동시성, 6 예외, 8 성능, 9 장애복구, 10 운영, 11 보안, 12 API 설계, 15 데이터 모델링, 17 UX (12개) | **트리아지 표** (정의 게이트에서 전수 스캔) |
| **상시 렌즈** | 모든 변경에 해당 → 트리아지 무의미, 항상 리뷰에서 봄 | 7 변경 가능성, 13 테스트 가능성, 18 협업 | 리뷰 패스 프롬프트에 상시 인라인 |
| **판정 입력** | 체크 대상이 아니라 stakes·스코프 결정의 입력 | 16 비용 | 칸6 판정 + 계획 단계의 "이 복잡도를 감당할 가치" 질문 |

**분류 근거:**

- 게이트 재료를 차원으로 두면 "기능 요구: 해당" 같은 무의미 행이 생긴다. 1·14는 점검 대상이 아니라 작업 정의 그 자체다.
- 상시 렌즈를 트리아지에 넣으면 매번 "해당"이라 행 낭비 + 트리아지의 변별력을 희석한다.
- 비용은 "건드리나/아니나"가 아니라 "감당할 가치가 있나"라는 다른 종류의 질문이다.

## 3. 단계 배치 — v2 파이프라인 위에 얹기

같은 차원이 단계마다 모습을 바꿔 재등장한다. 따라서 지도는 단계별 별도 목록이 아니라
**차원 × 단계 매트릭스** (차원당 한 항목에 트리아지 질문 / 계획 질문 / 구현 렌즈 / 검증 렌즈가 묶임).

```
[정의] ──────────────────────────────────────────────
  칸1·칸2 채우기        ← 1 기능 요구, 14 도메인 규칙 (게이트 재료)
  트리아지 전수 스캔     ← 조건부 차원 12개: 해당/비해당 + 근거 1줄
  칸6 stakes 도출       ← 16 비용 + 트리아지 결과 (§4)

[계획] ──────────────────────────────────────────────
  활성 차원의 "설계 결정" 질문만 펼침:
    4 → 트랜잭션 경계·롤백 범위         5 → 락/멱등 메커니즘 선택
    9 → retry·timeout·fallback 전략     8 → 인덱스·페이징 전략
    12 → 계약 형태(URL·Method·에러 포맷) 15 → 스키마·관계·삭제 정책
    6 → 에러 코드·메시지 정책 (프로젝트 기존 전략 확인)

[개발] ──────────────────────────────────────────────
  활성 차원의 "구현 렌즈":
    2 → 백엔드 최종 방어선 위치          10 → 로그·traceId·설정 외부화
    11 → 시크릿·마스킹·인젝션 방어       6 → 예외 일관성 (playbook 기존 규칙)

[검증] ──────────────────────────────────────────────
  활성 차원별 분리 리뷰 (stakes 비례 — 중간=렌즈 인라인 패스, 높음=차원군별 워커):
    2·3·11 → 이상 입력·권한별 결과·공격 표면 테스트
    4·5   → 동시 요청·중복 요청·상태 전이 테스트
    9     → 의존 실패·재시도 중복·DLQ 플로우 디버깅
    8     → 쿼리 수·N+1·대량 데이터
    17    → 사용자 가시 동작 확인
  + 상시 렌즈 3개 (7·13·18) → 트리아지 무관, 리뷰 패스에 항상 인라인

[기록] ──────────────────────────────────────────────
  비해당 판정한 차원이 구현·검증 중 등장했나 → measurement-log
  (트리아지 오판 데이터 = 지도 개정의 측정 근거, core §0-3)
```

기존 v2와의 관계: 이 배치는 새 기계장치가 아니다. 칸2의 5축을 12차원으로 정밀화하고,
verification playbook의 예외 경로·플로우 디버깅·데이터 특칙과 "렌즈 질문 인라인" 구조(core §5)에
내용을 공급하는 것이다. core.md 본문에는 트리아지 의무 + 지도 포인터 3~4줄만 추가되고,
지도 본체는 정의 단계 진입 시에만 읽는 조건부 문서로 둔다 (§0-2 컨텍스트 비용 제약 유지).

## 4. 발견 — 트리아지가 stakes를 도출한다 (단, 하한만)

core §4의 stakes 표를 보면 중간/높음의 정의가 사실상 이 차원들의 목록이다:
- 중간 = "동시성·재시도·부분 실패·외부 API·config/query" ≈ 차원 5·9 활성
- 높음 = "불가역·보안·권한·결제·public API/계약" ≈ 차원 3·11·12·15(쓰기) 활성

따라서 트리아지를 먼저 돌리면 **칸6이 감(판단)에서 계산(활성 차원 → stakes 하한)으로 바뀐다.**

**한계 (자기 반증):** stakes = 손실 × 낯섦 × 모호성 × 불가역인데, 트리아지가 잡는 것은
손실·불가역 축뿐이다. **낯섦(처음 쓰는 lib·패턴)과 모호성(요구사항 불명확)은 차원과 무관하게
stakes를 올린다.** 그러므로 트리아지 도출은 "하한"이고, 낯섦·모호성에 의한 승격 판단은 남는다.
→ 칸6 = max(트리아지 도출 하한, 낯섦·모호성 판단).

## 6. archive에서 건진 경고

구 하네스 `templates/domain-contracts.md` (archive/2026-06-10-opus-harness/)의 codex 경고:

> **전수 카탈로그 금지 — 낡으면 유지비 > 가치. 승격 기준 통과분만 올린다.**

당시 대상은 "프로젝트별 불변식 누적 카탈로그"였고 지금 만드는 것은 "고정 차원 지도"라 성격이 다르지만,
번역하면 유효하다: **지도는 작고, 범용이고, 안정적이어야 한다.** 차원 수를 늘리거나 렌즈 질문을
프로젝트 특화로 비대하게 만들면 같은 함정에 빠진다. 지도 개정은 measurement-log의
트리아지 오판 데이터를 근거로만 한다 (§3 [기록] 참조).

## 8. 사용자 결정 포인트 — **2026-06-10 결정 완료**

> 사용자 결정 (최종, 같은 날 수정): **A1 (전 stakes 동일 — 14행 전수+증거) / B2 (보정 포함) / C 일괄 채택(14개) / D1 (백엔드 기본만)**
> 최초 선택은 A2·D2였으나 사용자가 A1·D1로 수정. 아래는 결정 당시 제시된 선택지 원문.
> ⚠️ A1은 core의 경량 경로(낮음·자명=채팅 대체)와 상호작용 — 낮음 작업의 14행을 어디에 남길지(채팅 보고 vs task.md 강제)는 하네스 반영 게이트에서 해소할 것.

### A. 트리아지 증거 강도 — stakes별 차등을 둘 것인가
codex 최중요 지적(C1)대로 `판정/근거/본 파일·심볼/불확실성` 형식을 의무화하면 정의 게이트가 무거워진다.
- **A1. 전 stakes 동일 의무** — 일관성 최대, 낮음 작업의 오버헤드 증가
- **A2. (추천) 낮음=활성 차원만 한 줄 나열(경량 경로와 정합), 중간↑=14행 전수+증거 참조** — 기존 경량 경로 철학과 일치
- A2 채택 시: 낮음에서 트리아지를 생략한 차원이 터지면 그 자체가 측정 데이터(승격 트리거)

### B. stakes 도출 규칙의 복잡도
- **B1. 단순 하한**: 활성 차원 → 하한 (인플레이션 위험 수용, 규칙 1줄)
- **B2. (추천) 하한 + 영향면 보정 + 누적 승격 + 면제 조건(증거 의무)** — codex C5·C6 반영, 규칙 4~5줄
- B2가 정확하지만 규칙이 늘어남 — "판단 기준 제공 vs 절차 강제" 균형을 사용자가 결정

### C. 차원 구성 확정 — 12개 vs 14개(+이중 소속 3)
- C2~C4 반영 시: 조건부 차원 14개 (12 + 도메인 규칙 + 비용), 이중 소속 3건(14·16·13), 17 개명
- 일괄 채택할지, 일부만 채택할지 (개별 기각 의견 있으면 §7 표 번호로)

### D. 확장팩 작성 범위 (지금 vs 나중)
- **D1. (추천) 지금은 백엔드 기본 지도만** — 확장팩(배치/프론트/인프라)은 해당 surface 작업이 실제로 등장할 때
- D2. 배치·데이터 파이프라인 팩까지 지금 작성 — 사용자 작업에 배치가 많다면

차원당 트리거 질문 1 + positive signal 3 + negative signal 2 + 경로 힌트, 본체 ≤200줄. 백엔드 기본만(D1 —

### 질문 진화 루프 (2026-06-10 합의 — 매트릭스 작성 게이트의 입력)

질문 세트를 고정 가이드라인으로 쓰되, 작업에서 질문이 안 맞으면 역제안으로 개선하는 루프 (C9·C13의 확장):

1. **구분**: 비활성(차원이 안 닿음 — 트리아지의 정상 경로, 제안 대상 아님) vs **부적합**(질문 자체가 이 도메인에 안 맞거나, 구현 중 드러난 실패모드를 어떤 질문도 못 잡음 — 이것만 역제안 대상).
2. **작업별 기록**: 부적합 발생 시 Claude가 대체/신규 질문을 사용자에게 제안 → 사용자 결정 → task.md "질문 보정 기록" 절에 `질문 ID / 부적합 사유 / 제안 질문 / 사용자 결정` 기록. **정본은 그 자리에서 고치지 않는다.**
3. **승격**: 월 1회 측정 리뷰에서 승격 기준 통과분만 정본(매트릭스) 반영 — ① 서로 다른 작업에서 2회+ 재등장 ② 질문 공백이 실제 결함으로 이어짐 (archive domain-contracts 승격 기준 재사용). docs/17(인간용)은 승격분만 반영하는 안정 문서로 유지.
4. **전제**: 매트릭스의 질문에 ID를 부여해 보정 기록이 참조 가능하게 한다.
