## 0. 배경 — 이 설계가 나온 흐름

[07](07-코드리뷰-하네스-설계-참고.md)에서 Claude 코드리뷰의 **가이드레일**(생성자≠채점자, 분석≠수정, 검증은 별도)을 정리했다. 사용자가 이 역할 분리 원칙을 **구현 파이프라인 전체**로 확장하자고 제안:

> research=메인 / plan·context·checklist=별도 에이전트 / 구현·테스트설계=각각 별도 워커 / 이후 리뷰 / 검증=별도 워커 / 전체 통합 기반 learned.md.

추가로 두 가지:
- **메인 워커 = 페르소나 캐스팅 디렉터** (리서치 기반 페르소나 도출 → codex 적합성 검증 → 그 페르소나로 작업 지시).
- **규모를 사용자가 주면 그 규모대로 처리**하는 요구사항.

이 문서는 그 제안을 **현재 시스템 실측에 대입해 평가·정제한 결과**다.

## 2. 제약조건 (현재 시스템 실측)

설계는 아래 **현재 구조의 제약**을 위반하지 않아야 한다.

| 제약 | 근거 (file:section) |
|---|---|
| **게이트는 메인↔사용자 대화** — B2 방향성, B3 plan 승인, 대규모 주석/검토 반복. 격리 컨텍스트 워커는 이 대화를 못 가짐 | `impl B2(465) / B3(519-524)` |
| **codex가 이미 각 게이트의 독립 제2관점** — 큐레이션(X.5)/교차검증(X.6)/plan검토(X3)/테스트검증(X5) | `impl 4.B / agent §11.2` |
| **Plan·Explore 에이전트는 read-only** — Write 불가. 문서 저작은 general-purpose만(가장 비쌈) | `agent §1 표` |
| **에이전트 결과는 메인이 검증, 최종 결정은 메인** | `agent §5 / §11.9` |
| **병렬 최대 3 · 같은 파일 동시 수정 금지** | `agent §4.2` |
| **규모별 강도 모델** 이미 존재(소/중/대 → 산출물·검증 깊이) | `impl 1.2` |
| **위험 승격** — auth/결제/데이터마이그레이션/public API/빌드설정/DB스키마 등은 "최소 중규모" | `impl 1.2` |
| **페이즈 게이트** — 중/대규모는 페이즈 분리 + 로컬 검증 게이트(codex는 최종 1회) | `impl 5.8` |
| **learned.md 작성 전 변경파일 전부 재읽기 의무** — 메모리 의존 금지 | `impl 0.1 / 7.3` |
| **사용자 명시 기준 최우선** | `orchestration.md §2.4 / CLAUDE.md 규칙 2` |

핵심 함의: **현재 시스템은 이미 "메인 생성 + codex 독립 검증"의 2자 구조다.** 멀티워커는 이를 대체하는 게 아니라, codex가 못 메우는 *커버리지/특화*와 *생성자≠검증자 분리*를 더하는 것.

## 3. 결정 사항

### D1. 소유권 절단선 (ownership cut line)

> **사용자 합의·전체 판단이 필요한 산출물은 메인이 소유한다. 독립성이 품질을 직접 올리는 검토·테스트·검증은 별도 워커로 분리한다.**

| 단계 | 소유 | 비고 |
|---|---|---|
| research 판단 | **메인** | 무거운 탐색만 Explore 위임. 독립 신호=codex(B1.6) |
| **plan.md** | **메인(author)** + 선택적 워커(drafter) | plan은 "구현 지시서가 아니라 사용자와 합의하는 **계약**". 독립성은 codex(B3)가 이미 제공 |
| context/checklist | 워커 초안 가능 | plan에서 파생되는 기계적 산출물 → 컨텍스트 절약용 |
| 구현 | 워커(독립 모듈) 또는 메인 | 기존 `§7.1`·`§4.2` 규칙 |
| **테스트 설계** | **별도 워커** | 구현자와 분리(확증편향 차단) |
| **리뷰** | **별도 워커(신설)** | 구현자와 분리(G6) — `spec compliance reviewer` |
| 검증 | 별도 워커(리포트) | **최종 판정=메인** |
| learned.md | **메인** | 전체 실행 결과의 해석·조직 기억. 변경파일 재읽기 의무(7.3) |

**왜 plan/learned는 메인인가:** plan은 사용자 승인·주석 대상이고, learned는 전체 작업의 통합 해석이다 — 둘 다 격리 워커가 가질 수 없는 "전체 컨텍스트 + 사용자 대화 스레드"를 요구한다. codex 정정: plan은 "완전 금지"가 아니라 **`author=메인 / drafter=선택적 워커`**.

### D2. 테스트 설계 분리 (강한 채택) — 입력 스코프 규율 필수

- 같은 워커가 코드+테스트를 짜면 *자기 코드를 통과시키는* 테스트를 짠다(확증편향). → 테스트는 **plan/spec 기준**으로 별도 워커가 설계.
- **★ Test 워커는 구현 diff를 먼저 보면 안 된다.** 입력 = `plan/spec/context`. 구현 확인은 나중 단계로 제한. 안 그러면 분리가 형식적(구현 종속 테스트).
- plan에서 파생하므로 **구현과 병렬 가능** — 단 plan이 명확할 때만(모호하면 impl/test 해석이 발산).

### D3. 리뷰 단계 신설 = `spec compliance reviewer`

현재 파이프라인엔 리뷰 전용 단계가 없다(codex 테스트검증 B5 + 셀프체크 §11뿐). [B4.5] 리뷰 게이트를 신설하되, 단순 버그탐색이 아니라:
- plan ↔ 구현 불일치
- 테스트가 spec을 검증하는지 vs 구현을 따라갔는지
- 변경 범위 초과 (`§5.2` 범위 통제와 연동)
- 실패 케이스 누락
- 기존 동작 회귀 가능성

[07]의 가이드레일 1차 세트(G1 오탐배제 → G2 신뢰도≥80 → G5 포스팅 규율)를 이 워커의 계약으로.

### D4. 메인 워커 = 페르소나 캐스팅 디렉터

> 메인이 리서치로부터 **이 작업에 맞는 최소 페르소나 캐스팅**을 도출 → B2 게이트에서 codex가 "빠진/과한 페르소나" 검증 → 입력 스코프 부여해 작업 지시 → **최종 판정은 메인**.

페르소나 라이브러리 = [07] §1.4의 코드리뷰 차원 에이전트(보안/동시성/타입/테스트/주석/단순화 …)를 일반화한 것.

규율 5종:
1. **페르소나는 이름이 아니라 계약.** 각 페르소나 = `볼 것 / 안 볼 것 / 산출물 형식` 3종 계약. (예: 테스트설계자 = "impl diff 안 봄 / plan·spec만 / 출력=테스트 케이스 목록")
2. **캐스팅은 게이트 대상.** 메인이 위험을 못 보면 페르소나도 못 뽑는다(단일 실패점) → B2에서 codex가 누락/과잉 점검. **새 호출 아님 — 기존 B1.6/B2에 "제안 캐스팅" 항목으로 접어넣기.**
3. **최소 캐스팅.** 고정 로스터 금지 — 변경에서 도출.
4. **권위 착시 방어.** "보안리뷰어" 라벨로 약한 지적이 과대평가되지 않게 — 신뢰도 채점(G2)·증거수준은 라벨과 무관 적용.
5. **최종 판정 ≠ 투표 집계.** 메인은 종합자이지 집계자가 아니다 — 근거 품질 기준으로 재평가.

### D5. 페르소나 ≠ codex (혼동 금지)

| | 페르소나 | codex |
|---|---|---|
| 제공 | 관점 분산·전문 체크리스트·탐색 범위 확장 | 모델 다양성·합의 편향 견제 |
| 독립성 | **약한(절차적)** — 같은 모델, 다른 입력/체크리스트/목표함수 | **강한** — 다른 모델·추론 습관 |

codex 정정: 페르소나도 *약한* 독립성에 기여(다른 입력 스코프면 일부 사각지대 감소)하나, 같은 Claude 다수 페르소나는 같은 모델 사각지대를 공유. **커버리지=페르소나, 독립성=codex. 페르소나 다수결은 codex 검증을 대체 못 함.**

### D6. 규모 사용자 오버라이드 + 위험 하한 예외

```
- 사용자가 규모를 명시하면 → 사용자 기준 우선 (기존 "사용자 명시 기준 최우선"과 일관)
- 단, 위험승격 영역은 최소 규모 하한을 가진다
- 사용자 지정 규모 < 하한 → 자동 하향 금지 (결제 변경을 조용히 소규모 처리 X)
  → 충돌을 게이트로 노출 → 사용자 재확인 → 강행 시 그 결정을 기록하고 진행
- 기록: scale_decider=user|ai / risk_floor_applied=T|F / override_confirmed=T|F
```
프레이밍: **"AI가 사용자를 막는다"가 아니라 "위험 하한과 사용자 규모의 충돌을 게이트로 노출한다."** 최종 결정권=사용자, **조용한 축소만 금지.**

### D7. opt-in 3단계 — 규모가 캐스팅 깊이를 결정

```
소규모   : 페르소나 캐스팅 없음. 메인 + 셀프체크 + (필요시) codex 1회
중규모   : 1~2개 페르소나 (테스트설계자 OR spec준수리뷰어) + codex 검증
대/고위험: 풀 캐스팅 (구현/테스트설계/리뷰/검증 페르소나)
          + 캐스팅을 B2 게이트에서 codex 검증 + 메인 최종 판정 + learned.md
```
기존 `1.2 규모별 강도`·`5.8 페이즈 게이트`·[07] §8.3 "고급기능 opt-in"과 정합. 대규모 풀 캐스팅 실행체는 `Workflow` 도구(`dimensions→find→verify→synthesize`).

## 4. 설계 결과 — 통합 파이프라인 (기능 구현 4.B 기준)

```
[B1 리서치]                         메인 (탐색은 Explore 위임 가능)
   ↓
[B1.5 외부 큐레이션]                Claude WebSearch + codex
   ↓
[B1.6 모델 교차검증 + 캐스팅 검증]   ★추가★ codex가 분석 + "제안 페르소나 캐스팅" 점검
   ↓
[B1.7 research.md]                  메인 소유
   ↓
[B2 방향성 게이트 + 캐스팅 확정]     ★확장★ 방향 + 페르소나 캐스팅 + 규모(사용자 오버라이드/위험하한) 사용자 확인
   ↓
[B3 계획]                           plan=메인 author / context·checklist=워커 drafter 가능 / codex plan검토
   ↓
   ├─[B4 구현]            구현 페르소나/워커 (독립 모듈) ┐  plan에서 병렬 파생
   └─[B4-T 테스트 설계]   테스트설계 페르소나 (impl diff 미열람, spec 기준) ┘
   ↓
[B4.5 리뷰 게이트]                  ★신설★ spec compliance reviewer (구현자와 분리) — [07] 가이드레일
   ↓
[B5 테스트 실행 + 검증]             검증 워커(리포트) + codex 테스트검증 / ★최종 판정=메인★
   ↓
[B6 피드백 + learned.md]            메인 소유 (변경파일 재읽기)
```
- 버그(4.A)·리팩토링(4.C)도 동형 적용. 단 A2 진단 게이트·C2 목표 게이트에 캐스팅 확정을 얹는다.
- **소규모는 캐스팅·워커 분리 면제** — 기존 5.8 면제와 동일.

## 5. 구현 시 주의사항 — 새 실패모드 (도입 전 박을 것)

> codex 2회(파이프라인·페르소나)가 공통 지적한 멀티워커/페르소나 고유 위험.

| 실패모드 | 방어 |
|---|---|
| **컨텍스트 단절** — 워커가 사용자 게이트 뉘앙스를 모름 | 게이트 판단은 메인 전담. 워커엔 확정된 계약만 전달 |
| **책임 분산** — "누가 최종 품질을 보장했나" 흐려짐 | **최종 판정=메인** 못박기(D1·D4) |
| **통합 비용** — 워커 산출물 충돌을 메인이 재해석 | 산출물 형식 계약 통일, 충돌은 메인이 근거로 재평가 |
| **중복 검토 피로** — codex 검증 ≈ 워커 리뷰 반복 | 역할 분담 명시(페르소나=커버리지, codex=독립성) |
| **잘못된 독립성** — 같은 plan 결함을 모두 공유 → 같은 방향 오류 | plan 결함은 codex(다른 모델)가 게이트에서 / 페르소나 다수결 금지 |
| **테스트-구현 병렬 발산** — plan 모호 시 해석 갈림 | plan 명확성이 병렬화 전제(B2/B3 게이트에서 확인) |
| **고정 로스터화** — 습관적 풀 캐스팅 | 최소 캐스팅 + opt-in 3단계 강제 |
| **스코프 누수** — 테스트설계자가 impl을 봄 | 입력 스코프 계약(D2) |
| **권위 착시** — 라벨로 약한 지적 과대평가 | 신뢰도/증거수준을 라벨 무관 적용(D4-4) |
| **최종 판정 오염** — 메인이 투표 집계자화 | 근거 품질 재평가(D4-5) |
| **비용 폭증** — 오케스트레이션 비용 > 품질 향상 | opt-in 3단계, 소/중규모 린 유지 |
