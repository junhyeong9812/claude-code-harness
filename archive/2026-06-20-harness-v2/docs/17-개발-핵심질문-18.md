## 1. 기능 요구사항 — 무엇을 만들어야 하는가?

- 누가 사용하는가?
- 필수인 값은 무엇인가?
- 어떤 기능들이 세부적으로 필요한가?
- 데이터를 어떻게 저장할 것인가? 타입은?
- 실패하면 어떻게 처리할 것인가?
- 실패의 경계는 어디인가?

## 2. 입력 검증 — 이상한 값이 들어오면?

- 빈 값을 허용하는가?
- 길이 제한·날짜 형식·숫자 범위·enum 값을 검증하는가?
- SQL Injection / XSS 위험은?
- 프론트 검증과 백엔드 검증의 역할이 분리돼 있는가?
- **백엔드가 최종 방어선이다** — 프론트에서 막았어도 백엔드에서 또 막는가?

## 3. 권한 경계 — 누가 할 수 있는가?

- 인증: 누구인가?
- 인가: 이걸 해도 되는가?
- 소유권: 이 리소스가 정말 그 사람 것인가?
- (+) 권한을 건드렸다면 보안(11)도 같이 본다 — broken access control은 보안 문제이기도 하다.

## 4. 데이터 정합성 — 끝난 뒤 데이터 상태가 말이 되는가?

- 어느 범위까지 하나의 트랜잭션으로 묶을 것인가?
- 중간에 실패하면 어디까지 롤백할 것인가?
- 중복 요청이 들어오면 어떻게 막을 것인가?
- 동시에 같은 데이터를 수정하면 어떻게 되는가?
- 삭제는 물리 삭제인가, 논리 삭제인가?
- 상태값 전이는 올바른가?

## 5. 동시성 — 동시에 요청이 오면?

사용자 연타, 네트워크 재시도, 배치 중복 실행을 가정하라. 어떤 방어를 쓸 것인가:

- DB unique constraint
- optimistic lock / pessimistic lock / 분산락
- idempotency key
- 상태값 기반 중복 방지
- 요청 deduplication

## 6. 예외 처리 — 실패를 어떻게 알릴 것인가?

- 사용자에게 어떤 메시지를 보여줄 것인가?
- 클라이언트가 구분 가능한 에러 코드를 줄 것인가?
- 서버 로그에는 어떤 정보를 남길 것인가?
- 민감한 정보가 에러 응답에 노출되지 않는가?
- 복구 가능한 에러인가? 재시도 가능한 에러인가? 장애 알림이 필요한 에러인가?

## 7. 변경 가능성 — 요구사항이 바뀌면 어디를 고치나?

- 조건이 하나 더 추가되면 어디를 고쳐야 하는가? 그 구조가 안전한가?
- 옵션에 따라 조건문이 너무 길어지지 않는가?
- dto 변경이 엔티티 변경으로 전파되는가?
- 정책과 구현이 분리되어 있는가?
- 중복 코드가 여러 곳에 존재하는가?

## 8. 성능 — 데이터가 커져도 버티는가?

- DB 쿼리 수가 많은가? N+1 문제가 있는가?
- 인덱스를 탈 수 있는 조건인가? (RDBMS)
- 페이징은 적절한가? count 쿼리가 너무 무겁지 않은가?
- 대량 데이터 조회 시 메모리에 다 올리는가?
- 캐시가 필요한가?
- 검색 조건이 늘었을 때 쿼리가 버티는가? 배치 처리량은 충분한가?

## 9. 장애 복구 — 장애가 나면 어디까지 무너지는가?

**무너짐의 경계를 먼저 명확히 하고, 실패 대비책을 정리하라.**

- retry / timeout / circuit breaker / fallback은 있는가?
- dead letter queue가 필요한가?
- 보상 트랜잭션(compensation)이 필요한가?
- idempotency / checkpoint / 재처리 가능 구조인가?

## 10. 운영 가능성 — 배포 후 관찰·복구 가능한가?

- 로그가 충분한가? 어떤 요청에서 장애가 났는지 추적 가능한가?
- 사용자 id, requestId, traceId가 남는가?
- 배치 성공/실패 여부를 알 수 있는가? 모니터링이 있는가?
- 설정값을 코드 수정 없이 바꿀 수 있는가?
- 배포 후 롤백 가능한가? 장애 알림이 오는가?
- 데이터 보정 쿼리나 재처리 도구가 있는가?

## 11. 보안 — 악의적 요청에도 안전한가?

- 인증 토큰 관리, 비밀번호 암호화는?
- 개인정보 마스킹, 로그에 개인정보 남기지 않기
- SQL Injection / XSS / CSRF 방어, CORS 설정
- 파일 업로드 확장자·용량 제한
- 서버 간 통신 인증, 관리자 기능 접근 제한
- secret key 외부 노출 방지

## 12. API 설계 — 클라이언트가 쓰기 편한가?

- URL이 리소스 중심인가? HTTP Method가 적절한가?
- 응답 구조가 일관적인가? 에러 응답 포맷이 통일되어 있는가?
- 페이징/정렬/검색 조건이 확장 가능한가?
- 너무 많은 정보를 한 번에 주고 있지 않은가?
- 내부 엔티티 구조가 그대로 노출되지 않는가?

## 13. 테스트 가능성 — 바꿔도 안 깨진다는 자신감이 있는가?

**커버리지를 높이는 게 아니라 "바꿔도 안 깨진다는 자신감"을 얻기 위함이다.**

- 핵심 비즈니스 로직이 서비스에 분리되어 있는가?
- 외부 API·DB·파일 시스템 의존성을 분리할 수 있는가?
- 단위 테스트 가능한 구조인가? 통합 테스트가 필요한 부분은 어디인가?
- 실패 케이스 테스트가 있는가? 권한 테스트가 있는가? 동시성 테스트가 필요한가?
- (+) 이번 변경이 테스트 가능성을 **악화**시키지 않는가? (시간 의존성·난수·전역 상태·외부 API 직접 호출·DI 제거)

## 14. 도메인 규칙 — 문제를 올바르게 구조화했는가?

문제를 구조화하는 영역.

- (+) 항상 참이어야 하는 불변식을 한 문장으로 말할 수 있는가?
- (+) 상태 전이·금액 계산·정책 조건이 코드 어디에 사는가? 흩어져 있지 않은가?
- (+) 도메인 용어와 코드의 이름이 일치하는가?

## 15. 데이터 모델링 — 이 데이터의 주인은 누구인가?

- 관계가 1:1, 1:N, N:M 중 무엇인가?
- 정규화할 것인가, 반정규화할 것인가?
- 이력 관리가 필요한가? 상태값은 어떻게 관리할 것인가?
- unique 제약이 필요한가? 삭제 정책은 무엇인가?
- 조회 패턴에 맞는 인덱스가 있는가?
- 통계/검색/운영용 데이터는 분리해야 하는가?

## 16. 비용 — 이 복잡도를 감당할 가치가 있는가?

서버 · DB · 검색 엔진 · 네트워크 · 개발 · 운영 · 장애 대응 · 학습 · 변경 비용.

- (+) 같은 문제를 더 싸고 단순하게 푸는 대안은 없는가?
- (+) 이 선택이 캐시·쿼리·외부 API 호출량을 어떻게 바꾸는가?

## 17. 사용자 경험 — 사용자가 이해 가능한 결과를 받는가?

- 응답이 너무 느리면 사용자는 불안해한다.
- 에러 메시지가 애매하면 사용자는 뭘 해야 할지 모른다.
- 검색 결과가 이상하면 서비스 신뢰가 떨어진다.
- 저장 버튼을 눌렀는데 중복 생성되면 불쾌하다.
- 처리 중 상태를 알려주지 않으면 다시 누른다.
- (+) 여기서 "사용자"는 화면 사용자만이 아니다 — API client, 운영자, 에러 메시지를 읽는 개발자도 포함.

## 18. 협업 가능성 — 다른 개발자가 이어받을 수 있는가?

- 다른 사람이 읽기 쉬운가? 네이밍이 의도를 드러내는가?
- 패키지 구조가 역할별로 나뉘어 있는가?
- 주석이 필요한 곳에만 있는가? 컨벤션이 일관적인가?
- PR에서 설명 가능한 구조인가?
- 문서 없이도 흐름을 따라갈 수 있는가?

# 구현 단계별 질문 가이드

> **같은 질문이 여러 단계에 반복 등장한다 — 의도된 중복이다.** 같은 질문이라도 단계마다 답의 형태가 다르기 때문이다:
> 설계에서는 **정책 결정**("논리 삭제로 간다"), 구현에서는 **코드 위치**("그 정책이 어디에 사는가"),
> 테스트에서는 **재현**("그 정책이 깨지는 경우를 만들 수 있는가"), 운영에서는 **관찰**("깨졌을 때 보이는가").
> `[n]`은 위 18항목 번호.

## ① 요구사항 파악 — 코드 만지기 전

- 무엇을 만들어야 하는가? 누가 사용하는가? 필수 값은 무엇인가? [1]
- 항상 참이어야 하는 불변식을 한 문장으로 말할 수 있는가? [14]
- 실패의 경계는 어디인가 — 어디까지 무너져도 되는가? [1·9]
- 이 복잡도를 감당할 가치가 있는가? 더 싸고 단순한 대안은 없는가? [16]
- 사용자는 처리 중·성공·실패에 각각 무엇을 보게 되는가? [17]

## ② 데이터 모델링

- 이 데이터의 주인은 누구인가? 관계는 1:1 / 1:N / N:M? [15]
- 상태값 전이는 올바른가 — 어떤 전이가 금지되는가? [4·14]
- 삭제는 물리인가 논리인가? [4·15]
- unique 제약이 필요한가? — **동시성 방어의 첫 줄이다** [15·5]
- 조회 패턴에 맞는 인덱스가 있는가? 이력 관리가 필요한가? [15·8]

## ③ API·계약 설계

- URL이 리소스 중심인가? HTTP Method가 적절한가? [12]
- 누가 이걸 호출할 수 있는가? 소유권 검증은 어디서 하는가? [3]
- 필수 값·형식·범위 — 입력 계약이 명세에 드러나는가? [2·12]
- 에러 응답 포맷이 통일되어 있는가? 클라이언트가 구분 가능한 코드인가? [6·12]
- 내부 엔티티가 그대로 노출되지 않는가? 과다 노출은 없는가? [12]
- 페이징/정렬/검색 조건이 확장 가능한가? [12·8]

## ④ 비즈니스 로직 구현

- **백엔드가 최종 방어선이다** — 빈 값·범위·enum을 여기서도 막는가? [2]
- 권한 없는 사용자가 이 코드에 도달하면 어떻게 되는가? [3]
- 어디까지가 한 트랜잭션인가? 중간 실패 시 어디까지 롤백되는가? [4]
- 동시에 두 요청이 이 코드에 들어오면? 연타·재시도는? [5]
- 이 예외는 복구 가능한가? 사용자에게 뭐라고 알리나? 민감정보가 새지 않는가? [6]
- 정책과 구현이 분리되어 있는가? 조건 하나 추가되면 어디를 고치나? [7]
- 핵심 로직이 테스트 가능한 위치에 있는가 — 시간·전역 상태·외부 호출에 묶이지 않았나? [13]

## ⑤ 외부 연동·비동기 — DB 밖 의존·queue·배치가 있을 때

- 상대가 느리면? 죽어 있으면? 이상한 응답을 주면? [9]
- retry/timeout/fallback은 있는가? 재시도가 중복 실행을 만들지 않는가 (idempotency)? [9·5]
- 배치가 중간에 죽으면 어디서부터 다시 도는가 (checkpoint·재처리)? [9]
- 실패가 어디에 기록되는가 — DLQ·알림? [9·10]
- 호출량과 비용이 어떻게 변하는가? [16]

## ⑥ 테스트 작성

- 실패 케이스 테스트가 있는가 — 정상 경로 1개당 실패 경로 몇 개인가? [13·6]
- 권한 없는 사용자·남의 리소스 접근 테스트가 있는가? [13·3]
- 이상한 입력(빈 값·경계값·잘못된 enum) 테스트가 있는가? [13·2]
- 중복 요청·동시 요청을 재현하는 테스트가 필요한가? [13·5]
- 끝난 뒤 **데이터 상태**를 검증하는가 — 호출 성공 여부만 보고 있지 않은가? [13·4]

## ⑦ 머지 전 셀프 리뷰

- 의도 밖의 변경이 diff에 섞이지 않았는가?
- 조건이 하나 추가되면 어디를 고치나? 중복 코드를 만들지 않았나? [7]
- N+1은 없는가? 인덱스를 타는가? 데이터가 10배여도 버티는가? [8]
- 로그에 개인정보·secret이 남지 않는가? [11·10]
- 에러 메시지가 사용자에게 다음 행동을 알려주는가? [17·6]
- 네이밍이 의도를 드러내는가? 이 PR을 말로 설명할 수 있는가? [18]
- **바꿔도 안 깨진다는 자신감이 생겼는가 — 아니라면 무엇이 불안한가?** [13]

## ⑧ 배포·운영 준비
