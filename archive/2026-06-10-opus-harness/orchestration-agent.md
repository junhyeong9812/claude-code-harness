# 서브 에이전트 운용 가이드

> 모든 모드에서 서브 에이전트를 효과적으로 활용하기 위한 가이드.
> `orchestration.md`(라우터)에서 이 문서를 참조한다.

---

## 0. 이 문서의 목적

Claude Code는 하나의 세션 안에서 **서브 에이전트(자식 프로세스)**를 생성하여 복잡한 작업을 분업할 수 있다.
이 문서는 **언제, 어떤 에이전트를, 어떻게** 활용할지를 정의한다.

### 핵심 원리

```
메인 Claude (오케스트레이터)
    │
    ├── 직접 처리: 단순 작업, 직접 도구 호출이 효율적인 경우
    │
    └── 에이전트 위임: 복잡한 탐색, 독립적 병렬 작업, 깊은 분석
```

**에이전트는 도구다.** 무조건 쓰는 것도, 무조건 안 쓰는 것도 아니다. 상황에 따라 판단한다.

## 1. 사용 가능한 에이전트 유형

| 유형 | 카테고리 | 용도 | 사용 가능 도구 | 제한 도구 | 사용 시점 |
|------|---------|------|--------------|----------|----------|
| **Explore** | Claude 내부 서브 에이전트 | 코드베이스 탐색, 파일 검색, 구조 파악 | Read, Glob, Grep, Bash, WebFetch, WebSearch 등 | Agent, Edit, Write, NotebookEdit | 필요 시 선택 |
| **Plan** | Claude 내부 서브 에이전트 | 구현 계획 수립, 아키텍처 설계 | Read, Glob, Grep, Bash, WebFetch, WebSearch 등 | Agent, Edit, Write, NotebookEdit | 필요 시 선택 |
| **general-purpose** | Claude 내부 서브 에이전트 | 복잡한 멀티스텝 작업, 코드 수정 포함 | 모든 도구 | 없음 | 필요 시 선택 |
| **codex (외부 LLM)** | 외부 LLM 호출 | 모델 교차 검증 — Claude 분석에 대한 second opinion, 외부 큐레이션, plan/진단/테스트 검토 | `codex exec` Bash 호출 (stdin 프롬프트, stdout/파일 응답) | 모든 Claude 도구 — codex는 Claude 도구 없이 자체 추론만 수행 | **구현 모드 의무 단계**: B1.6 / A1.6 / C1.6 / A2 / B3·A3·C3 / B5·A5·C5. **토론·학습·설계 모드**: 답변당 1회 이상 의무. 상세는 11절 |

### 각 유형의 특성

**Explore 에이전트:**
- 빠른 코드베이스 탐색에 최적화
- 파일 패턴 검색, 키워드 검색, 구조 파악
- thoroughness 수준 지정 가능: quick / medium / very thorough
- **코드를 수정하지 못한다** (Read-only)
- 결과를 메인 Claude에게 보고한다

**Plan 에이전트:**
- 구현 전략 수립, 아키텍처 설계
- 주요 파일 식별, 트레이드오프 분석
- **코드를 수정하지 못한다** (Read-only)
- 단계별 계획을 반환한다

**general-purpose 에이전트:**
- 모든 도구를 사용할 수 있는 범용 에이전트
- 코드 수정, 파일 생성, 테스트 실행 등 가능
- 복잡한 멀티스텝 작업에 적합
- **가장 강력하지만, 가장 비용이 높다** (토큰 소모)

**codex (외부 LLM):**
- Claude 내부 서브 에이전트가 아닌 **외부 LLM 호출** — 별개 카테고리.
- 호출 도구: `codex exec` CLI (Bash 도구로 실행).
- 모델: GPT-5.5, reasoning effort `xhigh` (기본 설정 — `/home/jun/.codex/config.toml`).
- **사용 시점이 강제됨**: 위 표의 "사용 시점" 컬럼 참조. Claude 내부 서브 에이전트는 선택적이지만, codex는 의무 단계가 있다.
- 호출 표준 프롬프트 5종은 `templates/codex-prompt.md`, 보안 게이트는 `orchestration-impl.md` 5.7절, 결과 통합 규칙은 본 문서 11절.

## 2. 에이전트 사용 판단 기준

### 2.1 에이전트를 쓰지 않는 경우 (직접 처리)

| 상황 | 이유 | 대신 쓸 도구 |
|------|------|-------------|
| 특정 파일 1~3개 읽기 | 에이전트 오버헤드가 더 큼 | Read |
| 특정 클래스/함수 정의 찾기 | Glob으로 즉시 가능 | Glob |
| 특정 파일 내 키워드 검색 | Grep으로 즉시 가능 | Grep |
| 단순 질문 답변 | 에이전트 불필요 | 직접 답변 |
| 단일 파일 수정 | 에이전트 불필요 | Edit/Write |

**원칙: 3번 이하의 도구 호출로 끝나는 작업은 직접 처리한다.**

### 2.2 에이전트를 쓰는 경우

| 상황 | 추천 에이전트 | 이유 |
|------|-------------|------|
| 코드베이스 전체 구조 파악 | Explore (very thorough) | 다수 파일 탐색, 메인 컨텍스트 보호 |
| "이 함수를 호출하는 곳 전부 찾아줘" | Explore (medium) | 여러 디렉토리 탐색 필요 |
| 독립적인 두 가지 조사를 동시에 | Explore × 2 (병렬) | 병렬로 시간 절약 |
| 구현 전 아키텍처 분석 | Plan | 계획 수립에 특화 |
| 독립적인 모듈 수정 (다른 모듈과 무관) | general-purpose | 코드 수정 필요 |
| 테스트 실행 + 결과 분석 | general-purpose | 실행 + 판단 필요 |

### 2.3 판단 흐름도

```
작업이 들어왔다
    │
    ├── 도구 호출 3회 이하로 끝나나? ── YES → 직접 처리
    │
    ├── 코드를 수정해야 하나?
    │   ├── YES → general-purpose
    │   └── NO → Explore 또는 Plan
    │
    ├── 독립적인 작업이 2개 이상인가?
    │   ├── YES → 병렬 에이전트
    │   └── NO → 단일 에이전트
    │
    └── 코드베이스 탐색인가, 계획 수립인가?
        ├── 탐색 → Explore
        └── 계획 → Plan
```

## 3. 에이전트 프롬프트 작성 규칙

에이전트는 **현재 대화 컨텍스트를 공유하지 않는다.** 새 동료가 방금 들어온 것처럼 브리핑해야 한다.

### 3.1 필수 포함 사항

1. **목표**: 무엇을 달성해야 하는지
2. **배경**: 왜 이 작업이 필요한지
3. **이미 파악한 것**: 불필요한 중복 조사 방지
4. **기대 결과**: 어떤 형태로 보고받고 싶은지
5. **범위 제한**: 하지 말아야 할 것

### 3.2 좋은 프롬프트 예시

```
❌ 나쁜 예: "auth 관련 파일 찾아줘"
  → 너무 막연. 뭘 찾아야 하는지, 왜 필요한지 모름.

✅ 좋은 예:
  "이 프로젝트(/home/jun/project/myapp)에서 인증(authentication) 관련 코드를 찾아줘.
   현재 JWT 기반 인증을 사용하고 있는 것으로 보이는데,
   토큰 발급/검증/갱신이 어떤 파일에서 이루어지는지 파악해줘.
   특히 미들웨어에서 토큰을 어떻게 검증하는지가 중요해.
   파일 경로와 핵심 함수 시그니처를 정리해서 보고해줘."
```

### 3.3 결과 형태 지정

에이전트에게 **보고 형식**을 미리 지정하면 결과 활용이 쉽다:

- "200자 이내로 요약해줘" → 빠른 판단용
- "파일 경로 + 핵심 함수 목록으로 정리해줘" → 코드 탐색 결과
- "선택지 3개를 장단점과 함께 제시해줘" → 설계 판단용

## 4. 병렬 실행 규칙

### 4.1 병렬 실행이 가능한 경우

두 작업이 **완전히 독립적**일 때만 병렬 실행한다.

```
✅ 병렬 가능:
  - 에이전트 A: "frontend/ 폴더의 컴포넌트 구조 파악"
  - 에이전트 B: "backend/ 폴더의 API 엔드포인트 목록 정리"
  → 서로 다른 영역, 결과가 서로에게 영향 없음

❌ 병렬 불가:
  - 에이전트 A: "DB 스키마 분석"
  - 에이전트 B: "DB 스키마에 맞는 API 설계"
  → B는 A의 결과가 필요함. 순차 실행해야 함.
```

### 4.2 병렬 실행 제한

| 규칙 | 이유 |
|------|------|
| 같은 파일을 수정하는 에이전트를 병렬 실행하지 않는다 | 충돌 위험 |
| 결과가 서로 의존하는 에이전트를 병렬 실행하지 않는다 | 순서 보장 불가 |
| 병렬 에이전트는 최대 3개까지 | 결과 통합의 복잡성 증가 |

### 4.3 병렬 실행 방법

한 번의 응답에서 여러 Agent 도구를 동시에 호출한다:

```
메시지 하나에:
  Agent(Explore) — "frontend 구조 파악"
  Agent(Explore) — "backend 구조 파악"
  → 두 에이전트가 동시 실행
```

**순차 실행이 필요한 경우:**
첫 번째 에이전트의 결과를 받은 후, 그 결과를 반영하여 두 번째 에이전트를 실행한다.

## 5. 결과 검증

에이전트의 결과는 **검증 없이 채택하지 않는다.**

### 5.1 검증 방법

| 검증 항목 | 방법 |
|-----------|------|
| 파일 경로가 실제로 존재하는가 | Glob 또는 Read로 확인 |
| 함수/클래스가 실제로 존재하는가 | Grep으로 확인 |
| 코드 수정이 올바른가 | Read로 수정된 파일을 확인 |
| 분석 결과가 합리적인가 | 핵심 파일 1~2개를 직접 읽어서 교차 확인 |

### 5.2 검증 수준

| 상황 | 검증 수준 |
|------|----------|
| Explore 에이전트의 파일 목록 | 경량: 주요 경로 1~2개만 확인 |
| Plan 에이전트의 설계 제안 | 중간: 핵심 결정사항을 사용자에게 보고 |
| general-purpose의 코드 수정 | 필수: 수정된 모든 파일을 Read로 확인 |

### 5.3 에이전트 결과 통합

여러 에이전트의 결과를 받으면:
1. 각 결과를 개별적으로 검토한다.
2. 결과 간 모순이 있는지 확인한다.
3. 통합된 결론을 도출한다.
4. 통합 결과를 사용자에게 보고한다.

## 6. 컨텍스트 관리 전략

에이전트 사용의 핵심 이점 중 하나는 **메인 컨텍스트를 보호**하는 것이다.

### 6.1 메인 컨텍스트에 남겨야 할 것

- 사용자와의 대화 흐름
- 핵심 결정 사항
- 현재 작업 상태
- 에이전트 결과의 **요약**

### 6.2 에이전트에게 위임해야 할 것

- 대량 파일 탐색 (10개+ 파일)
- 긴 코드 분석 (수백 줄)
- 독립적인 조사/검증 작업
- 반복적인 패턴 확인

### 6.3 컨텍스트 절약 패턴

```
❌ 비효율적:
  메인 Claude가 20개 파일을 직접 Read → 컨텍스트 폭발

✅ 효율적:
  Agent(Explore)에게 "20개 파일을 분석하고 핵심 3개만 경로와 요약을 알려줘"
  → 메인 Claude는 요약만 받음 → 필요한 파일만 직접 Read
```

## 7. 모드별 에이전트 활용

### 7.1 구현 모드 (`orchestration-impl.md`)

| 파이프라인 단계 | 에이전트 활용 |
|----------------|-------------|
| **리서치** | Explore로 코드베이스 구조 파악. 독립 영역은 병렬 Explore |
| **계획** | Plan으로 구현 전략 수립 (선택적) |
| **구현** | 독립 모듈은 general-purpose로 분리 구현 가능 (같은 파일 수정 금지) |
| **테스트** | general-purpose로 테스트 실행 + 결과 분석 |
| **피드백** | Explore로 변경 파일 재확인 (선택적) |

**구현 모드 주의사항:**
- 에이전트에게 코드 수정을 위임할 때, `orchestration-impl.md`의 규칙(계획에 없는 변경 금지 등)을 프롬프트에 명시한다.
- 에이전트가 수정한 코드는 반드시 메인 Claude가 검증한다.

### 7.2 토론/학습/설계 모드 (`orchestration-discuss.md`)

| 서브 모드 | 에이전트 활용 |
|-----------|-------------|
| **토론** | 대부분 불필요. 특정 기술의 최신 정보가 필요하면 웹 검색 에이전트 |
| **학습** | 코드 예시가 필요하면 Explore로 실제 프로젝트에서 패턴 탐색 |
| **설계** | Explore로 기존 아키텍처 파악, Plan으로 설계 대안 분석 |

**토론/설계 모드 주의사항:**
- 단순 대화에는 에이전트를 쓰지 않는다.
- 에이전트는 **정보 수집**용이지, **판단/답변**용이 아니다.

## 8. 안티패턴 (하지 말아야 할 것)

### 8.1 과도한 에이전트 사용

```
❌ 파일 하나 읽으려고 에이전트 생성
❌ 단순 Grep 작업에 에이전트 사용
❌ 모든 작업마다 에이전트 생성 (습관적 위임)
```

**기준:** 직접 도구 3회 이내로 끝나면 에이전트를 쓰지 않는다.

### 8.2 검증 없는 채택

```
❌ 에이전트가 "이 파일에 있습니다"라고 했는데 확인 없이 수정 시작
❌ 에이전트의 설계 제안을 그대로 사용자에게 전달
```

**기준:** 에이전트 결과를 사용자에게 전달하기 전에 최소 1개 항목을 교차 검증한다.

### 8.3 중복 작업

```
❌ 에이전트에게 탐색을 시키면서, 메인 Claude도 같은 탐색을 수행
❌ 같은 파일을 에이전트와 메인 Claude가 동시에 읽기
```

**기준:** 에이전트에게 위임한 작업은 결과가 올 때까지 메인에서 중복 수행하지 않는다.

### 8.4 맥락 없는 위임

```
❌ "auth 관련 파일 찾아줘" (맥락 없음)
❌ "코드 리팩토링해줘" (범위/기준 없음)
```

**기준:** 3절(프롬프트 작성 규칙)의 5가지 필수 포함 사항을 지킨다.

## 9. 백그라운드 에이전트

에이전트를 백그라운드(`run_in_background: true`)로 실행할 수 있다.

### 9.1 백그라운드가 적합한 경우

- 결과가 즉시 필요하지 않은 조사 작업
- 메인 작업과 독립적인 검증/탐색
- 시간이 오래 걸리는 대규모 코드베이스 분석

### 9.2 백그라운드가 부적합한 경우

- 다음 단계가 이 결과에 의존하는 경우 → 포그라운드로 실행
- 사용자에게 즉시 보고해야 하는 경우 → 포그라운드로 실행

### 9.3 백그라운드 에이전트 관리

- 백그라운드 에이전트가 완료되면 자동 알림을 받는다.
- 알림을 받기 전까지 **폴링하거나 sleep하지 않는다.**
- 결과를 받으면 검증 후 메인 작업에 통합한다.

## 10. 워크트리 에이전트

`isolation: "worktree"`로 에이전트를 실행하면 **격리된 git 작업 공간**에서 작업한다.

### 10.1 워크트리가 적합한 경우

- 실험적 코드 변경을 시도해보고 싶을 때
- 메인 브랜치의 코드를 건드리지 않고 대안을 테스트할 때
- 위험한 리팩토링을 안전하게 시도할 때

### 10.2 워크트리 사용 규칙

- 변경이 없으면 자동 정리된다.
- 변경이 있으면 워크트리 경로와 브랜치가 반환된다.
- 워크트리의 변경을 메인에 반영할지는 **사용자가 결정**한다.

## 11. 외부 LLM (codex) 호출 가이드

Claude Code의 내부 서브 에이전트(Explore/Plan/general-purpose)는 같은 Claude 모델의 자식 호출이라 다수결 편향을 공유한다. codex(GPT-5.5)는 **다른 학습 분포·다른 RLHF·다른 아키텍처**를 가진 외부 LLM이라 사각지대가 일부 다르다. 이를 활용해 분석·계획·검증 단계의 신호를 다중화한다.

### 11.1 호출 도구와 옵션

```
cat /tmp/codex-input.md | codex exec --skip-git-repo-check -s read-only --ephemeral -o /tmp/codex-output.md -
```

- `--skip-git-repo-check`: git repo 외 디렉토리에서도 실행.
- `-s read-only`: codex가 파일 시스템 쓰기 불가 — Claude 작업 공간 보호.
- `--ephemeral`: 세션 파일 디스크 보존 안 함 — 단발 호출에 적합.
- `-o /tmp/codex-output.md`: 마지막 메시지를 파일로 저장 — 응답 캡처.
- 마지막 `-`: stdin으로 프롬프트 수신 — 긴 프롬프트 전달.
- 응답 시간: 30~120초 (xhigh reasoning effort 영향).
- Bash 호출 시 `timeout` 600000ms(10분) 권장, 가능하면 `run_in_background: true`로 백그라운드 실행 후 다른 작업 병행.

### 11.2 의무 호출 단계 (구현 모드)

`orchestration-impl.md` 4.A/4.B/4.C 파이프라인 참조:

| 단계 | codex 프롬프트 (`templates/codex-prompt.md`) | 목적 |
|------|-------------------------------------------|------|
| X.5 외부 큐레이션 | 1. 외부 큐레이션 프롬프트 | 비주류·최신·반대 관점 자료 발굴 |
| X.6 모델 교차 검증 (리서치) | 2. 모델 교차 분석 프롬프트 | **선택지 보강·체크리스트 추출** — 대안 접근·선택지·점검항목 발굴(검증 관문 아님, B2 방향성 입력). 재정의 `docs/14` §6 |

### 11.3 의무 호출 (토론·학습·설계 모드)

`orchestration-discuss.md` 3.7 참조: **답변당 1회 이상** codex 교차 검증. 답변 작성 직전에 잠정 답변 + 컨텍스트를 codex에 전달, 받은 의견을 사용자에게 교차 보고.

### 11.4 호출 실패 정책

- 비제로 종료 코드 / 응답 파일 비어있음 / 타임아웃 → **자동 스킵**, 작업 중단 없음.
- 실패 사유와 시각을 다음 위치에 기록:
  - checklist.md "단계별 codex 호출 기록" 표
  - research.md "3.2 호출 실패 시 사유" 또는 plan.md "7.4 호출 실패 시 사유"
  - learned.md "11.4 호출 실패 / 스킵 기록"
- 사용자가 명시적으로 재시도를 요청하면 호출 ID 순번을 증가시켜 다시 호출.

### 11.5 보안 게이트 (필수)

프롬프트 전송 직전에 패턴 스캔 — `orchestration-impl.md` 5.7절 + `templates/codex-prompt.md` 0.2절 (동일 패턴 표 동기화). 매칭 0건일 때만 자동 통과.

### 11.6 결과 통합 절차

1. 응답 파일 존재·비어있지 않음·종료 코드 0 확인.
2. 응답이 예상 형식(예: "## 지적 N:" 패턴)을 따르는지 검증.
3. research.md / plan.md 해당 절에 항목별 채택/기각/사용자 확인 결정과 함께 정리.
4. checklist.md 호출 기록 표를 호출 ID + 입력 해시(sha256 앞 12자) + 응답 요약으로 갱신.
5. 작업 종료 시 learned.md "11. 모델 교차 검증 기록"에 누적.

### 11.7 채택 / 기각 판단 기준

- **채택**: codex 지적이 명백한 누락/오류를 짚고, 반영 비용이 작거나 가치가 큰 경우.
- **기각**: codex가 자기 cwd/컨텍스트 오인으로 잘못 지적하거나, 사용자 의사·기존 결정과 충돌하는 경우. **기각 사유는 반드시 기록.**
- **사용자 재확인**: 사용자 의사·정책 결정이 필요한 경우 → AskUserQuestion 도구로 옵션 제시.

### 11.8 입력 크기 / 중복 방지

- 호출 1회 입력 상한 약 30,000 토큰. 큰 파일은 핵심 발췌·diff·관련 절만 추출해 전달.
- 입력 해시(sha256 앞 12자)가 직전 호출과 동일하면 캐시 응답 재사용 — 새 호출 안 함.
- 작업 재개 시 checklist 표를 보고 "호출 여부 = ✅" 행은 건너뛴다.

### 11.9 codex는 Claude 도구가 아니다 — 결정 책임은 Claude가 진다

codex 응답은 **참고용 second opinion**이지 자동 채택 대상이 아니다. 검증·기각·통합 결정은 Claude가 사용자와 함께 내린다. codex가 잘못 지적하는 경우(자기 cwd 오인 등)도 있으므로 무비판 채택 금지.

## 12. 페르소나 캐스팅 디렉터 + 멀티워커 절단선

> 코드리뷰 가이드레일의 "역할 분리"를 구현 파이프라인 전체로 확장한 운용 규칙. 설계 근거: 대상 작업의 `docs/08-멀티워커-오케스트레이션-설계안.md`(또는 claude_study `docs/`). 메인 워커는 단순 실행자가 아니라 **캐스팅 디렉터**다.

### 12.1 소유권 절단선 (누가 무엇을 소유하나) — D1

> 사용자 합의·전체 판단이 필요한 산출물은 **메인**이 소유한다. 독립성이 품질을 직접 올리는 검토·테스트·검증은 **별도 워커**로 분리한다.

| 단계 | 소유 | 비고 |
|------|------|------|
| research 판단 | 메인 | 무거운 탐색만 Explore 위임. 독립 신호=codex(impl B1.6) |
| plan.md | 메인(author) + 선택적 워커(drafter) | plan은 사용자와 합의하는 계약. 독립성은 codex(impl B3) 제공 |
| context/checklist | 워커 초안 가능 | plan에서 파생되는 기계적 산출물 |
| 구현 | 워커(독립 모듈) 또는 메인 | §7.1·§4.2 규칙 |
| 테스트 설계 | 별도 워커 | impl diff 미열람(impl 6.7) |
| 리뷰 | 별도 워커 | 구현자와 분리, spec compliance(impl 5.9) |
| 검증 | 별도 워커(리포트) | 최종 판정=메인 |
| learned.md | 메인 | 전체 해석·조직 기억. 변경파일 재읽기(impl 7.3) |

**plan/learned가 메인인 이유**: 격리 워커가 가질 수 없는 "전체 컨텍스트 + 사용자 대화 스레드"를 요구한다. plan은 "완전 금지"가 아니라 **author=메인 / drafter=선택적 워커**.

### 12.2 페르소나 캐스팅 — D4

메인이 리서치로부터 **이 작업에 맞는 최소 페르소나 캐스팅**을 도출 → 방향성 게이트(impl B2/A2/C2)에서 codex가 "빠진/과한 페르소나" 점검 → 입력 스코프 부여해 작업 지시 → **최종 판정은 메인**.

페르소나는 두 형태: **역할형**(spec준수 리뷰어 / 동시성·경쟁조건 헌터 / 무음실패 헌터 등 — 코드리뷰 차원 에이전트의 일반화)과 **named-expert 렌즈형**(12.3).

**규율 5종**:
1. **페르소나는 이름이 아니라 계약.** 각 페르소나 = `볼 것 / 안 볼 것 / 산출물 형식` 3종 계약. 템플릿: `templates/persona-contract.md`. (예: 테스트설계자 = "impl diff 안 봄 / plan·spec만 / 출력=테스트 케이스 목록")
2. **캐스팅은 게이트 대상.** 메인이 위험을 못 보면 페르소나도 못 뽑는다(단일 실패점) → 방향성 게이트에서 codex가 누락/과잉 점검. **새 codex 호출 아님 — B1.6/B2에 "제안 캐스팅" 항목으로 접어넣기.**
3. **최소 캐스팅.** 고정 로스터 금지 — 변경에서 도출.
4. **권위 착시 방어.** 라벨(역할명·인물명)로 약한 지적이 과대평가되지 않게 — 신뢰도 채점(impl 5.9)·증거수준은 라벨과 무관 적용.
5. **최종 판정 ≠ 투표 집계.** 메인은 종합자이지 집계자가 아니다 — 근거 품질로 재평가.

### 12.3 named-expert 렌즈 (유명 저자 기반 페르소나) — ★ 흉내 금지, 원칙 적용 ★

> 핵심 규칙: **named-expert persona는 실존 인물의 흉내가 아니라, 그 인물의 공개 저작에서 검증 가능한 원칙·휴리스틱을 적용하는 리뷰 렌즈다.** 출력은 "누가 말했는가"가 아니라 **"어떤 원칙이 어떤 증거로 적용되는가"** 중심으로 작성한다.

**왜 효과가 있나**: LLM 학습 데이터가 유명 저자의 저작·용어망에 크게 기반 → 이름은 모델 안에서 특정 문헌군을 더 선명히 활성화한다(generic role보다 구체적 체크 유도). 단 이득은 이름 자체가 아니라 **이름에 연결된 명시적 체크리스트**에서 나온다. 이름만 던지면 연극이 된다.

**규칙**:
- 이름은 **내부 렌즈 선택·출처 있는 원칙 식별에만** 사용. 인용·의견 귀속·권위 기반 결론 금지("Kent Beck would say" 금지).
- 발견은 코드 증거·재현 가능성·영향도·확신도로 평가(유명세 무관 — 12.2-4 강화).
- 실명 인용은 **출처가 있을 때만**. 가능하면 외부 큐레이션(impl B1.5 WebSearch)으로 실제 원칙을 ground.
- 최종 판단자는 named-expert가 아니라 **evidence-based reviewer(메인)**.
- 산출물은 "Kent Beck 리뷰"가 아니라 "TDD/classic xUnit 원칙 기반 테스트성 리뷰"처럼 **원칙명으로** 보여야 한다.

**분야별 3명 선정 기준** (유명함보다):
- 원전성(개념 창시/고전 기준) · 상보성(이론가+실무자+비판자 등 렌즈가 갈리게) · 현대성(고전 1 + 실무 확장 1 + 현대 비판/운영 1) · 검증 가능성(공개 저작) · 도메인 적합성(코드 체크로 변환 가능).
- **3명 기본**: 1명=권위 편향, 2명=대립 과열, 4명+=신호 흐려짐.
- 예(DDD): Evans(고전) + Vernon(실무) + Fowler(비판/정리) — 같은 학파 반복 금지.

### 12.4 페르소나 라이브러리 (미리 만들고 꾸준히 성장)

도메인별 named-expert 렌즈를 **미리 정의해 두고 캐스팅 시 참조**하는 라이브러리. 위치: `templates/persona-library.md`. 도메인: 인프라/SRE · 백엔드·설계 · 데이터·분산 · 프론트엔드 · 디자인/UX · 언어별 등.

**운영 규칙**:
- **라이브러리는 참조이지 캐스팅이 아니다.** 큰 라이브러리가 있어도 캐스팅은 여전히 **최소·변경 도출**(고정 로스터화 방어 — 12.7).
- **성장은 실제 작업에서.** 새 도메인/작업을 만나면 그때 외부 큐레이션으로 원칙을 ground해 항목 추가. **한 번에 거대 추측 목록을 만들지 않는다.**
- **선정 편향 경계.** 특정 문화권·시대·언어 쏠림을 의식적으로 분산.
- 각 항목 형식: `렌즈명(인물) / 적용 원칙 / 체크리스트 / 적합 문제 유형 / 금지된 주장 / 출처·최종검토일`. (persona-contract 형식)
- 출처 링크·최종 검토일을 남겨 **구식 견해를 관리**(전문가도 견해가 바뀐다).

### 12.5 페르소나 ≠ codex (혼동 금지) — D5

| | 페르소나 | codex |
|---|---|---|
| 제공 | 관점 분산·전문 체크리스트·탐색 범위 확장 | 모델 다양성·합의 편향 견제 |
| 독립성 | **약한(절차적)** — 같은 모델, 다른 입력/체크리스트/목표함수 | **강한** — 다른 모델·추론 습관 |

**커버리지=페르소나, 독립성=codex. 페르소나 다수결은 codex 검증을 대체하지 못한다.** 같은 Claude 다수 페르소나(named-expert 포함)는 같은 모델 사각지대를 공유한다(다수결 동조화).

### 12.6 opt-in 3단계 (규모가 캐스팅 깊이를 결정) — D7

규모(impl 1.2)가 캐스팅 깊이를 정한다.

```
소규모   : 페르소나 캐스팅 없음. 메인 + 셀프체크 + (필요시) codex 1회
중규모   : 1~2개 페르소나 (테스트설계자 OR spec준수리뷰어) + codex 검증
대/고위험: 풀 캐스팅 (구현/테스트설계/리뷰/검증 + 도메인 named-expert 렌즈)
          + 캐스팅을 게이트에서 codex 검증 + 메인 최종 판정 + learned.md
```

대규모 풀 캐스팅 실행체는 `Workflow` 도구(dimensions→find→verify→synthesize)를 쓸 수 있다(opt-in).

**캐스팅 깊이는 작업 단위로 고정 — 페이즈로 낮추지 않는다 (★ 2026-06-09 ★).** 규모(1.2)는 작업 전체로 판단한다. 작업을 페이즈로 쪼개도(impl 5.8) 개별 페이즈가 1~2파일로 작아 보인다는 이유로 깊이를 소규모로 낮추지 않는다. 대/고위험 작업의 **모든 페이즈**가 고정 로스터를 적용해 test-design 분리·review 게이트를 거친다(위험 하한). 페이즈마다 다시 캐스팅을 판단하는 게 아니라, 한 번 고정한 로스터를 매 페이즈에 돌린다. 페이즈 루프 안에서의 캐스팅 배선은 `orchestration-impl.md` 5.8 "페이즈 루프와 캐스팅 배선".
