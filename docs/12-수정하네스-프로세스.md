# 수정 하네스 프로세스 (Process Tasks)

> 작성일: 2026-06-09
> 기반: `11-하네스-재설계-제안.md`(8축). 본 문서는 그 재설계를 **프로세스 태스크 흐름**으로 표현한다.
> 핵심 재정의(사용자): **외부 큐레이션·codex = "검증 도장"이 아니라 "체크리스트 추출기"** → 추출된 체크리스트로 **토론 → 방향성 결정 → plan**.

---

## 모드 지형 — 이 프로세스의 위치 (라우터: T0보다 위)

> ★ 모드 판단은 T0~T9보다 **한 층 위**다. T0~T9 전체는 **[B] 구현 모드 안의 일**이고,
> 토론/학습/설계는 그 옆의 **별도 가지**로 T0~T9를 거치지 않는다.

```
[요구사항]
   │
   ▼
╔══════════════════════════════════════════════╗
║ ROUTER (orchestration.md) — 모드 판단          ║   ← 최상위. T0보다 위.
╚══════════════════════════════════════════════╝
   │
   ├─[A] 토론 / 학습 / 설계 모드   (코드 없음 · 자유 흐름)
   │       목적: 지식 · 판단 · 설계
   │       loop: 질문 → (리서치) → [stakes 시] 체크리스트 추출(codex/큐레이션) → 토론 → 결론
   │       codex: 고위험 결정 · 장기 설계안만 (매 답변 아님)
   │       산출물: 대화 / 정리문서 / 설계문서 / definition.md
   │            │
   │            └─(사용자: "이제 만들어줘") ── 브리지 ──┐
   │                                                     │
   └─[B] 구현 모드 ────────────────────────────────────→ T0 → T1 → … → T9
                   ↑ 설계/토론 산출물을 T2~T5 입력으로 ──┘
```

**"토론"이 두 곳에 나온다 — 혼동 금지:**

| | 토론 **모드** [A] | T4 토론 **단계** (구현 모드 안) |
|---|---|---|
| 성격 | 전략적 · 독립적 | 전술적 · 종속적 |
| 목적지 | 지식/판단/설계 (코드 아님) | *이 구현*의 방향 결정 |
| 범위 | 세션 전체 | T3 체크리스트 → T5 plan 사이 |
| 끝나면 | 대화/문서 (or 브리지로 구현 전환) | 곧장 T5 plan |

**브리지 — 모드 A가 모드 B를 먹인다:**

```
설계 모드: "인증 구조 설계하자" → 설계문서 + definition.md (경계·불변식·실패의미론)
                                         │
사용자: "이제 구현해" ──────────────────┘
                                         ▼
구현 T2(리서치)·T3(체크리스트)·T4(방향)·T5(plan)이 그 산출물을 입력으로 재사용
   → 설계를 다시 안 함 (브리지 핵심)
```

> 모드 [A]의 stakes 트리거: 토론/학습은 대부분 codex 불필요. **고위험 결정·장기 설계안**일 때만 codex 1회(구 "답변당 1회 의무"를 대체). 본 세션 자체가 모드 [A](하네스 설계)다.

## 0. 한눈 — 무엇이 바뀌나

```
[기존]  리서치 → 큐레이션(의무) → codex 교차검증(의무) → 방향성 게이트 → plan
         └ 큐레이션·codex가 "단계마다 통과시켜야 할 관문"

[수정]  리서치 → [stakes] → 체크리스트 추출(큐레이션·codex는 여기서만, stakes 비례)
                              → 토론 → 방향성 → plan
         └ 큐레이션·codex는 "체크리스트를 만들어내는 입력". 관문이 아니라 재료.
         └ 졸업 루프: 한 번 추출한 체크리스트는 자산이 되어 다음엔 도구 없이 재사용.
```

```
   │
   ▼
```

## 2. T1 — stakes 분류 태스크

```
INPUT : 요구사항 + T0 기준
OUTPUT: stakes ∈ {낮음, 중간, 높음}

task classify_stakes:
    high_if  any:
        - 불가역 (데이터 변경/삭제 · 마이그레이션)
        - 보안 · 권한 · 결제 · tenant 경계
        - public API / 계약 변경
        - 낯섦 (처음 쓰는 lib·패턴·배포방식)
        - 모호성 큰 요구사항
    mid_if   any:
        - 데이터 의미 변경 읽기 (집계·정렬·dedup·timezone·pagination)
        - 동시성 · 재시도 · 중복실행 · partial failure
        - 외부 API·webhook·queue·async·scheduler 연결
        - 최근 반복오류 영역
        - 테스트가 happy-path 1개뿐 / characterization 없음
    low_if   all:
        - blast radius 작음
        - invariant 명확
        - 실패해도 복구 쉬움
        - 기존 테스트가 의미있게 막아줌
    # ★ "작다"는 low의 근거가 아니다. config·auth·query·retry는 작아도 mid↑
```

## 3. T3 — 체크리스트 추출 태스크 ★재정의 핵심★

```
INPUT : stakes + 리서치 결과
OUTPUT: checklist[]  (이 작업에서 점검·결정해야 할 항목들)

task extract_checklist(stakes):

    base = self_checklist()                    # 항상
    base += falsification_questions()          # 항상 (자기검증 맹점 차단)
        # - 의도와 다르게 적용될 다른 호출 경로?
        # - 데이터가 비어/중복/오래된 경우?
        # - 권한 없는 사용자가 같은 경로?
        # - 테스트가 실패모드 재현하나, happy-path 따라갔나?

    if stakes >= 중간:
        codex_out = codex_targeted_review(분석요약)   # 검증 아님 → "내가 놓친 항목 뽑아줘"
        base += extract_missed_items(codex_out)

    if stakes == 높음:
        web = web_search(키워드, 최신1년)            # 비주류·최신·반대관점
        codex_cur = codex_curation(키워드)
        base += merge(web, codex_cur)               # 체크리스트 + 반대관점

    return dedup(base)

    # ★ codex/큐레이션 산출물은 "통과/실패"가 아니라 "checklist 항목"으로 변환된다.
    # ★ 졸업(F): 여기서 새로 안 항목은 T9에서 영구 체크리스트/domain-contracts로 승격.
```

## 4. T4 — 토론 → 방향성 결정 태스크

```
INPUT : checklist[] + 리서치
OUTPUT: 방향성(접근) + 결정된 정의

task decide_direction(checklist):

    report_to_user(checklist + 요구사항요약 + 기존코드현황)

    # 정의 3문항 (구 B2.5 — 독립게이트 아니라 여기 흡수)
    assert no_ambiguous_terms()                 # 모호 용어/완료조건 없나
    assert defined(불변식, 실패시_동작)            # 경계별 정의됐나
    assert defined(비대상_범위)                   # 범위 밖 명확한가

    for q in open_questions:
        if q.ambiguous:
            decision = AskUserQuestion(q.options)   # 모호 → 진행 아니라 결정화
        if still_ambiguous:
            escalate(stakes += 1)                   # (G) 모호 = 승격 사유

    return direction, definitions
```

## 5. T7~T8 — 리뷰 + 최소 안전선 태스크

```
task review(stakes, diff):
    # 프로덕션 리뷰 렌즈 5개 (named-expert 캐스팅 아님 — 체크리스트)
    for lens in [데이터무결성, 장애·운영, 보안, API계약, 테스트가능성]:
        findings += apply(lens.checklist, diff)
    if stakes >= 중간:
        findings += codex_independent_verify(diff, 변경파일범위)   # 다른 모델 독립성
    return high_confidence(findings)              # ≥80만, 오탐 억제

task merge_floor(diff):       # ★ universal floor — 낮음도 무조건 통과 (H) ★
    require run_related_tests() or log_reason()
    require diff_self_review()                     # 의도 외 변경 없나
    require rollback_or_forwardfix_plan()
    require check_public_contract_impact()         # API·DB·이벤트 경계
    # 하나라도 실패 → 머지 금지
```

## 6. T9 — 측정 + 졸업 태스크 (E + F)

```
task measure(task_meta):                          # 작업당 <1분
    log {
        유형, 규모, stakes,
        총_소요, 하네스_오버헤드,
        재작업_횟수, 테스트실패후_수정,
        검증서_잡은_실제결함, 오탐_수,
        머지후_결함,
        생략한_게이트 + 그_결과            # ← 어떤 규칙이 실제 필요한지의 증거
    }

task graduate(checklist, codex_catches):          # F — 비계 줄이기
    for item in newly_learned(checklist + codex_catches):
        if reusable or 깨지면_장애 or 테스트기준:
            promote_to(domain-contracts.md or 영구_체크리스트)
    # → 다음 작업엔 같은 패턴을 codex 없이 본인이 잡음 = 비싼 도구 점점 덜 필요

# 주기 점검(orchestration §6): 측정 로그 분석
#   유지  = 결함/재작업 줄인 증거 + 저비용
#   삭제  = 설명만 그럴듯 + 측정효과 없음
```

## 7. 페르소나 — 두 집 (D축)

```
[프로덕션 파이프라인]   T7 review에서만
    리뷰 렌즈 5개 = 고정 체크리스트 (데이터무결성/장애·운영/보안/API계약/테스트가능성)
    named-expert 캐스팅 ✗

[학습 레퍼런스]        파이프라인 밖, 낯선 도메인 만날 때
    named-expert 라이브러리 = "무엇을 점검할지 발견하는 인덱스"
    flow:  낯선 도메인 → 라이브러리 읽기 → 체크리스트 추출 → (그 체크리스트를) 사용
    산출물: 이름 ✗  →  체크리스트 ✓
    예: "DDD 관점" ✗ → "aggregate경계·invariant위치·tx경계·repository책임" ✓
```

## 9. 한 줄
