## 1. 목표

Claude Code 인사이트(160세션, 4152메시지 분석)에서 도출된 6개 구조적 갭을 해소하고, 작업 유형별 서브 파이프라인(버그 수정 / 기능 구현 / 리팩토링)을 도입하여 마찰을 줄인다.

### 해결할 문제 (인사이트 기반)
| # | 문제 | 빈도 | 근본 원인 |
|---|------|------|----------|
| 1 | 이해 전 행동 | 38건 잘못된 접근 | 리서치→계획 사이 확인 게이트 없음 |
| 2 | 범위 확장/무단 변경 | 7건 과도한 변경 + 다수 | 범위 통제가 선언적이고 구조적이지 않음 |
| 3 | 버그 오진 | 32건 오해 중 다수 | 버그/기능/리팩토링 구분 없는 단일 파이프라인 |

| 5 | 멈추지 않음 | 반복적 | 사용자 부정 시그널 대응 규칙 없음 |
| 6 | 문서 덮어쓰기 | 다수 | 기존 파일 보호 규칙 없음 |

## 2. 접근 방식

### 2.1 서브 파이프라인 도입

현재 단일 파이프라인을 **작업 유형 판단 → 유형별 서브 파이프라인 분기**로 변경한다.

```
요구사항 수신
    │
    ├── 유형 판단 (새로운 1.0 단계)
    │
    ├── [버그 수정] 조사 → 진단 보고 → 승인 → 수정 → 테스트 → 피드백
    ├── [기능 구현] 리서치 → 계획 → 승인 → 구현 → 테스트 → 피드백 (현행 유지 + 강화)
    └── [리팩토링] 현상 분석 → 목표 정의 → 승인 → 단계적 변환 → 회귀 테스트 → 피드백
```

### 2.2 각 서브 파이프라인의 핵심 차이

| | 버그 수정 | 기능 구현 | 리팩토링 |
|---|---|---|---|
| **핵심 위험** | 오진 | 설계 오류 | 기존 기능 파괴 |
| **필수 게이트** | 진단 보고 후 승인 | 계획 승인 | 목표/범위 승인 |
| **범위 특성** | 좁고 명확 | 명시적 | 넓지만 동작 불변 |
| **테스트 중점** | 재현→수정 확인 | 새 기능 + 회귀 | 회귀 100% |

### 2.3 구조적 갭 해소 방법

| 갭 | 해소 방법 | 반영 위치 |
|---|---|---|
| 이해 확인 게이트 | 모든 서브 파이프라인에 "보고 → 승인" 필수 게이트 | 각 서브 파이프라인 |
| 범위 통제 | plan.md에 "변경 파일"+"금지 파일" 필수. 구현 시 매 Edit 전 계획 대조 | 4.2절 + 4.4절 강화 |
| git 안전 | 새 9절 "Git 작업 규칙" 추가 | orchestration-impl.md 9절 |
| 부정 시그널 대응 | 새 10절 "긴급 정지 프로토콜" 추가 | orchestration-impl.md 10절 |
| 파일 보호 | 기존 파일 Write 전 Read + 확인 규칙 | 4.4절 구현 규칙 내 |

## 4. 참고 코드 스니펫

### 현재 orchestration-impl.md의 파이프라인 구조 (1절)
```markdown
### 파이프라인 (모든 규모 공통)

[1. 리서치] → [2. 계획] → [3. 구현] → [4. 테스트] → [5. 피드백]
                                ↑            |
                                └── 실패 시 ──┘

**모든 단계는 규모에 관계없이 생략하지 않는다.** 규모에 따라 달라지는 것은 각 단계의 **깊이**다.
```
- 출처: `orchestration-impl.md:53~61`

**코드 분석:**
- 현재는 규모(소/중/대)로만 분기하고, 작업 유형(버그/기능/리팩토링)으로는 분기하지 않음
- "모든 단계는 생략하지 않는다"는 원칙은 유지하되, 유형별로 단계의 **내용**이 달라져야 함

### 현재 리서치 단계의 "멈추는 시점" (4.1절)
```markdown
**멈추는 시점**:
- 요구사항이 모호하거나 충돌이 있을 때 → 사용자에게 질문한다.
- 기존 코드의 의도가 불분명할 때 → 사용자에게 확인한다.
```
- 출처: `orchestration-impl.md:233~235`

**코드 분석:**
- 문제: "모호하거나 충돌이 있을 때"만 멈춤 → 모호하지 않다고 **착각**하면 그냥 진행
- 개선: 모든 경우에 리서치 결과를 **보고**하고 확인받는 필수 게이트 필요

### 현재 구현 단계의 범위 통제 (4.4절)
```markdown
- 승인된 계획의 구현 순서에 따라 코드를 작성한다.
- 사용자가 주석으로 지시한 방향을 따른다.
- 계획에 없는 "개선"을 임의로 추가하지 않는다.
- 구현 중 계획과 다른 상황이 발생하면 멈추고 사용자에게 보고한다.
```
- 출처: `orchestration-impl.md:317~320`

**코드 분석:**
- "계획에 없는 개선을 추가하지 않는다" — 선언만 있고 **체크 메커니즘**이 없음
- 실제로는 파일을 수정할 때 "이 파일이 plan.md의 변경 대상 목록에 있는가?"를 확인하는 절차 필요
