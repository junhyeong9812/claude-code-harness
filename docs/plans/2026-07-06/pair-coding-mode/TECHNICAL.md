# TECHNICAL: 페어코딩(pair-coding) 모드 신설

> diff 비종속 동작 모델 — 다이어그램은 OVERVIEW 소유, 여기는 왜 그렇게 동작하는가만.

## 알아야 하는 개념 (구현 전제 지식)

### 개념 1: 훅 기반 게이팅 (hook-as-policy-enforcement)

① Claude Code는 도구 호출 전후(PreToolUse/PostToolUse)에 외부 스크립트(훅)를 실행하고, 그 종료 코드(0=통과, 2=차단)로 도구 실행 자체를 막을 수 있다. ② 이 저장소는 "무엇을 해도 되는가"라는 정책을 모델 프롬프트(설명·부탁)가 아니라 **결정론적 셸 스크립트**로 강제한다 — 이번 작업이 정확히 이 계층에 새 규칙(`pair` 모드)을 추가하는 것이다. ③ 모르면: 훅이 아니라 프롬프트만으로 "로직 파일은 건드리지 마라"고 지시했을 경우, 모델이 실수·컨텍스트 압축·지시 망각으로 위반해도 아무것도 막지 못한다.

### 개념 2: 파일 경로 패턴 매칭 vs 의미론적 판단

① "테스트 코드인가 로직 코드인가"는 원래 의미(그 코드가 무엇을 검증/구현하는가)로 판단해야 정확하다. ② 하지만 셸 스크립트는 파일 내용을 이해할 능력이 없으므로, `is_test_file()`은 **파일명·경로 컨벤션**(예: `FooTest.java`, `tests/**`)으로 근사한다 — 관례를 따르는 코드베이스에서는 대체로 맞고, 관례를 벗어나면 오탐한다. ③ 모르면: 어떤 파일이 왜 허용/차단됐는지 "합리적인데 이해가 안 되는" 상황에서 원인을 못 찾는다(정답은 "그 파일명이 컨벤션에 안 맞아서"인 경우가 많다).

## 동작 방식

`gate-guard.sh`는 모든 Edit/Write/MultiEdit(및 PreToolUse:Bash) 호출마다 실행되는 **stateless 스크립트**다 — 상태는 자기 프로세스가 아니라 `.claude/lazymode/<session_id>` 파일에 산다. 매 호출마다: ① stdin JSON에서 `tool_name`·`file_path`·`session_id`를 읽고, ② 파일 경로를 canonical(realpath, symlink 전부 해소)로 정규화하고, ③ 그 경로가 리포 안인지·면제 대상(`docs/plans/**`·상태파일)인지 먼저 판정한 뒤, ④ 세션 상태파일의 `MODE` 값에 따라 분기한다.

`MODE=pair`는 이 ④ 단계에 끼워 넣은 **독립 분기**다(`hooks/gate-guard.sh:181-194`). 기존 4종처럼 `PENDING_GATE`나 `WRITE_PHASE` 같은 상태 전이를 쓰지 않는다 — pair는 **매 호출이 파일 경로만으로 즉시 판정**되는 무상태(stateless) 규칙이라 상태 필드가 필요 없다. `is_test_file()`이 참이면 그냥 통과(exit 0), 거짓이면 PreToolUse에서 무조건 차단(exit 2)한다.

`is_test_file()` 자체는 두 종류의 매칭을 한다 — ① 경로 세그먼트 매칭(`*/tests/*` 등, 디렉토리 전체를 신뢰), ② basename 매칭(`?*Test.java` 등, 개별 파일명 규칙). ①이 걸리면 그 디렉토리 안의 어떤 파일이든(확장자 무관) 허용된다 — 디렉토리 이름 자체가 "여긴 테스트 영역"이라는 강한 신호라고 보는 설계다. ②는 `?*` (bash 확장 글롭에서 "1글자 이상")을 접두어로 요구하는데, 이는 리뷰에서 발견된 버그의 수정 결과다 — `*Test.java`(글롭 `*` = 0글자 이상)는 접두어 없는 `Test.java` 자체도 매칭해버렸다.

`is_test_file()`이 검사하는 경로(`CFILE`)는 **이미 이전 단계(`canon_file()`)에서 실존 심링크를 전부 해소한 뒤**의 경로다 — 그래서 `tests/foo -> ../src/Foo.java` 같은 심링크가 있어도, 검사 대상은 심링크 이름이 아니라 실제 타겟(`src/Foo.java`)이 되어 올바르게 "로직 파일"로 분류된다. 이건 pair 모드가 새로 만든 방어가 아니라 **기존 canon_file() 파이프라인을 그대로 물려받은 것**이다(기존 `gt_13`/`gt_14` 테스트가 이미 이 성질을 검증하고 있었다).

## 불변조건 / 계약

- **pair 모드에서 Edit/Write/MultiEdit로 로직 파일(is_test_file()=false)을 성공시킬 수 없다** — PreToolUse가 항상 exit 2를 반환한다. 깨지면: `is_test_file()` 판정 자체가 로직 파일을 test-file로 오분류했거나(과거 F2), canon_file() 정규화가 실패했을 때뿐이다(그 경우도 정규화 실패는 별도로 fail-closed).
- **pair 모드에서 Bash를 통한 로직 파일 수정은 차단되지 않는다(경고만)** — 이건 불변식이 아니라 **의도된 잔여 리스크**다(§0.6: 하드 차단은 결정론적으로 판정 가능한 것에만 적용하고, 임의 Bash 명령의 "이게 파일쓰기인가"는 오탐이 크다). 이 경계를 불변식으로 착각하면 안 된다.
- **테스트 파일 컨벤션에 맞는 파일 + docs/plans/상태파일은 pair에서도 항상 쓰기 가능** — task.md의 6칸 라이브 append(playbook §1)가 이 위에서 동작하므로, 이 예외가 없으면 정의 게이트 자체가 불가능해진다.

## 상태와 소유권

- `MODE` 값의 source of truth는 `.claude/lazymode/<session_id>` 파일 한 줄(`MODE=pair`)이다. 이 세션(대화) 안에서는 이 값을 사용자 답변을 받아 Claude가 직접 `Edit` 도구로 갱신했다(상태파일은 게이트 면제 경로라 가능 — `gate-guard.sh:117-120`의 `.claude/lazymode/*` 면제).
- `is_test_file()`의 패턴 목록은 `hooks/gate-guard.sh` 함수 정의가 유일한 source다 — `playbooks/pair-coding.md`는 설명·확장 가이드일 뿐 목록을 복제하지 않는다(복제하면 두 파일이 어긋날 위험, §0.1 단일 출처).

## 외부 경계와 의존성

- 이 훅은 `jq`(JSON 파싱)·`realpath`/`python3`(경로 정규화)·`flock`(상태파일 원자 갱신)에 의존한다 — 전부 훅 실행 환경(로컬 셸)에 이미 있다고 가정하며, 없으면 `canon_file()`이 fail-closed로 차단한다(`gate-guard.sh:100-104`).
- Claude Code 하네스 자체(PreToolUse/PostToolUse 이벤트, stdin JSON 스키마)가 유일한 "상위" 의존성이다 — 이 스키마가 바뀌면 이 훅 전체가 영향받는다(이번 작업의 범위 밖).

## 실패 모드 메커니즘

- **PostToolUse에서 로직 파일 변경이 관측되는 경우** (`gate-guard.sh:190-193`): 정상 흐름에서는 PreToolUse가 이미 막았어야 하므로 여기 도달하면 안 된다. 원인은 PreToolUse 훅 자체가 등록 안 됐거나(설정 오류), 다른 경로로 파일이 바뀌었거나(Bash 등), 혹은 세션 간 상태파일 불일치다. 증상은 사용자가 의도치 않은 코드 변경을 발견하는 것. 시스템은 이걸 막을 수 없으므로(사후 시점) 대신 stderr에 감사 경고를 남겨 **관측 가능하게** 만든다(리뷰 F1 이후 추가 — 이전엔 완전 침묵).
- **Bash를 통한 로직 파일 우회** (`gate-guard.sh:61-77`): `IS_BASH=1` 경로는 `file_path`가 아예 없어(Bash 툴은 `command`만 줌) 위쪽의 canonical 경로 분류 자체가 적용되지 않는다 — 그래서 "이 명령이 어떤 파일을 건드리는가"를 원천적으로 알 수 없고, 무조건 소프트 리마인더만 낸다. 하드 차단으로 승격하려면 명령 파싱(어떤 파일을 쓰는지 추출)이 필요한데, 임의 셸 명령 파싱은 본질적으로 불완전해 오탐(정당한 테스트 실행까지 차단)이 크다 — 그래서 §0.6 기준상 훅에 맡기지 않고 문서(리마인더+플레이북 규율)로 남겼다.
- **`is_test_file()` 정규화 실패는 없다** — 이 함수는 항상 정의된 값(0 또는 1)을 반환하는 순수 문자열 매칭이라 예외 경로가 없다. 실패 가능성은 그 이전 단계인 `canon_file()`(경로 정규화)에 있고, 거기는 이미 fail-closed로 처리된다.

## 함정 (이번에 확인된 비직관 동작)

- `tests/**`·`spec/**` 디렉토리 전체가 확장자 무관하게 신뢰된다 — 그 안에 실수로 로직 파일(예: 헬퍼가 아닌 실제 도메인 클래스)을 두면 pair 모드 보호가 적용되지 않는다. 디렉토리 배치 자체가 신뢰 경계라는 뜻.
- 대소문자를 구분한다 — `Tests/`(대문자 T)나 `FOO.TEST.TS`는 컨벤션에 안 걸려 로직 파일로 분류(=차단)된다. 안전한 방향의 오차단이라 버그로 취급하지 않았다(리뷰에서 확인, 수정 대상 아님으로 판정).
- Bash 리마인더는 이제 **명령 내용과 무관하게 무조건** 발화한다(`gate-guard.sh:74-75`) — 최초 구현은 `sed -i`/`tee`/heredoc 패턴에만 반응했으나, plain redirect(`>`)·`cp`·`perl -pi` 등이 새는 게 리뷰에서 확인돼 `*-write` await/verify와 동일하게 무조건 발화로 강화했다.
