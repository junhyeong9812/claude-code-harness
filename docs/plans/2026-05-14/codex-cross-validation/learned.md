|----------------|------|------|-------------|
| codex CLI | `codex-cli 0.130.0` | 외부 LLM(GPT-5.5) 비대화형 단발 호출 | 사용자 환경에 이미 설치/인증되어 있고 ChatGPT 구독 한도 내 사용 가능. Claude → 다른 LLM 단방향 호출에 적합 |

## 2. 핵심 함수 / 메서드

본 작업의 핵심 "함수"는 **codex 호출 패턴**과 **마크다운 구조 변환 패턴**.

### 2.1 codex 호출 표준 패턴

| 함수/메서드 | 시그니처 | 역할 | 사용 위치 |
|------------|---------|------|----------|
| `codex exec` | `cat <input> \| codex exec --skip-git-repo-check -s read-only --ephemeral -o <output> -` | 비대화형 단발 호출 (stdin 프롬프트, 파일 응답) | `templates/codex-prompt.md` 호출 방식 |
| `Bash(run_in_background=true)` | Claude Code 도구 | 30~120초 codex 응답을 백그라운드 대기 → 자동 알림 | 본 작업 plan 검토·강점 분리 검토 2회 사용 |

**사용 예시** (본 작업의 plan 메타 검토 호출):

```
cat /tmp/codex-plan-review-input.md | codex exec --skip-git-repo-check -s read-only --ephemeral -o /tmp/codex-plan-review-output.md - > /tmp/codex-plan-review.stdout.log 2> /tmp/codex-plan-review.stderr.log
```

- 출처: 본 작업의 codex 메타 검증 호출 명령

**코드 설명:**
- `cat <input>`: 프롬프트 파일 표준 출력으로
- `|` pipe: codex exec에 stdin으로 전달
- `--skip-git-repo-check`: codex가 자기 cwd 외에서도 실행 허용
- `-s read-only`: codex가 파일 시스템 쓰기 차단 — Claude 작업 공간 보호
- `--ephemeral`: 세션 파일 디스크 보존 안 함 — 단발에 적합
- `-o <output>`: 마지막 메시지를 파일로 저장
- `-` (stdin 명시): prompt 인자 대신 stdin에서 읽음 — 긴 프롬프트 전달
- `> stdout.log 2> stderr.log`: stdout/stderr 분리 캡처

### 2.2 마크다운 구조 변환 패턴

| 패턴 | 적용 위치 | 역할 |
|------|----------|------|
| 헤딩 위계 깊이 (####) | 파이프라인 단계 식별 | LLM에 단계 구분 신호 |
| 펜스 코드 블록(```...```)에 보고 템플릿 | B2/A2/C2 게이트 보고 형식 | LLM이 출력 템플릿으로 그대로 재현 |
| `★ 의무 ★`, `★ 필수 게이트 ★` 시각 기호 | 강제력 표지 | 일반 강조보다 강한 priority 신호 |
| 표 형식(`| 컬럼 |`) | 정책·매핑·체크리스트 | LLM이 표 구조로 채워야 함을 인식 |
| `[ ]` 체크박스 (GFM 확장) | 진행 상태 추적 | 사용자/LLM 토글 가능 — 행동 유도성 |

## 6. 디자인 패턴

### 6.1 신호원 다중화 (Signal Diversification)

| 패턴 | 적용 위치 | 왜 사용했는가 | 구조 |
|------|----------|-------------|------|
| 다른 신호원으로 같은 판단 흔들기 | B1.5 + B1.6 + B3 codex 검토 + B5 codex 검증 | LLM 단일 추론의 다수결 편향을 외부 신호로 보정 | Claude 내부 분석 → 외부 사람 자료(WebSearch) → 외부 LLM(codex) → 사용자 확인 — 4단 신호원 |

**패턴 상세:**

### 신호원 다중화
- **의도**: 한 모델의 추론에 의존하면 학습 데이터 다수결 편향이 그대로 답에 반영됨. 다른 성격의 신호원으로 다중 검증.
- **구조**: 4개 신호원이 단계적으로 호출됨 — Claude(내부) → 사람 자료 → 외부 LLM → 사용자.
- **이 프로젝트에서의 적용**: 모든 X.5/X.6 단계가 이 패턴의 구현.

```markdown
[B1.5 외부 큐레이션]
  → Claude WebSearch (사람 자료)
  → codex 외부 큐레이션 (다른 LLM 큐레이션)
  → 둘을 research.md 2절에 함께 기록, 출처 구분

[B1.6 모델 교차 검증]
  → codex로 Claude 분석에 second opinion
  → research.md 3·4절에 교차 보고
```
- 출처: `orchestration-impl.md:4.B 절`

### 6.2 게이트 + 의미 확장 (Gate Expansion)

기존 B2 "이해 확인" 게이트가 새 절차 도입으로 **"방향성 점검"** 으로 의미 확장. 게이트 구조(보고 형식 + 진행 조건)는 그대로 유지하되 입력 자료가 단일 분석에서 통합 산출물(research.md)로 바뀜.

### 6.3 패턴 기반 보안 게이트 (Pattern-Based Security Gate)

- **의도**: `.env` 파일명 차단은 시크릿 키/PII/스택 트레이스 누설을 막지 못함. 내용 패턴 기반이 더 정확.
- **구조**: 정규식 + 키워드 + 차단 동작 표 (6개 분류) — `orchestration-impl.md` 5.7절.
- **적용**: codex 호출 직전 자동 스캔 → 매칭 0건일 때만 자동 통과, 매칭 발견 시 사용자 보고 후 redact/중단.

### 6.4 캐시 키로서의 입력 해시 (Input Hash as Cache Key)

- **의도**: 같은 입력으로 codex를 다시 부르면 비용·시간 낭비. 작업 재개 시 중복 호출도 막아야 함.
- **구조**: 호출 ID(`{작업명}/{단계}/{순번}`) + 입력 해시(sha256 앞 12자)를 checklist 표에 기록 → 동일 해시면 캐시 응답 재사용.
- **적용**: `templates/checklist.md` 호출 기록 표, `templates/codex-prompt.md` 0.4절.

- **소규모 작업에서 절차 비용 33배 오버헤드 가능성**. general-purpose 메타 평가가 정량 추정 — 소규모(1~2파일) 작업의 절차 비용 ~67분 vs 실제 코드 작업 2분. 사용자가 "원안 유지(모든 단계 의무)"로 결정했지만, 30일 운용 후 데이터 보고 재검토 가치 큼.

- **codex CLI의 자기 cwd 오인 패턴**. codex가 plan 메타 검토할 때 자기 호출 시점의 cwd(`/home/jun/project/claude-code-study`)를 본 작업 plan의 컨텍스트로 오인해서 "경로 불일치" 지적을 했다. 실제로는 plan 경로(`/home/jun/project/claude_study`)가 정확. **외부 LLM 호출 시 컨텍스트 격리 효과의 부작용** — 컨텍스트가 격리되어 객관적 시각이 좋지만, 동시에 호출자(Claude)의 cwd를 모름. 향후 plan.md 1절에 "기준 경로" 한 줄 명시가 표준 패턴화 권장.

- **호출 ID + 입력 해시 캐시는 작업 재개에 의미 있음**. codex 응답 시간이 30~120초라 작업 중단 후 재개 시 매번 다시 부르면 누적 손해. sha256 앞 12자 정도면 표 가독성도 좋고 충돌 가능성도 낮음.

### 11.5 모델 교차 검증의 본 작업에서의 학습

- **codex와 general-purpose agent는 신호 성격이 다르다**. codex는 짧고 날카로운 지적 위주(8개 / 5절), agent는 광범위하고 구조화된 평가(6개 절 + 정량 추정). 같은 검토를 두 곳에 부탁하면 둘 다 활용 가치가 다름.
- **프롬프트 형식의 강제력**. 본 작업의 codex 프롬프트들은 "동의·칭찬·도입부 금지, 곧바로 지적부터" 같은 형식 강제로 잘 작동. agent 프롬프트에도 같은 패턴 적용 시 응답 품질 균일화.
- **백그라운드 호출의 시간 흡수**. codex/agent 호출이 30초~3분 소요되는 동안 templates 작성·문서 보강 등 메인 작업 병행 가능. 단 큰 게이트(B2 사용자 보고)는 응답 받기 전 진행 불가.
- **재귀 적용 가치**. 새 절차를 자기 plan에 적용하면 함정이 빨리 드러남 — 본 작업에서 codex 메타 검토 8개 지적 중 6개 즉시 plan에 반영됨. 절차 정의 직후 자기 자신에게 시험 적용을 표준 패턴으로 권장.
- **외부 LLM의 자기 평가 편향 의식**. codex에게 "Claude=추상화 vs codex=알고리즘" 가설을 물을 때 자기 강점 평가 편향이 들어갈 수 있어 프롬프트에 명시 — 결과는 codex가 오히려 "능력 고정이 아니라 검토 관점 분리"라며 자기 강점 가설 자체를 흔드는 답을 줌. 외부 LLM의 객관성을 과대평가하지도 과소평가하지도 않는 균형이 필요.
- **외부 LLM 첫 응답의 일반론 편향 — 재귀 검토로 정정 가능**. 본 작업 직후 부속 토론(`docs/analysis/2026-05-14-harness-comparison.md`)에서 codex가 같은 도메인 질문에 1차/2차로 상반된 결론을 줌. 1차는 "Skills 전환 1순위" (일반 베스트 프랙티스 기반), 2차는 "인라인이 더 나음" (사용자 운용 맥락 적용). **첫 응답을 그대로 채택하지 말고 한 번 더 흔드는 절차**가 일반론 편향을 거름. 사용자 직관이 두 응답 사이 시점에서 미리 같은 방향을 봄 — **운용 패턴을 깊이 아는 사용자의 직관 > 일반론적 외부 권고**.
- **외부 권고는 검증 도구이지 대체재가 아님**. Plugin/MCP/Skills 도입 권고 3종 모두 사용자 운용 맥락 필터링 후 skip. 두 차례 codex + WebSearch + Agent 동원해도, 사용자가 모르는 가치를 발견하기보다 사용자 결정의 **타당성을 검증**하는 데 더 큰 가치가 있었음. 외부 신호의 적정 사용 패턴은 "이 결정을 정말 해도 되는가"의 second opinion이지 "무엇을 해야 하는가"의 답이 아님.
