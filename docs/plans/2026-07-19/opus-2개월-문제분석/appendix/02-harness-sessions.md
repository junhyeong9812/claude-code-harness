## 대표 문제 에피소드 Top 9

**1. [7/6, Sonnet] git-guard docs-commit false-block 루프 — 최악의 UX 마찰 (~1시간 50분)**
README docs 커밋이 git-guard의 one-shot 승인 모델에 7회 연속 차단됐다. "커밋해줄래?"는 물음표라 질문으로 분류, "커밋해줘"는 화이트리스트 exact-match 실패, "네"조차 중간에 설명 턴이 끼어 턴 카운트(+1 규칙)가 어긋나 2회 무효화. 사용자는 "어떤게 문제야?" → "아니 이건 커밋은 왜 막히는거야?"로 점점 답답해했고, Claude는 매번 "정확히 '네'만/'문서 커밋해줘'라고 말해달라"고 마법 주문을 요구했다. **세션은 커밋 미완 상태로 종료**됐다(마지막 메시지도 재차 문구 요청). 하네스가 스스로 만든 덫을 Claude가 우회 설계 없이 사용자에게 부담 전가한 사례.

**2. [7/3, Opus 구간] heredoc 조기 종료로 실제 `git push`가 실행된 사고**
테스트 픽스처를 `cat >> ... << 'EOF'`로 추가하다 내용 속 heredoc 태그와 충돌해 EOF가 조기 종료, 픽스처 안의 `git push` 문자열이 **실제 셸 명령으로 실행**됐다(refspec 오류로 무해하게 실패). 직전에 git-guard가 같은 패턴을 차단하자 guard의 스캔 로직을 수정해 통과시킨 뒤 발생한 것이라, 안전훅 우회 후 사고라는 점이 뼈아프다. Claude가 즉시 원인을 파악하고 python3 기반 안전 append로 전환·복구했고, 이후 guard에 heredoc 첫 태그 추출 로직이 추가됐다.

**3. [7/3, Opus 구간] 좀비 백그라운드 대기 루프 5개 (최대 1시간 31분)**
워커 완료 대기용으로 `until [ -f /nonexistent ]; do sleep 30; done` 류 루프를 백그라운드로 5개 띄웠는데, 워커가 다 끝나도 조건이 영원히 거짓이라 계속 돌았다. 사용자가 "지금 쉘스크립트 돌아가는거 머야?"라고 물어서야 발견됐고, ps로 확인 후 5개 전부 kill로 정리했다. (메모리의 "pgrep self-match loop" 교훈과 같은 계열 — 폴링 대기 패턴 반복 실패.)

**4. [6/22, Opus] git-guard jsonl 지연 false-block + AskUserQuestion 답변 미인식**
사용자가 AskUserQuestion 답변으로 "푸시해줘..."라고 명시 승인했는데 push가 2회 연속 차단됐다. 당시 git-guard가 승인을 세션 jsonl(기록 지연)에서만 읽어 현재 턴 발화를 못 봤기 때문. Claude가 훅을 디버깅해 원인을 규명하고 메모리에 기록했으며, 사용자가 "둘다 버그아니야?"라고 못박자 F4(이중질문)와 함께 버그로 인정 — 이후 capture-prompt 사이드카 훅으로 근본 수정됐다.

**5. [6/22, Opus] 모드 선택 메뉴 4개 중 3개만 제시 (lazy-write 누락)**
write 모드 4분기를 막 구현 완료한 직후, 새 작업 모드를 묻는 AskUserQuestion에 자신이 방금 만든 `lazy-write`를 빼고 3개만 띄웠다. 사용자가 "그런데 lazy-write모드는 왜 안물어보지?"라고 지적하자 "제 실수입니다 — 4개 중 3개만 띄웠습니다"라고 자인. 구현(훅 메뉴)은 정상이었고 Claude의 질문 구성만 누락이라 즉시 정정으로 수습.

**6. [7/3] "푸시해줘" 이후에도 반복되는 승인 차단 — 정상 동작과 마찰의 경계**
새로 배포한 scoped 승인 모델이 이전 턴 승인("push까지 부탁해")을 stale로 차단, "정리하자"의 원격 브랜치 삭제 차단, "기록도 부탁해"의 docs 커밋 차단 등이 연쇄됐다. Claude는 매번 "새 guard의 정상 동작(dogfood)"이라 해설했지만 사용자는 "해당 내용이 결국 리뷰 루프마다 승인 구조가 제대로 안되는게 문제라는거야?"라고 되물었고, Claude가 "자연어 승인을 셸 정규식으로 파싱하는 구조적 한계"를 정리 → 사용자가 "한계라 그대로 하고"로 수용 결정. (이 한계가 에피소드 1의 7/6 마찰로 그대로 재현된다.)

**7. [7/6, Sonnet] 한국어 사용자에게 영어 응답 지속**
git-guard 차단 해설을 갑자기 영어로 하기 시작했고, 사용자가 "한국어로 해줄래?"라고 요청한 후에도 다음 응답 2개를 다시 영어로 했다. 사용자가 "왜 영어로 답변일까?"라고 재지적하자 사과 후 한국어로 복귀. 별도 트리거 없이 발생한 언어 드리프트.

**8. [6/21, Opus] make-tools 동작에 대한 잘못된 단정 → 사용자 반박 → 정정**
모드 리네이밍 토론 중 Claude가 설계 문서만 보고 "make-tools는 implementation 절차를 건너뛰는 모드"라고 표로 단정했는데, 사용자가 "아닐텐데? ...실 구현으로 가면 물어보지않아?"라고 반박. Claude가 "제가 과하게 말했네요"라며 실제 훅 코드를 읽고 정정했다. 문서 근거만으로 실동작을 단정한 core §2(실코드 확인) 위반 사례.

**9. [7/6, Sonnet] main 직접 작업 (§6.5 브랜치 우선 위반) — 자가 발견**
pair 모드 훅 4개 + 테스트를 main 위에서 바로 작업하다가 커밋 직전에 스스로 "제가 지금까지 main 위에서 바로 작업했네요, 브랜치 생성을 놓쳤습니다"라고 자인하고 `feature/pair-coding-mode` 브랜치를 만들어 수습. 사용자 지적 전 자가 교정이라 피해는 없었다.

**보조 관찰**: (a) 7/3 세션에서 "하지 말라고 안내된" 서브에이전트 원본 트랜스크립트를 열었다가 즉시 사과·중단한 건이 1건(Opus 구간). (b) Edit 실패(string-not-found, 미독 파일)는 5건으로 낮은 빈도이고 모두 1회 재시도로 회복. (c) API 레벨 에러·컨텍스트 요약 이벤트는 5개 세션 모두 0건 — 문제의 대부분은 모델 추론 오류보다 **하네스(특히 git-guard 자연어 승인)와의 상호작용 마찰**과 **셸 조작 사고(heredoc·폴링 루프)**에 집중돼 있다.
