## 3. 문제 리스트업 (유형별 · 빈도순)

### A. 게이트/상태 (빈도 高)

- **A1. 워크트리마다 상태파일이 갈라진다** — gate-guard가 *편집 대상 파일이 속한 repo 루트* 기준으로 상태를 찾으므로, 워크트리 병행 작업(이 그룹의 기본 작업 방식: `was-*-wt`, `front-*-wt`, `text-*-wt`)에서는 **같은 승인을 경로마다 다시 기록**해야 한다. 실측: `spec-approved` 87회 / 작업폴더 66개, 2경로 동시 기록 패턴이 반복(`for sf in <루트> <was-server>; do …`). 근거: 2026-07-21T02:09 차단, 메모리 `gate-state-per-worktree.md`.
- **A2. 상태가 세션 도중 사라진다** — 2026-07-23T10:25 워커 보고: 최초 편집은 통과했는데 이후 상태파일이 **양쪽 경로 모두 부재**. 워커가 정지·핸드오프해 손실은 없었지만, 장시간 세션(이 그룹 세션은 최장 8일 연속: 8a4f44d2 07-20→07-28)에서 turn/date 경계 소실이 관측됨. 빈도 1건(관측), 영향 큼.
- **A3. 모드 답변이 자동 기록되지 않는다** — AskUserQuestion으로 모드를 물어도 훅이 기록하지 않아 매번 `set-state`를 손으로 호출해야 한다. "매 세션 L1 첫 산출물 변경 때 반복되는 마찰"(메모리 원문). 빈도: L1 진입마다(82회).
- **A4. 직전 SPEC=1 재사용(core §1이 명시한 고유 한계)이 실제로 광범위하게 발생** — 8c8e5f1d에서 spec 1개가 5시간·명세 범위 밖 L1 20여 회를 덮었다. 66개 폴더가 만들어졌다는 사실이 곧 "모든 L1이 명세를 통과했다"는 뜻이 아니다. 훅으로 관측 불가.
- **A5. lazy 모드 사용률 0%** — 2택이 실질 1택. 게이트가 실제로 조절하는 축은 "auto냐 lazy냐"가 아니라 "spec을 쓰느냐"뿐이다.
- **A6. 빚(DEBT)이 문서와 상태로 이원화** — `## 생략한 검증` 47회 vs `DEBT=1` 상태 1회. 재주입이 상기시키는 빚은 사실상 1건뿐이었고, 나머지 46건은 log.md에만 남아 "차기 L1 진입 시 빚 우선" 규칙이 발동하지 않았다.

### B. 리뷰 (빈도 中)

- **B1. Opus 리뷰의 오탐이 "packet-only 격리"에서 나온다** — 명시 오탐 3건(R7/R8/R9)이 전부 "실코드를 안 읽어 없는 결함을 지어낸" 유형이고, 판정 근거가 전부 "실코드 확인"이었다. codex 오판 1건(I3)도 packet 범위 밖 파일이 원인. **격리가 오탐의 원인이자 오탐 검출 비용의 원인**.
- **B2. Opus 단독 finding의 채택률(37%)이 codex 단독(58%)보다 낮다** — 다만 양쪽이 함께 짚은 finding의 채택률은 88%로, **교차 일치가 가장 강한 신호**. (근사치 — §1-4 한계 참조.)
- **B3. codex 실행 자체가 환경에 막힌다** — 분류기 차단 2 + `sleep` 폴링 차단 3 = 5건. 전부 명령 형태 문제(파이프 입력·sleep 체이닝)라 재시도로 풀렸지만, 매 리뷰마다 같은 함정을 다시 밟는다.
- **B4. 리뷰 결과 회수 실패 1건**(C3) — 백그라운드 codex 산출물이 없어 `cat` 실패. `review blocked` 선언이나 대체 리뷰어 절차로 가지 않고 우회.
- **B5. "리뷰가 독이 된" 명확한 사례는 관측되지 않음** — 오탐 4건은 모두 **기각으로 걸러졌고 코드에 반영되지 않았다**. 다만 비용은 실재한다: OTP 왕복(B1 케이스)에서 듀얼 리뷰 3회·워커 6회분이 폐기된 코드에 소모됐고, 8c8e5f1d 긴급 국면에서는 리뷰 절차 자체가 사용자 불만의 직접 원인이 됐다(아래 C1).

### C. 절차 무게 ↔ 리드타임 (빈도 中, 체감 强)

- **C1. 긴급 국면에 본작업급 절차를 적용** — 2026-07-29 배포가 막힌 상태에서 라벨 한 줄 수정에도 워커 왕복·듀얼 리뷰·전체 IT 재실행을 붙여 **연속 4턴 질책 + 3회 인터럽트**. 사용자가 직접 규칙을 만들어 메모리에 박음(`urgent-fix-weight-protocol.md`: "수정→즉석 스모크→즉시 push→생략분은 빚"). core §1 긴급 경로가 이미 정의한 모드인데 **발동 판단을 놓쳤다**.

- **D1. silent failure는 대체로 사용자가 먼저 발견했다** — D4(US/CN 무음 배선 제거), C4(워커 CSS 누락), B2(등급 무음 소실) 모두 코드/테스트가 아니라 **사용자 눈 또는 메인의 스팟체크**가 잡았다. 반면 "그린 위장" 함정 3종은 이미 메모리로 축적돼 있다(`verify-pitfalls-2026-06-10`: `mvn | grep | tail` exit 마스킹, testcontainers reuse×Flyway, 백그라운드 조기 완료 알림).

## 4. 판정 불가 · 한계

1. **서브에이전트 전사 240개는 개수만 셌다**(브리핑 지시). 따라서 "워커 내부에서 일어난 게이트 우회·codex 호출·자격증명 취급"은 이 보고서 범위 밖이다. 훅이 워커 쓰기를 관측하지 못한다는 core §5·§6.3의 절차 한계는 **검증되지 않은 채 남아 있다**.
2. **reinject 1줄 재주입의 실발화 여부 판정 불가** — UserPromptSubmit additionalContext가 전사에 별도 레코드로 남지 않아, "매 턴 모드·DEBT가 실제로 재주입됐는지"를 확인할 수 없었다.
3. **리뷰 ledger 수치는 근사** — 같은 finding의 초안/확정 이중 기록을 완전히 병합하지 못했다(§1-4). 절대 건수보다 **출처별 채택률과 오탐 유형**을 신뢰할 것.
4. **"리뷰가 독이 됐는가"에 대한 직접 증거 부족** — 오탐이 코드에 반영된 뒤 되돌려진 사례는 이 그룹에서 발견되지 않았다. 다만 리뷰가 **기각 판정에 들인 비용**(오탐 4건마다 실코드 재확인)과 **긴급 국면의 리드타임 손해**(C1)는 관측됐다. 반영 후 회귀를 확인하려면 각 repo의 실제 커밋 히스토리 대조가 필요하다(본 태스크 범위 밖 — git 조작 금지).
5. **일부 세션은 2026-07-21 이전에 시작**(92b86f3b 07-10~07-13, cdf01b67 07-14~07-20, 8a4f44d2 07-20~07-28). 훅 사건은 timestamp로 pre/post를 분리했으나, **8a4f44d2·f33bab99처럼 v3→v4 전환을 걸친 세션은 앞부분이 구 모드값(auto-implements 등) 문구를 포함**한다. §1 수치는 전부 `timestamp >= 2026-07-21` 필터 적용본이다.
6. **업무 데이터 값(고객·상표·자격증명)은 의도적으로 제외**했다. 사건 구조·경로·시각만 기록했으므로, 개별 케이스를 재확인하려면 원 전사의 해당 시각을 직접 열어야 한다.
