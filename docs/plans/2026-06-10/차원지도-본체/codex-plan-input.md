당신은 독립 검토자다. 이전 라운드에서 당신(또는 동급 검토자)이 지적한 설계 원칙이 반영된 구현 초안이다.
반증·누락·집행 공백 중심으로 검토하라. 칭찬 금지.

## 이전 라운드 합의 (구현이 지켜야 할 계약)
- 트리아지: 14차원 전수, 행 형식 `판정(활성/light/비활성)/근거/본 파일·심볼/불확실성`, 비활성에도 증거 인용, 불확실하면 light 활성
- stakes: 하한(활성 차원 max) → 영향면 보정(면제도 증거) → 누적 승격(중간 3+) → 낯섦·모호성과 max
- 본체 ≤200줄·차원당 ≤10줄·색인이지 교과서 아님, 확장팩(배치/프론트/인프라) 조건부 로드
- 질문 보정 루프: 부적합≠비활성, task.md에 기록, 정본 개정은 월 1회 승격(2회+ 재등장 or 결함 연결)만
- 질문 ID는 원 18번호 유지 + P/I/V 접미사

## 검토 질문
1. 아래 본체의 차원별 트리거 질문(n-T)·활성/비활성 신호가 서로 겹치거나(같은 변경이 어느 차원인지 모호) 빠지는 변경 유형이 있는가? 구체 사례로.
2. stakes 표기가 차원 간 일관적인가? (예: 4 정합성=중간 vs 5 동시성=중간 — 같은 write 변경이 두 차원에서 다른 하한을 받는 경우의 처리)
3. light 활성의 정의("P/I/V 질문에 답만 기록, 분리 리뷰 생략")가 집행 가능한가? 빠져나갈 구멍은?
4. 확장팩 차원(B/F/I)과 기본 14차원의 중복·충돌은? (예: I3 secrets vs 11 보안, B2 부분 실패 vs 9 장애복구)

6. 경량 경로 폐지의 부작용: 1줄 오타 수정 같은 작업도 task.md+14행 트리아지를 요구하게 된다. 운영 가능한가? 완화책이 필요하다면 무엇인가?

# 본체 초안 (dimensions.md)

# dimensions.md — 개발 차원 지도 (트리아지 + 단계별 렌즈)

> 로딩 트리거: 정의 게이트 진입 시 (core §7). 절차 규칙은 core.md, **차원 내용은 이 문서가 단일 출처.**
> 개정은 월 1회 측정 리뷰의 승격 절차로만 (§정비). 인간용 자매 문서: claude_study `docs/17`(승격분만 반영).

## 사용법 — 트리아지 (모든 정의됨 작업, 전 stakes)

1. 아래 14차원을 **전수** 판정해 task.md §1 트리아지 표에 기록. 행 형식: `판정(활성/light/비활성) / 근거 / 본 파일·심볼 / 불확실성`.
2. **비활성에도 증거를 인용한다** (변경 파일·심볼·diff 범위) — "해당 없음" 한마디 금지.
3. **불확실하면 비활성 금지** → light 활성. light = 해당 차원 P/I/V 질문에 답만 기록, 분리 리뷰는 생략.
4. 활성 차원의 질문이 작업에 안 맞으면(부적합) §보정 루프로 — 임의로 질문을 바꾸지 않는다.
5. 작업 표면이 배치/프론트엔드/인프라에 닿으면 확장팩 추가 로드 (§확장팩).

## stakes 도출 — 칸6 = max(아래 1~3, 낯섦·모호성 판단)

1. **하한**: 활성 차원별 stakes 표기의 최대값.
2. **영향면 보정**: production 코드·공개 표면·돈·PII·불가역에 닿으면 표기대로, 아니면 한 단계 하향 가능 — **면제에도 증거 의무** (예: "테스트 fixture만 — 경로 인용").
3. **누적 승격**: 중간급 차원 3개+ 동시 활성 → 한 단계 승격 검토 (blast radius).
4. 낯섦(처음 쓰는 lib·패턴·배포)·모호성(요구 불명확)은 차원이 못 잡는다 — 별도 판단 후 max.

## 차원 (ID = 원 18번호 · P=계획 I=구현 V=검증)

### 2 입력 검증
- 2-T: 외부에서 온 값(사용자 입력·API 요청·파일·헤더)을 새로 받거나 검증 경로를 바꾸는가?
- 활성: endpoint 파라미터/DTO 필드 신설·변경 · 파일 업로드 · 외부 데이터 파싱 | 경로: controller·dto·validator·form
- 비활성: 내부 함수 시그니처만 변경 · 이미 검증된 값의 내부 전달
- stakes: 활성=낮음↑ · 공개 표면이면 중간
- 2-P: 검증 규칙(필수·길이·형식·범위·enum)이 계약에 명시됐나? 프론트/백 역할 분리는?
- 2-I: **백엔드가 최종 방어선** — 어느 층에서 막나? 인젝션 가능 지점은?
- 2-V: 빈 값·경계값·잘못된 enum·인젝션 문자열 테스트가 있나?

### 3 권한 경계
- 3-T: 인증·인가·소유권·tenant 경계를 지나는 경로를 만들거나 바꾸는가?
- 활성: 신규 endpoint · role/ownership check 변경 · admin 기능 · 토큰 처리 | 경로: auth·security·middleware·policy
- 비활성: 권한 검사 이후의 내부 로직만 · 테스트 fixture만 (증거 필요)
- stakes: 활성=높음 (production 권한 로직 아님이 증명되면 중간) · **3 활성 → 11 light 자동 활성**
- 3-P: 인증(누구)/인가(되는가)/소유권(그 사람 것인가) 3단이 각각 어디서 검증되나?
- 3-I: 권한 없는 사용자가 이 코드에 도달하면? 우회 경로는?
- 3-V: 권한별 결과·남의 리소스 접근 테스트가 있나?

### 4 데이터 정합성
- 4-T: 데이터를 쓰거나(write) 상태를 바꾸는가?
- 활성: insert/update/delete · 상태 전이 · 트랜잭션 경계 변경 | 경로: service(write)·repository·migration
- 비활성: 순수 조회 · 표현 계층만
- stakes: 활성=중간 · 돈·불가역 삭제·마이그레이션이면 높음
- 4-P: 트랜잭션 범위는? 중간 실패 시 어디까지 롤백? 삭제는 물리/논리?
- 4-I: 상태 전이 검증이 코드에 있나? 중복 요청 방어는?
- 4-V: 실행 후 **데이터 상태를 직접 검증**하나(호출 성공만 말고)? edge(빈·중복·stale) 데이터는?

### 5 동시성
- 5-T: 같은 리소스에 동시 접근(연타·재시도·배치 중복·다중 인스턴스)이 가능한 경로인가?
- 활성: write 경로 · 재고/잔액/카운터 · 스케줄러 · 외부 재시도 유발 | 경로: queue·scheduler·lock
- 비활성: 불변 데이터 조회 · 단일 사용자 로컬 도구
- stakes: 활성=중간 · 돈이 움직이는 write면 높음
- 5-P: 방어 선택 — unique 제약 / 낙관락 / 비관락 / 분산락 / idempotency key / 상태 기반?
- 5-I: 락 범위·데드락 가능성은? 멱등 키는 어디서 생성되나?
- 5-V: 동시 요청·중복 요청을 재현하는 테스트가 필요한가, 있는가?

### 6 예외 처리
- 6-T: 실패할 수 있는 동작(외부 IO·DB write·API 경계·job·타임아웃·상태 변경)을 만들거나 바꾸는가?
- 활성(넓게): 외부 호출 · write · 신규 endpoint · 에러 매핑 변경 | 경로: exception·handler·advice·client
- 비활성(좁게): 순수 리네임 · 계산식 정리
- stakes: 활성=낮음↑ · 실패가 사용자·데이터에 전파되면 중간
- 6-P: 에러 코드·메시지 정책이 프로젝트 기존 전략과 일관한가?
- 6-I: 복구 가능/재시도 가능/알림 필요를 구분했나? 민감정보가 응답에 새나?
- 6-V: 실패 의미론마다 예외 경로 테스트 1개+ 있나?

### 8 성능
- 8-T: 쿼리·데이터량·호출량 특성이 바뀌는가?
- 활성: 신규 쿼리/조인 · 루프 내 호출 · 페이징·검색 조건 · 대량 처리 | 경로: repository·query·batch
- 비활성: 데이터량 특성 불변의 로직 변경 · 상수·설정만
- stakes: 활성=낮음↑ · 핵심 경로·대량 데이터면 중간
- 8-P: 인덱스 타는 조건인가? 페이징·count 전략은? 캐시 필요?
- 8-I: N+1은? 메모리에 전량 적재하나?
- 8-V: 데이터 10배 시나리오에서 버티나? 쿼리 수를 실측했나?

### 9 장애 복구
- 9-T: 내가 제어하지 않는 것(외부 API·queue·타 서비스·네트워크)에 의존하는 경로를 만들거나 바꾸는가?
- 활성: 외부 API 호출 · MQ 발행/소비 · webhook · 배치 재처리 | 경로: client·consumer·retry
- 비활성: 단일 프로세스 내 동기 로직만
- stakes: 활성=중간 · 결제·정산 등 불가역 외부 효과면 높음
- 9-P: 상대가 느림/다운/이상 응답일 때 각각? retry·timeout·fallback·DLQ·보상 중 무엇을?
- 9-I: 재시도가 중복 실행을 만들지 않나(idempotency)? checkpoint·재처리 구조는?
- 9-V: 의존 실패를 주입한 플로우 디버깅을 했나? 실패가 어디에 기록되나?

### 10 운영 가능성
- 10-T: 배포 후 관찰·복구가 필요한 동작을 추가·변경하는가?
- 활성: 신규 기능 경로 · 배치 · 설정값 추가 · 로그 의미 변경 | 경로: config·logging·metrics
- 비활성: 기존 관측 범위 안의 미세 수정
- stakes: 활성=낮음↑ · 장애 시 수동 복구가 필요한 기능이면 중간
- 10-P: 설정을 코드 수정 없이 바꿀 수 있나? 롤백·기능 끄기 가능한가?
- 10-I: requestId·traceId·사용자 id가 로그에 남나? 실패 알림은?
- 10-V: 장애 시 따라 할 runbook·보정 쿼리·재처리 도구가 있나?

### 11 보안
- 11-T: 공격 표면(입력 파싱·토큰·파일·secret·서버 간 통신·로그)이 생기거나 바뀌는가?
- 활성: 토큰/세션 처리 · 업로드 · secret 사용 · CORS/CSRF 설정 · PII 취급 | 경로: security·filter·config·env
- 비활성: 공격자 도달 불가 내부 로직 (증명 필요)
- stakes: 활성=높음 (내부 전용·비프로덕션 증명 시 중간)
- 11-P: 하위 영역 — secrets / 암호화 / 세션·토큰 / PII·마스킹 / 감사 로그 중 해당은? (참조: OWASP ASVS)
- 11-I: 인젝션·XSS·CSRF 방어는? 로그에 개인정보·secret이 남나?
- 11-V: 악의 입력·권한 우회 시나리오 테스트가 있나?

### 12 API 계약
- 12-T: 외부(클라이언트·타 서비스)가 의존하는 계약(URL·스키마·이벤트·에러 포맷)을 만들거나 바꾸는가?
- 활성: 신규/변경 endpoint · 응답 필드 변경 · 이벤트 스키마 | 경로: controller·dto·openapi·contract
- 비활성: 계약 동일이 증명되는 내부 구현 변경
- stakes: public 계약 변경=높음 · 내부 계약=중간
- 12-P: 하위 호환인가? 리소스 중심 URL·Method·에러 포맷 통일은?
- 12-I: 내부 엔티티가 그대로 노출되나? 과다 응답은?
- 12-V: 기존 클라이언트가 깨지나? (최소 안전선 contract 항목과 연결)

### 14 도메인 규칙
- 14-T: 상태 전이·금액/수량 계산·정책 조건(할인·환불·정산 등)을 만들거나 바꾸는가?
- 활성: 계산식 · 상태 머신 · 정책 분기 · 반올림/통화/시간대 | 경로: domain·policy·calculator
- 비활성: 도메인 의미 불변의 기술적 변경
- stakes: 활성=중간 · 돈·법적 의무에 닿으면 높음 (**보안·권한 없어도**)
- 14-P: 불변식을 한 문장으로 말할 수 있나? 규칙이 한 곳에 사나, 흩어지나?
- 14-I: 경계값(0원·음수·환불 후 재환불)에서 규칙이 유지되나?
- 14-V: 불변식을 직접 검증하는 테스트가 있나?

### 15 데이터 모델링
- 15-T: 스키마·관계·제약·인덱스를 만들거나 바꾸는가?
- 활성: 테이블/컬럼 추가·변경 · 마이그레이션 · unique/FK · 인덱스 | 경로: entity·migration·schema·ddl
- 비활성: 모델 불변의 조회·로직 변경
- stakes: 마이그레이션·기존 데이터 변경=높음(불가역) · 신규 모델 추가=중간
- 15-P: 데이터 주인은? 관계? 정규화/반정규화? 이력? 삭제 정책? (unique 제약 = 동시성 방어 첫 줄 — 5와 연동)
- 15-I: 제약이 DB에 있나, 코드에만 있나?
- 15-V: 마이그레이션 record-level 검증(core §6.3) — count·sample·orphan?

### 16 비용
- 16-T: 자원 소비 구조(서버·DB·외부 호출량·저장량)나 복잡도를 유의미하게 바꾸는가?
- 활성: 외부 유료 API · 캐시/인프라 추가 · 데이터 적재 증가 · 새 의존성 도입 | 경로: client·infra·build 파일
- 비활성: 자원 특성 불변의 로직 변경
- stakes: 활성=낮음↑ · 호출량·저장량이 단위 증가하면 중간
- 16-P: 더 싸고 단순한 대안은? 이 복잡도(학습·변경 비용 포함)를 감당할 가치가 있나?
- 16-V: 호출량·저장량 변화를 추정해 기록했나?

### 17 사용자/소비자 가시성
- 17-T: 사용자·API client·운영자가 보는 동작(응답·메시지·지연·상태 표시)이 바뀌는가?
- 활성: 응답 내용/형식 변경 · 처리 지연 증가 · 에러 메시지 · 알림 | 경로: controller·view·message·i18n
- 비활성: 가시 동작 동일이 증명되는 내부 변경
- stakes: 활성=낮음↑ · 신뢰 훼손 가능(중복 생성·오결과)이면 중간
- 17-P: 처리 중·성공·실패에 각각 무엇이 보이나? 메시지가 다음 행동을 알려주나?
- 17-V: 사용자 가시 동작을 실제로 확인했나(테스트 통과 말고)?

## 질문 보정 루프

- **부적합**(질문이 이 도메인에 안 맞음 / 어떤 질문도 못 잡는 실패모드 발견) ≠ **비활성**(트리아지의 정상 경로).
- 부적합 발견 → 대체/신규 질문을 사용자에게 제안 → 결정을 task.md "질문 보정 기록"에 `질문 ID / 사유 / 제안 / 결정`으로 기록. 정본은 그 자리에서 고치지 않는다.
- 정본 반영은 월 1회 측정 리뷰에서 승격 기준 통과분만: ① 서로 다른 작업 2회+ 재등장 ② 질문 공백이 실제 결함으로 연결.

### B1 멱등·재실행
- B1-T: 같은 잡이 두 번 돌면(스케줄 중복·수동 재실행) 결과가 달라지는가?

### B2 부분 실패
- B2-T: N건 처리 중 k건이 실패할 수 있는가?
- stakes: 활성=중간

- B2-V: 실패/스킵 건수가 성공 건수와 분리 집계되나? (core §6.3 데이터 특칙과 연결)

### B3 시간 의미론
- B3-T: 처리 결과가 실행 시각·윈도·순서에 의존하는가?
- stakes: 활성=중간
- B3-P: watermark·window 경계는? 늦게 도착한 데이터(late data)는? timezone·DST는?
- B3-V: 윈도 경계·재실행 시각 변화 케이스를 검증했나?

### B4 스키마 진화
- B4-T: 입력 데이터의 스키마가 내 통제 밖에서 바뀔 수 있는가?
- stakes: 활성=중간
- B4-P: 필드 추가/삭제/타입 변경 시 잡이 어떻게 반응하나 — 실패? 무시? 격리?
- B4-V: 예상 밖 스키마 입력 케이스가 있나?

### B5 데이터 품질·계보
- B5-T: 산출 데이터를 다른 시스템·사람이 신뢰하고 소비하는가?
- stakes: 활성=낮음↑ · 의사결정·정산에 쓰이면 중간↑
- B5-P: 품질 규칙(null·중복·범위)과 위반 시 격리(quarantine)는? 출처 추적(lineage) 필요?
- B5-V: count·sample 대조로 산출물을 검증했나?

### B6 보존·재처리 가능 기간

- B6-P: retention 정책은? 며칠 전 데이터까지 재처리 가능해야 하나?

# dimensions-infra.md — 인프라 확장팩

> 로딩: dimensions.md surface detector — IaC·배포 설정·네트워크·클라우드 리소스 변경일 때.
> 기본 14차원에 **추가** (특히 11 보안·10 운영은 기본 차원에서 이미 다룸). I행으로 덧붙인다.
> 인프라 변경은 기본적으로 blast radius가 크다 — 비활성 판정에 더 강한 증거를 요구한다.

### I1 네트워크 노출
- I1-T: 포트·보안 그룹·인그레스·공개 endpoint가 생기거나 바뀌는가?
- stakes: 활성=높음 (내부망 한정이 증명되면 중간)
- I1-P: 인터넷에 무엇이 새로 보이게 되나? 최소 노출인가?
- I1-V: 변경 후 실제 노출 면을 확인했나 (의도한 것만 열렸나)?

### I2 IAM·권한
- I2-T: 서비스 계정·역할·정책을 만들거나 바꾸는가?
- stakes: 활성=높음
- I2-P: 최소 권한인가? 와일드카드 권한은 없나? 누가 이 역할을 assume할 수 있나?
- I2-V: 필요 동작만 되고 그 외는 거부되는지 확인했나?

### I3 secrets 관리
- I3-T: secret·키·인증서를 만들거나 전달 경로를 바꾸는가?
- stakes: 활성=높음
- I3-P: 저장 위치(vault/manager)는? 코드·로그·상태 파일에 평문 노출은? 회전 경로는?

### I4 배포·롤백
- I4-T: 배포 방식·순서·대상이 바뀌는가?
- stakes: 활성=중간 · 무중단 요구·DB 마이그레이션 동반이면 높음
- I4-P: rollout 전략(canary·rolling)은? 롤백은 명령 하나로 되나? 마이그레이션과 코드 배포의 순서는?
- I4-V: 롤백을 실제로 한 번 해봤나?

### I5 용량·쿼터
- I5-T: 트래픽·인스턴스 수·스토리지가 쿼터·한도에 다가가는 변경인가?
- stakes: 활성=중간
- I5-P: autoscaling 경계는? rate limit·쿼터 초과 시 무엇이 죽나?

### I6 IaC 정합 (drift)
- I6-T: 코드 밖(콘솔·수동)에서 바뀔 수 있는 리소스를 다루는가?
- stakes: 활성=중간
- I6-P: 선언 상태와 실제 상태의 차이를 어떻게 감지하나? plan diff를 사람이 읽었나?
- I6-V: apply 전 plan에 의도 밖 변경이 없었나?

### I7 DR·백업
- I7-T: 데이터 저장소·리전 구성을 만들거나 바꾸는가?
- stakes: 활성=높음
- I7-P: 백업 주기·복구 절차·RTO/RPO는? 복구를 실제로 연습했나?

### I8 공급망
- I8-T: 새 이미지·패키지·외부 모듈을 도입하는가?
- stakes: 활성=중간
- I8-P: 출처·서명·버전 고정(pin)은? 베이스 이미지 갱신 경로는?
