# Lazy-busy 모드 설계 (plans.md)

> 작성: 2026-06-20. 상태: **설계안 — 사용자 검증 대기.**
> 목적: Claude가 자율주행해서 사용자에게 아무것도 안 남는 문제를, 하네스 레벨에서
> **매 단계 사용자의 이해를 주관식으로 검증하며 진행하도록** 강제해 해소한다.
> 이 문서는 "어떻게 설계하고 어떻게 만들지"의 단일 출처다. 구현 전 이 문서와 사용자 이해가
> 일치하는지부터 검증한다.
>
> ⚠️ **택소노미 개편(2026-06-21, 부분 supersede)**: 아래 §1 **두-레벨 모드(make-tools/implementation × implementation/lazymode)**는
> **단일 분기 `auto-implements` | `lazy-implements`**로 대체됐다(make-tools 제거). 상태도 프로젝트 단위 `lazymode-state`→
> **세션 단위 `.claude/lazymode/<session_id>`**. §2~§4의 게이트 기계(주관식·판정 워커·before/after)는 **그대로 유효**(이름만 lazymode→lazy-implements).
> 개편 단일 출처: `docs/plans/2026-06-21/mode-taxonomy-session-keying/`.

---

## 0. 핵심 원칙

1. **검증 없이는 다음 단계 없음.** 매 결정·매 코드에서 사용자가 *직접 설명*(주관식)해 이해를 증명해야 진행.
2. **강제는 훅, 판단은 문서.** 모드 선택은 훅으로 결정론적 강제. "이해했는가" 판정은 Claude가 문서 프로토콜로 수행(훅이 못 막음).
3. **토큰 비용은 의도된 비용.** 많이 써도 좋다. 강제하는 게 목적이다.
4. **단일 출처.** 하네스 전체를 복제하지 않는다. 바뀌는 건 **개발 단계(implementation)뿐**, 나머지(정의·dimensions·templates·hooks·orchestration·review·verification·git-workflow·open-source)는 그대로 재사용.

## 1. 모드 시스템 (2026-06-21 개편 — 단일 분기)

```
[정의됨 진입 = 구현·계획·설계 착수 (task.md 생성·코드 변경)]   ※ 개념 탐색·토론·학습은 자유
   │  (gate-guard가 task.md·산출물 변경을 막아 강제 선택 — 둘 중 하나, 태스크마다 재질문)
   ├─ auto-implements ──────► 앞단(정의·계획) 합의 후 자율 실행. per-diff 게이트 없음.
   │                          (검증·codex·테스트는 stakes 비례로 자율 수행)
   │
   └─ lazy-implements ──────► 풀 이해 게이트. 매 diff 주관식 검증. (이 문서의 핵심)
```

- **모드 선택**: `auto-implements` vs `lazy-implements` — **세션 시작이 아니라 정의됨 진입(구현·계획·설계 착수, task.md 생성 포함) 시** gate-guard가 막으며 선택(미선택 시 진입 불가). **개념 탐색·토론·학습은 자유.** session-mode-guard는 상태 초기화/복구만 하고 시작 때 묻지 않는다.
- **태스크 재질문**: 새 `task.md` 생성 시 task-mode-guard가 모드를 UNSET으로 리셋 → 태스크마다 다시 선택.
- `auto-implements` = 앞단 합의 후 자율 실행(현행 implementation 계승). **`lazy-implements` = 이해 게이트 모드(현행 lazymode 계승).** `make-tools`(완전 자율주행)는 **제거**(over-scoping 가드까지 끄는 철학 구멍).
- **상태 격리**: `.claude/lazymode/<session_id>`(MODE + PENDING_GATE) — 같은 폴더 동시 세션이 서로의 모드를 clobber하지 않음. reinject-mode(UserPromptSubmit)가 매 턴 모드·경로 재주입.

## 2. 게이트 형식 — 주관식 직접 작성 (2026-06-21 확정)

- 사용자가 **자기 말로 직접 작성**(주관식 서술)한다. **객관식 없음, 백스톱도 없음.**
- 판정 기준(루브릭, 상세 §4.2): 핵심 메커니즘·트레이드오프·"왜"를 짚으면 통과. 표면적·복창·틀린 설명이면 불통과.
- 불통과 시 재설명·재질문 — **변경별 최대 2회(x/2)**. **2회째도 불통과면 판정 워커가 틀린 부분을 짚어주고 통과 처리 → 다음 진행**(무한 차단 없음). 상세 §4.2.

## 3. lazymode 단계별 동작

### 3.1 정의 · 요구사항 명확화
- 명확도 6칸(목표·불변식·기준소스·금지영역·검증방법·stakes) + dimensions 트리아지 — **현행 그대로**.
- 추가: **요구사항을 제대로 정의하는 구간**을 task 문서에 명시적으로 적는다(모호하면 여기서 해소).

### 3.2 계획 (리서치 + 트레이드오프 선택) — ★ 재설계
- **task 문서에 계획을 디테일하게** 작성한다. 이를 위한 **리서치를 강제**한다(없는 계획·트레이드오프 금지):
  - 내부 리서치: 실제 코드·호출처 파악(실파일).
  - **외부 리서치(강제)**: 외부 사례·문서·함정을 찾아 ground — 낯선 영역·최신은 필수.
- **모든 계획 간 트레이드오프를 전수 열거**하고, 각 트레이드오프를 **사용자가 직접 선택**하게 한다(질의응답식 전체 피드백).
- 사용자가 트레이드오프를 고민해 **확정**해야 계획이 닫힌다.

### 3.3 계획 이해 게이트 (상호 정렬 · 무한 루프) — ★ 신규
> 이 게이트는 **한 방향 검증이 아니라 상호 정렬(mutual alignment)**이다. 두 가지를 동시에 본다:
> (a) 사용자가 계획을 제대로 이해했는가, (b) **Claude가 사용자의 의도를 제대로 캡처했는가**
> (Claude가 잘못 이해했을 수 있다 — 불일치 원인이 Claude일 수 있음).
```
계획 전체 확정(초안)
   │
   ▼
양방향 대조:
  · 사용자 → 전체 프로세스를 주관식으로 설명
  · Claude → 자기가 캡처한 의도·계획을 제시
   │
   ▼
서로 일치하는가?  (+ 추가 피드백 있나?)
   ├─ 일치 & 피드백 없음 ──────────► 개발 진입
   └─ 불일치 또는 추가 피드백 있음
        │   (원인 무관 — 사용자가 잘못 이해 / Claude가 잘못 캡처, 둘 다 동일 처리)
        ▼
      Claude가 계획을 **재정리** ──► (게이트 재실행, **최대 2회**)
```
- 불일치의 원인이 **누구든** 똑같이 처리한다: 계획을 재정리하고 게이트를 다시 돌린다.
- **상호 합의(일치 + 무피드백)에 도달해야만** 개발 진입.
- ★ **이 게이트는 작업 방향 전체가 걸려 stakes가 높다**: diff 게이트와 달리 2회 실패 시 *자동 진행하지 않는다*. 남은 간극을 정리해 **사용자에게 "그대로 진행 / 계속 정렬"을 묻는다**(어긋난 채 개발 시작하는 비용 방지).

### 3.4 개발 — 문제 발생 루프 — ★ 신규
구현 중 문제가 생기면:
```
문제 발생
  ├─ ① 문제를 서술한다
  ├─ ② 사용자가 그 문제를 이해했는지 확인(주관식)
  ├─ ③ 어떻게 해결할지 명시한다
  ├─ ④ "어떻게 해결한다고 했는지" 질문 → 사용자가 이해했는지 확인(주관식)
  ├─ ⑤ 진행(해결 시도)
  └─ ⑥ 해결됨? ── 예 ► 다음 진행
                 └ 아니오 ► ①~⑤ 재시도 (기술적 해결 루프)
```
- 이해 게이트(②·④)는 각 **최대 2회**(§4.2). 단 ⑥ "실제로 해결됐나"는 기술적 루프라 해결될 때까지 재시도(이해 cap과 별개).

### 3.5 개발 — diff 단위 게이트 (무조건) — ★ 신규 핵심
- **선행 강제**: 모든 수정의 **before/after 코드 스니펫을 작업 문서(plans/task)에 기록**한다. 이게 판정 워커의 **그라운드 트루스**(§4.2). 동시에 학습·복습 산출물이 된다.
- **diff 1개마다 무조건**:
```
diff 수정 적용  →  before/after 스니펫 문서에 기록
  ├─ ① 어떻게 수정되었는지 간단 설명(Claude)
  ├─ ② 주관식: 사용자가 "이 코드가 무엇인지/어떻게 수정됐는지" 직접 작성
  ├─ ③ **판정 워커(서브에이전트)**가 [사용자 답변 ↔ 실제 diff·문서 스니펫] 리뷰 → 메인은 verdict만 수신 (맥락 오염 차단, §4.2)
  └─ pass면 ► 다음 구현으로. (fail ► 재설명, **최대 2회**; 2회째도 fail이면 워커가 틀린 부분 지적 후 통과 처리·다음 진행 — §4.2)
```
- **테스트 코드도 동일**: 이 테스트 코드가 **무엇을 의미하는지/어떤 내용인지** 정확히 이해했다고 판정돼야 다음 구현으로 넘어간다(동일하게 2회 cap).

### 3.6 검증 — 테스트 게이트 — ★ 신규
- 검증 단계의 **테스트 코드 작성·수정·처리**도 **순차적으로 똑같이** 주관식으로 전부 확인한다(§3.5와 동일 패턴).

### 3.7 기록
- changelog·learned·OVERVIEW·TECHNICAL·review-log 등 **기록 산출물은 현행 그대로**.
- 순서 제약: **트레이드오프가 §3.2에서 제대로 정의·선택된 뒤에만** changelog/learned 작성.

## 4. 강제(훅) vs 판단(문서) 경계

> **핵심 분해: 게이트의 *발생*(occurrence)은 훅으로 강제 가능, 게이트의 *판정*(judgment)은 훅 불가.**
> 훅은 "게이트 없이 다음 diff로 못 감"을 기계적으로 막고(=스킵 차단), Claude는 "그 답이 진짜
> 이해인가"를 판정한다. 사용자가 진짜 두려워하는 실패모드(Claude가 그냥 지나쳐 자율주행)는
> **스킵 모드**이고, 그건 훅으로 완전히 죽일 수 있다 — 가치의 대부분이 여기서 나온다.

| 항목 | 수단 |
|---|---|
| 세션 모드 선택(make-tools/implementation) | **훅 강제** (세션 시작) |
| 태스크 서브모드 선택(implementation/lazymode) | **훅 강제** (태스크 진행마다) |
| **diff/단계 게이트의 *발생* 강제** — 직전 diff의 게이트(질문+사용자 답변)가 처리되기 전엔 다음 Edit/Write/테스트 차단 | **훅 강제** (PreToolUse/PostToolUse on Edit\|Write\|Bash) |
| 트레이드오프 정의 전 changelog 금지 | **훅 강제** |
| 질문 *내용* 생성 · "이해했는가" *판정* · 무한 루프 종료 | **문서 프로토콜** (Claude — 훅이 내용을 못 짓고 정답성을 못 가름) |

### 4.1 훅으로 되는 것 / 안 되는 것 (정직한 경계)
- ✅ 훅이 강제할 수 있다: **게이트가 *존재*하고 *막는다*** — 질문이 던져지고 *사람의 답변 턴*이 들어오기 전엔 다음 코드 변경 불가. ("스킵" 실패모드 박멸.)
- ⚠️ 훅이 못 한다: **그 답이 *맞았는지/이해했는지*.** 이건 환원 불가한 판정 — Claude(문서 프로토콜) + 사용자의 정직함에 남는다. 어떤 훅도 "정말 이해했나"를 기계화 못 한다.
- 결론: 게이트의 *발생*을 훅으로 박으면 핵심 가치의 ~90%를 가져가고, 판정 품질(~10%)만 사람/LLM에 남는다. 이게 §0.2(강제는 훅, 판단은 문서)의 정확한 적용이다.

### 4.2 판정 워커 (서브에이전트로 위임) — ★ 사용자 제안
판정(§4.1의 환원 불가한 부분)을 **메인이 직접 하지 않고 서브에이전트에 위임**한다.
- **이유 1 (맥락 보호)**: 채점 심의·사용자 오답·재설명 사이클이 메인 컨텍스트에 안 쌓인다. 긴 작업에서 diff마다 게이트가 도는데 그 잡음이 메인에 누적되면 판정 품질이 망가진다. 메인은 **verdict만** 받는다.
- **이유 2 (탈편향)**: 메인은 '빨리 진행하고 싶은' 관성이 있어 자기 설명을 러버스탬프할 위험(§7-6)이 있다. **신선한 워커는 관성이 없다** — 패킷과 판정 임무만 있다. → §7-6 러버스탬프 문제 완화.
- **패킷 계약 (절단선)**:
  - 입력: ① 방금 적용된 **실제 diff/코드(그라운드 트루스)** ② 게이트 질문 ③ 사용자의 주관식 답변 ④ 판정 루브릭(메커니즘·왜·효과를 짚었나 / 단순 복창은 불통과).
  - **금지**: 메인의 diff *해설*을 그라운드 트루스로 넘기지 않는다 — 사용자 답을 'Claude 말'과 대조하면 안 되고 **실제 코드와 대조**해야 한다.
  - 출력: `{pass | fail, 부족한 점 1~2줄}`.
- **클리어링**: 게이트는 **워커 verdict=pass**로 해제(+ §4.1 사용자 답변 턴으로 발생 보장). 메인 자기클리어보다 덜 러버스탬프적.
- **그라운드 트루스 소스**: §3.5에서 작업 문서에 강제 기록한 **before/after 스니펫** + 실제 코드 + 맥락. 워커는 이걸로 사용자 답을 리뷰한다(메인의 해설이 아니라 실제 코드·문서 기준).
- **시도 카운트(x/2)**: 워커가 변경별 시도를 `x/2`로 추적. **1회 fail** = 정답 비노출, 부족점만 주고 재질문. **2회째도 fail** = 틀린 부분을 명확히 지적하고 **게이트 통과 처리 → 다음 진행**(무한 차단 없음·데드락 방지).
- 이 워커는 하네스 기존 원칙(메인=관리감독, 독립 검증은 워커로 — orchestration playbook)의 자연스러운 적용이다.

## 5. 파일 / 구현 계획 (이 설계의 산출물)

- `playbooks/implementation-lazymode.md` — **lazymode 플레이북**(§3.2~3.6 게이트 절차). 신규.
- `playbooks/implementation.md` — 현행 유지(서브모드 `implementation`).
- 훅 3종 신규:

### 7-A. 태스크 경계 감지 — ✅ (b) 채택 (2026-06-21)
훅은 추상적 "태스크"가 아니라 **구체 이벤트**(세션시작·프롬프트제출·툴호출)에만 걸린다. 태스크 서브모드(implementation/lazymode) 훅이 *언제* 강제 선택을 띄울지 = "새 태스크 시작" 신호를 뭘로 잡나.
- (a) **명시적 선언**: 새 작업 시작 시 사용자가 선언(또는 슬래시커맨드). 단순·정확, 수동.
- (b) **정의 게이트 진입 감지(추천)**: 새 `docs/plans/<날짜>/<작업>/task.md` 생성(Write)을 훅이 잡아 모드 선택 강제. 결정론적·자동, 단 "정의 시점"에 물음.
- (c) (a)+(b) 혼합.
- 잘못 잡으면: 매 프롬프트마다 물으면 게이트 답변할 때도 모드를 또 물어 짜증. 그래서 "모든 프롬프트=새 태스크"는 탈락.
