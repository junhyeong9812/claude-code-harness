# 하네스 v2 프로세스 도해

> 2026-06-10 전면 개편(Phase 14) 결과의 실행 흐름을 그림으로 정리한 문서.
> 규칙 본문은 `core.md`가 단일 출처 — 이 문서는 **도해만** 담고, 충돌 시 core.md가 우선한다.

---

## 1. 전체 흐름 — 테스크 상태 모델

모드/라우팅 없음. 작업은 두 상태만 가진다.

```
                      사용자 입력
                          │
            ┌─────────────┴─────────────┐
            │ 산출물 변경 없음            │ 산출물 변경 있음
            │ (토론·학습·설계·분석)       │ (코드·설정·문서·스크립트·스키마)
            ▼                           ▼
      ┌──────────┐   정의 게이트   ┌──────────┐
      │ 탐색 중   │ ─────────────▶ │  정의됨   │
      │ 게이트 없음│  명확도 6칸     │ 파이프라인 │
      │ 자유 흐름 │  + 사용자 합의  │  진입     │
      └──────────┘                └──────────┘
            │                           │
            │ 결론이 구현 입력이 되면      ▼
            │ → 실코드 재확인        [정의]→[계획]→[개발]→[검증]→[기록]
            │ 고위험 결론(장기 설계·     ★합의   ★승인          (stakes 비례)
            │ 정책·불가역)이면
            │ → 확정 전 교차 검증 1회
```

- **긴급(장애)**: 게이트 왕복 압축, 단 최소 안전선은 생략 불가 + 산출물·측정 사후 소급.
- **세션 재개**: `docs/plans` 최신 작업 폴더의 task.md(다단계면 master-plan 승인 상태)부터 읽고 이어감.

## 2. 정의 게이트 — 명확도 6칸

```
┌─────────────────────────────────────────────────────┐
│  ① 목표·대상   어느 경로/모듈에서 무엇이 되면 끝인가     │
│  ② 경계·불변식  무엇이 항상 참이어야 하나               │
│                (버그=깨진 불변식 / 기능=새 경계 /       │
│                 리팩토링=보존할 동작)                   │
│  ③ 기준소스    무엇이 정답인가 (사용자 지정 최우선)      │
│  ④ 금지영역    건드리면 안 되는 곳                      │
│  ⑤ 검증 방법   무엇으로 완료를 증명하나                 │
│  ⑥ stakes     틀리면 얼마나 아픈가 → 검증 강도          │
└─────────────────────────────────────────────────────┘
   한 칸이라도 비면 = 아직 [탐색 중] → 변경 금지
   "일단 구현하면서 정하자" 금지 → AskUserQuestion으로 결정 수령
   중간↑ stakes의 ②칸: 실패 의미론/외부 경계/시간·동시성/보안·권한/관찰가능성 축 명시
```

## 3. stakes 판정 → 강도 분기

stakes = 손실 × 낯섦 × 모호성 × 불가역 ("변경 크기" 아님 — 인증 한 줄도 높음).

```
                        stakes 판정
        ┌──────────────────┼──────────────────────┐
        ▼                  ▼                      ▼
      낮음               중간                    높음
   blast 작음        데이터 의미 변경          불가역(삭제·마이그레이션)
   불변식 명확        동시성·재시도·부분실패     보안·권한·결제·tenant
   복구 쉬움          외부 API·queue·scheduler  public API/계약·낯섦·모호성
        │            config·query·timeout       │
        │                  │                    │
        ▼                  ▼                    ▼
 ┌─────────────┐   ┌─────────────────┐   ┌──────────────────────┐
 │검색  —       │   │검색  낯선 영역만  │   │검색  의무 (실패 시 분기)│
 │codex —       │   │codex 반드시 1회  │   │codex 계획+최종        │
 │테스트 셀프    │   │테스트설계 분리패스│   │테스트설계 별도 워커     │
 │리뷰  셀프체크 │   │리뷰  별도 패스   │   │리뷰 별도 워커+codex판정│
 │task.md 1파일 │   │task.md+페이즈 절 │   │definition + task.md   │
 │(자명→채팅대체)│   │                 │   │(다단계→master-plan+    │
 │              │   │                 │   │ phases/)              │
 └─────────────┘   └─────────────────┘   └──────────────────────┘
        └──────────────────┴──────────────────────┘
                           │
              머지 전 최소 안전선 (stakes 무관 항상):
              테스트 실행 □ diff self-review □ rollback 판단 □
              contract 영향 □ 반증 질문 1회 □
```

- **승격 트리거** (하위→상위): 테스트 설계 막힘 / 불변식 한 문장 설명 실패 / 변경 확산 / 새 경계 발견 / 같은 곳 2회+ 수정 / 모호성 미해소.
- **하한**: 위험 영역을 사용자가 낮게 지정하면 자동 하향 금지 — 충돌 보고 후 사용자 재확인.
- **다단계 판정**: "중간 검증을 통과시킬 수 있는 독립 변경 단위가 2개 이상인가?" → 예면 페이즈 분할.

## 4. 개발 절단 구조 — 메인 = 관리감독

```
                    메인 (오케스트레이터)
        소유: 정의·계획·사용자 합의·게이트 판정·최종 종합·learned
        ────────────────────────────────────────────
          │ 위임 (브리핑 5요소: 목표/배경/파악한 것/형식/범위제한)
          │ 워커 = 서브에이전트 (프롬프트에 준 것만 봄 = 구조적 격리)
          │
   ┌──────┼──────────┬───────────────┬─────────────────┐
   ▼      ▼          ▼               ▼                 ▼
 Explore  구현 워커   테스트설계 워커   리뷰 워커          codex (외부 LLM)
 대량탐색  (독립모듈)  입력: spec·정의만  입력: diff+spec    다른 모델 = 독립성
                     ★구현 diff       ★구현자와 분리      리뷰 findings 판정
                       미열람★        귀속 증명 의무      페르소나 다수결로
                          │               │              대체 불가
   └──────┴──────────────┴───────────────┴─────────────────┘
                          │ 결과는 요약 수신 + 1~2개 교차 확인
                          ▼
            메인이 근거 품질로 재평가 (투표 집계 아님)
```

- 구현 중 새 실패 경로 발견 → 구현자가 테스트에 직접 추가 금지(역산 오염) → 보고 → 메인이 spec 갱신 → 테스트설계 패스가 갱신 spec만 보고 추가.
- 렌즈(구 페르소나): 5~8개 질문 체크리스트를 워커 프롬프트에 인라인.
- 대규모 fan-out(find→adversarial verify→synthesize)은 Workflow 도구 — 사용자 opt-in.

## 5. 높은 stakes 다단계 — 페이즈 루프

```
master-plan.md (사용자 승인 단위: 전체 범위·페이즈 경계·의존성·acceptance)
   │
   ▼  페이즈마다 반복:
┌────────────────────────────────────────────────────────┐
│ spec.md 작성 (목표/변경파일/검증명령 + 테스트 설계)         │
│   → spec 고정: 문서 커밋(docs만)  ──── 구현 진입          │
│        │                                               │
│   [구현]  ∥  (테스트 설계는 이미 spec에 — diff 미열람 증빙) │
│        ▼                                               │
│ changes.md (실제 git diff 스니펫 — 학습 자료 겸용)         │
│        ▼                                               │
│ gate.md: 빌드/테스트 → 예외경로 → 플로우 디버깅            │
│          → 절단 확인 → 리뷰 → codex 독립검증 → 판정       │
│        ▼                                               │
│ 통과 → 그 페이즈 코드만 커밋 (diff 격리 = 오귀속 차단)      │
│ 실패 → 같은 페이즈 내 수정, 같은 접근 2회 실패 시 사용자 보고│
└────────────────────────────────────────────────────────┘
   │ 모든 페이즈 통과
   ▼
 전체 통합 acceptance → 최종 codex 검증 → 기록(master-plan 기록 절)
```

## 6. 검증 단계 상세 — "테스트 통과 ≠ 검증 완료"

```
[테스트]                     [플로우 디버깅 (중간↑)]          [데이터 특칙]
 회귀: stakes 비례            API: 실호출 추적                migration·write(높음):
  낮음=변경·호출 경로           성공 1 + 예외(잘못된 입력·       count 비교·실패/스킵 분리
  중간=+영향권                  권한·의존 실패) 각 1            100건+ sample·orphan
  높음=전체                   서비스 간: 느림/다운/이상 응답 시   read 의미 변경(중간↑):
 예외 경로 의무:               예외 발생 지점·전파 실측          before/after diff
  실패 의미론마다 1개          비동기: queue·scheduler·webhook   edge(null·중복·stale·tz)
                              재시도 중복·DLQ·순서·ack          권한별 결과
```

## 7. 문서 로딩 맵 — 무엇을 언제 읽나

```
상시 (매 세션):  CLAUDE.md(11줄) + core.md(~200줄)          ← 이게 전부
─────────────────────────────────────────────────────────
조건부 (트리거 시):
  중간↑ stakes 진입        → playbooks/orchestration.md (절단 계약)
  개발 단계                → playbooks/implementation.md (예외 일관성·범위)
  검증 단계                → playbooks/verification.md (플로우 디버깅·데이터)
  산출물 작성              → templates/task.md
  높은 stakes 정의         → templates/definition.md
  높은 stakes 다단계 계획   → templates/master-plan.md + phase.md
  학습 가치 트리거          → templates/learned.md (제품 산출물 — 풀 10항목)
  측정 파일 최초 생성       → templates/measurement-log.md
─────────────────────────────────────────────────────────
강제 (훅 — 문서 아님):
  git push / docs-only 커밋 → hooks/git-guard.sh (차단)
  docs+code 혼합 변경       → hooks/scope-guard.sh (경고)
```

## 8. v1 → v2 대비

```
                v1 (Opus, ~2026-06-09)            v2 (Fable 5, 2026-06-10~)
상시 선독        4문서 ~2,500줄 (~50k 토큰)         212줄 (CLAUDE 11 + core 201)
모드             발화 동사 라우팅 + 훅 상태머신       테스크 상태 (탐색↔정의됨)
게이트           8개 (B2·B2.5·B3·X4-T·X4.5·…)      2개 합의 게이트 + 최소 안전선
codex           작업당 6~10회 균일 의무             stakes 트리거 (0/1/계획+최종)
산출물           research·plan·context·checklist·   task.md 1파일 기본
                learned·definition (+페이즈 6파일)   (높음 다단계만 master+3파일)
절단 집행        산문 규칙 자기 집행 (드리프트 실측)   서브에이전트 구조적 격리 + Workflow
페르소나         라이브러리 2,444줄 상시 보관         렌즈 질문 5~8개 프롬프트 인라인
learned         규모 기준 (소규모 5줄)              학습 가치 기준 (제품 산출물)
훅              5종 (상태머신·로더 포함)             2종 (git-guard·scope-guard)
규칙 증감 근거    사건 발생 → 절 추가                measurement-log 데이터
```
