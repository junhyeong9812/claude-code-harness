## 0. 이 문서의 목적

본 문서는 사용자가 명시적으로 요청한 **본인 LLM 사용 능력에 대한 객관적(가능한 한) 평가** 의 결과물이다.

## 3. 질문/요청 스타일

### 3.1 길이 분포 (text-search 프로젝트 563건 기준)
| 구간 | 비중 |
|------|------|
| < 30자 | 31.8% |
| 30 ~ 100자 | 34.6% |
| 100 ~ 300자 | 17.6% |
| 300자+ | 16.0% |

**해석**: 짧고 빠른 결정/지시 위주. 의도 전달 속도 우선, 정확성은 후속 턴에서 보완.

### 3.2 빈출 패턴
- **선택지 파싱형** `1. a 2. b 3. c 진행하자` — 681회
- **빠른 루프** "진행하자" 237회 / "처리하자" 321회 / "부탁해" 176회
- **컨텍스트 부착형 paste** — 코드/로그/ES 매핑/SSH 출력을 통째로 붙이고 1~2줄 질문. 코드로 시작하는 줄 1,704회.
- **타이핑 질** — 오탈자/구어체 다수 ("운서화", "그케", "꺼 같아", "ㅔㅌ스트")

### 3.3 좋은 예시 (의역)
- "EU 검색에서 `_build_similar_search_queries`가 다른 4개국엔 없어. 한국 패턴대로 통일해서 만들어줘. boost 3000 기준."
  → 목표·제약·수치까지 포함된 좋은 요청

### 3.4 개선 여지가 큰 예시
- "그케해줘" / "ㅔㅌ스트 통과했어"
  → 모델이 의도 추정 1턴 들어감. 정확한 한 단어 추가의 비용은 0이지만 추정 오류 비용은 큼.

## 8. 강점 신호 (구체 사례)

1. **도메인 지식 깊이**
   - g2p 룰셋의 ää/öö 분할, ES n-gram 2~30 → 2~10 축소, terms vs should.term 분기를 본인이 설계
   - 모델이 잘못된 인덱스 버전 보면 즉시 잡음 ("이거 v1 바라보고 있어?", "9203개 차이 어디서 왔어?")

2. **운영 감각**
   - docker-compose 포트 충돌, ES heap·shard, mariadb 버전을 동시 트래킹
   - "야매로 할 생각하지 말라고"로 임시 처리 차단

3. **메타인지 + 시스템화** ⭐
   - 오케스트레이션 체계(라우터+구현/토론/에이전트), 산출물 4종 강제, `/effort max` 습관화
   - **상위 1~3% 영역**

4. **문서/커밋 위생**
   - docs 커밋 분리, "feat(scope):" 컨벤션, Claude 푸터 제거 명시

5. **사람-LLM 분담 인식**
   - "1번은 에이전트로 진행하고 2번은 나랑 대화" — 위임/직접 명시 분리

6. **본질 통찰**
   - LLM의 "다수결 편향" → "사람의 사전 가이드가 더 최적" — TDAD 논문이 학술적으로 뒷받침하는 결론을 스스로 도달

## 9. 약점 / 마찰 신호

### 9.1 입력 정확도
- 오탈자/짧은 한 문장 → 모델 의도 추정 1턴 추가 → 누적 reset 비용
- 예: "ㅔㅌ스트 통과", "운서화" 등

### 9.2 컨텍스트 외부화 부족
- 매 세션 "어제 한 일 기억해?"로 시작 → 모델이 매번 추측·재구성
- 4월 말에야 plan.md 외부화 학습

### 9.3 시스템 가드레일 부재 ⚠️ **(가장 큰 약점)**
- `master에 push 하지 마`, `docs는 push 하지 마`, `야매로 하지 마` 를 30일 동안 자연어로 매번 잡음
- 같은 실수 반복 — 시스템(훅/permissions/pre-commit)으로 막으면 영구 해결인데 안 막고 있음

### 9.4 선택지 의존 — "4번 옵션의 부재"
- `1.a 2.b 3.c` 패턴은 빠르지만 모델이 못 떠올린 4번 옵션은 영영 사라짐
- "더 나은 4번 없어?"를 거의 안 묻는다 → 사각지대

### 9.5 검증 비대칭 — 순환 검증 위험
- 운영 서버 결과는 즉시 SSH/DB로 교차검증 ✅
- 새 알고리즘 (g2p 룰): "200개 코퍼스에서 90% 통과" 모델 보고를 그대로 수용 ⚠️
- 테스트셋도 같은 모델이 만들었기에 자기 채점 위험

### 9.6 인프라 작업 위험 노출
- `master에 push`, `docs commit` 사고를 사후 잡음
- 권한·브랜치 정책을 LLM 흐름에 가두지 못한 시기 길었음

## 10. 종합 평가

LLM-사용자 스펙트럼에서 **상위 약 5~10%**.

### 10.1 평균 코더보다 두세 단계 위인 이유
1. **위임 범위가 넓다** — 운영·문서·아키텍처·자기 성찰까지 통합
2. **도구 체계를 직접 설계한다** — 도구 소비자가 아닌 제작자 사고
3. **모델을 검증 가능한 방식으로 부린다** — SSH·DB·UI 교차 확인

### 10.2 상위 1%로 가지 못하게 막는 한계
- 요청 표면(타이핑·짧은 문장)에 비해 요구 깊이가 큼 → 매번 1~2턴 reset 비용
- 모델 옵션 메뉴 밖으로 잘 안 나감 → 사각지대 존재
- 같은 실수를 시스템(훅·permissions·pre-commit)으로 잠그기보다 자연어로 잡음 → 마찰 누적
- 도메인은 좁고 깊지만, 횡적 검증을 모델 답변에 의존

### 10.3 한 줄 평가
> **"본인이 직접 LLM 사용 프레임워크를 설계할 만큼 메타인지가 살아 있는 진지한 실무자.
> 그러나 그 프레임워크의 보이지 않는 입력 정확도(프롬프트 위생, 컨텍스트 외부화, 시스템 가드레일)에
> 같은 강도의 투자가 들어가면 한 단계 더 갈 수 있는 위치."**
