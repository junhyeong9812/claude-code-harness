# playbook: 구현 — lazymode

> 트리거: 자율성 모드 = **lazy** 선택 시 (core v4 §1 — gate-guard 훅).
> 목적: **자율주행 금지** — 매 결정·매 diff에서 사용자 이해를 주관식으로 검증하며 진행한다.
> 설계 근거: v3 재설계 `docs/plans/2026-07-19/harness-v3-restructure/`. 토큰 비용은 **의도된 비용**.

## 0. 모드 진입 (훅 강제)

- **L1 진입 시 훅이 명세 합의(SPEC) 후 자율성 2택**(auto · lazy)을 강제 선택시킨다(gate-guard가 SPEC=0/MODE=UNSET 의 L1 변경을 차단). 작업 폴더마다 재질문. **L0(대화·리서치·설계)은 자유 — 이때 묻지 않음.**
- `auto` = 앞단(정의·계획) 합의 후 자율 실행(per-diff 게이트 없음). **`lazy` = 이 플레이북**(매 diff 이해 게이트).
- lazy 모드면 **이 플레이북이 §2~§6 게이트를 지배**한다. 인터뷰·명세·검증·리뷰 규칙은 core v4 **현행 그대로**(단일 출처 — 복제 금지).

## 1. 게이트 형식 (공통)

- 사용자가 **주관식 직접 작성**한다. 객관식·백스톱 없음.
- 판정은 **독립 서브에이전트 워커**(§4)가 한다. 메인은 verdict만 받는다.
- 변경별 **최대 2회(x/2)**. 2회째도 fail이면 워커가 **틀린 부분을 지적하고 통과 처리 → 다음 진행**(무한 차단 없음).

## 2. 계획 게이트 (개발 진입 전)

- **리서치 강제(필수)**: 계획 전에 **내부 코드 리서치(실파일) + 외부 리서치(웹 — 낯선 영역·최신·함정)**를 수행해 requirement-spec.md에 근거를 남긴다. 리서치 없는 트레이드오프·계획 금지.
- requirement-spec.md에 **디테일 계획 + (위) 리서치 + 트레이드오프 전수 열거** → 사용자가 각 트레이드오프를 **직접 선택·확정**.
- **계획 이해 게이트(상호 정렬)**: 사용자 주관식 설명 ↔ Claude가 캡처한 의도를 대조. 불일치/추가 피드백이면 **원인 무관**(사용자 오해/Claude 오해 동일) 계획을 재정리 → 게이트 재실행(최대 2회).
- ★ 작업 방향 전체가 걸려 stakes가 높다: **2회 실패 시 자동 진행 금지** → 남은 간극을 정리해 **사용자에게 "진행 / 계속 정렬"을 질의**.

## 3. 개발 게이트

### 3.1 diff 단위 (무조건)
- **선행 강제**: 모든 수정의 **before/after 스니펫을 작업 문서에 기록** — 워커의 그라운드 트루스이자 복습 산출물.
- 흐름: diff 적용 → ① Claude 간단 설명 → ② 사용자 주관식("이 코드가 무엇/어떻게 수정됐나") → ③ 워커 판정 → **pass면 다음**, fail은 최대 2회(§1).
- **테스트 코드도 동일**: 그 테스트가 무엇을 의미하는지 이해됐다고 판정돼야 다음 구현으로.

### 3.2 문제 발생 시
- ① 문제 서술 → ② 사용자 이해 확인(주관식) → ③ 해결법 명시 → ④ 해결법 이해 확인(주관식) → ⑤ 진행 → ⑥ 해결 여부.
- 이해 게이트 ②·④는 각 **최대 2회**. ⑥ "실제로 해결됐나"는 기술적 루프라 해결될 때까지 재시도(이해 cap과 별개).

## 4. 판정 워커 (서브에이전트) ★

- **위임 이유**: ① 맥락 보호(채점·오답·재설명 잡음이 메인에 안 쌓임) ② 탈편향(신선 워커는 "빨리 진행" 관성이 없어 러버스탬프 덜함).
- **패킷 입력**: 실제 diff/코드 + 문서 before/after 스니펫(그라운드 트루스) + 게이트 질문 + 사용자 답변 + 루브릭.
  - **금지**: 메인의 *해설*을 그라운드 트루스로 넘기지 않는다 — 사용자 답을 **실제 코드와 대조**(Claude 말과 대조 금지).
- **루브릭**: 메커니즘·왜·효과를 짚으면 pass. 복창·표면적·틀림은 fail.
- **시도 x/2**: 1회 fail = 정답 비노출, 부족점만 주고 재질문. 2회 fail = 틀린 부분 지적 후 통과 처리.
- **출력**: `{pass | fail, 부족점 1~2줄}`. 메인은 이것만 수신해 다음 행동 결정.

## 5. 강제 경계 (훅 vs 판단)

- **훅 강제(발생)**: 모드 선택 + 게이트 발생 — 직전 diff 게이트(질문→사용자 답변)가 처리되기 전 다음 Edit/Write/테스트 **차단**. 상태: `.claude/lazymode/<session_id>`(MODE + `PENDING_GATE`, 세션 단위 — 통과 시 `set-state.sh gate-pass`).
- **문서/워커(판정)**: 질문 생성·이해 판정·루프 종료는 훅이 못 한다. 훅은 *발생*까지, **정답성은 워커 + 사용자 정직함**에 남는다(환원 불가).

## 6. 검증·기록

- 검증의 **테스트 작성·수정·처리도 §3.1과 동일** 주관식 게이트(순차 전부 확인).
- 기록은 core §7 — **log.md 완료 요약**(diff before/after 스니펫 포함) + 리뷰 ledger(中↑) — 단 트레이드오프 정의(§2)가 끝난 뒤에만 작성.
