# playbook: 구현

> 트리거: 파이프라인 개발 단계(core §3.3) 진입 시.

## 0. 설계 (코드 작성 전) ★

- **렌즈는 설계의 입력이다**: `playbooks/review.md` §3 렌즈(API 예외 전파 · 메서드 내부 알고리즘/자원·속도 · 네이밍 · ORM 쿼리/실행계획 · 완전성·운영성[diff에 *없는 것* — 빠진 CRUD/복구 경로·필터가 admin 가두나] · 통합·부작용[이 변경 밖 — 공유자원 무단 덮어쓰기·소스전환 단절] · 설계 품질·취향[응집·경계·이름·냄새 — 카탈로그 `design-taste.md`])를 고려한 설계가 올바른 설계다 — 리뷰 대비용 사전 작업이 아니라 설계의 본질이고, 리뷰는 같은 기준으로 그 결과를 확인하는 절차다. 기준 본체는 review.md 단일 출처.
- **설계 자문 6질문** (구현 착수 전 자답, task.md에 1~3줄 기록):
  ① 함수/메서드명이 도메인을 직관적으로 드러내나 ② 이 구조가 테스트하기 쉬운가 (의존 주입·경계 분리·결정론) ③ 이 로직의 주인은 누구인가 — 도메인 경계가 올바른 모듈에 놓였나 ④ 더 나은 설계 대안이 있나 — 1회 자문하고 채택/기각 사유를 남긴다 ⑤ **이 설계로 바로 구현을 시작할 수 있을 만큼 명확한가** — 모호한 부분이 남았으면 구현이 아니라 정의/계획으로 되돌린다 (승격 트리거, core §4.1) ⑥ 이 구조가 슬롭/오버킬이거나 이름붙은 코드냄새가 있나 — `design-taste.md`로 자가심판, 단정 가능한 것만.
- **높음 stakes — 설계 codex 검증 (구현 착수 전 의무)**: 구현하려는 **구조 자체**가 리뷰 대상이다 — 설계 메모(함수 시그니처·도메인 경계·예외 전략·쿼리 접근·자원/속도 가정)를 codex로 1회 검증 후 구현 진입 (보안 스캔·호출 수단은 core §5). 계획 검토와 별개 시점이다 — 계획 검토 = "무엇을 바꾸나", 설계 검증 = "어떻게 바꾸나".

## 1. 읽기 규칙

- 수정할 파일은 수정 지점 주변이 아니라 **전체**를 읽고 맥락 파악 후 수정한다.
- 호출되는 함수를 수정하면 **호출하는 쪽도 실제로 읽어** 영향 범위를 확인한다.
- 컨텍스트가 요약됐거나 불확실하면 다시 읽는다 — "아까 읽었으니 기억난다" 금지.

## 2. 범위 통제

- Edit/Write 전에 해당 파일이 계획의 "변경 파일" 목록에 있는지 대조한다.
- 목록 밖 파일을 수정해야 하면 **즉시 멈추고 보고** — 승인 후 진행.
- 계획에 없는 "개선"·리팩토링·포매팅 변경 금지. 금지영역(정의 칸 4)은 어떤 이유로든 불가.
- 한 번에 하나의 의도만 변경 — "하나"는 빌드/테스트 가능한 단위(컴파일 안 되는 원자 단위까지 쪼개지 않는다). 다음 변경 전 최소 1회 검증.

## 3. 예외처리 일관성 ★

- **기존 예외 전략이 기준소스다**: 구현 전에 대상 프로젝트의 예외 계층·전파 방식·에러 응답 포맷을 파악하고 따른다. 새 예외 체계를 발명하지 않는다 (변경하려면 별도 작업으로 분리).
- **같은 실패 유형 = 같은 처리 패턴**: 한 기능 안에서 검증 실패·미존재·권한·외부 장애의 처리가 제각각이면 안 된다.
- **무음 실패 금지**: catch 후 삼키지 않는다. 로깅 없이 기본값 반환 금지 — 실패는 정의 칸2와 활성 차원(#6 예외·#9 장애복구)의 P 답에 적은 실패 의미론대로 드러나야 한다.
- **에러 응답에 내부 정보 금지**: 스택 트레이스·내부 경로·쿼리를 사용자에게 노출하지 않는다. 로그에는 남기되 민감 정보는 제외.
- **예외 시 상태 보존**: 정의 칸2·활성 차원 P 답의 실패 의미론을 코드 경계로 구현한다 — 트랜잭션 경계 · partial success 정책 · 재시도 idempotency · "외부 호출 후 내부 저장 실패 / 내부 저장 후 외부 호출 실패" 순서 · 보상 불가 시 사용자에게 드러나는 상태.
- **구현 중 새 실패 경로 발견 시**: 구현자가 테스트 설계에 직접 써넣지 않는다(구현 diff 역산 오염). 멈추고 "정의/불변식 누락"으로 보고 → 메인이 정의·spec 갱신 → 테스트 설계 패스가 **갱신된 spec만 보고** 케이스 추가 → 재개.

## 4. 페이즈 규율 (중간↑ stakes)

- 페이즈 종료 = 검증 명령 통과 + **그 페이즈의 변경 파일 집합만 커밋** — 집합의 기준은 계획(task.md 페이즈 절 또는 spec.md)에 명시한 변경 파일 목록이다. phases/ 폴더가 없는 중간 stakes도 동일하게 적용 (diff 격리 — 리뷰 오귀속 차단).
- **커밋 분리**: spec 고정 시점 커밋 = 문서(spec.md)만 / 게이트 통과 커밋 = 그 페이즈 코드만 — docs·code 혼합 금지(core §6.4)와 충돌하지 않게 두 커밋을 나눈다.
- 페이즈 중간에 다른 페이즈 파일을 건드리게 되면 멈추고 계획을 갱신한다.

## 5. 주석

- 구현 중에는 코드 작성에 집중, 주석은 테스트 통과 후. "무엇"이 아니라 **"왜"**를 설명하는 주석만.
- 검증 출처 주석 금지(core §6.4) — "codex 지적"·"리뷰 반영" 류는 주석이 아니라 review-log.md에.
- 포팅·이관에서는 원본 주석·엔티티를 보존한다 (삭제는 명시 요청 시만 — core §6.2).

## 6. 리팩토링 규율 (계획된 리팩토링을 *할 때* — *언제 안 하나*는 §2)

- **동작 보존이 불변식**: 외부 관찰 가능한 행위를 바꾸지 않는다 — 행위가 바뀌면 리팩토링이 아니라 기능 변경(분리한다).
- **그린 테스트 전제**: 리팩토링 전 관련 테스트 통과를 확인 → 작은 단계로 변경 → 매 단계 재실행해 그린 유지. 안전망(테스트)이 없으면 characterization test부터 깔고 시작.
- **한 번에 하나·커밋 분리**: 한 리팩토링씩, 기능 변경과 같은 커밋에 섞지 않는다(§4 연계 — refactor 커밋 따로). (test-first는 도입 안 함 — 테스트 설계 절단선 §5·verification이 대신한다.)
