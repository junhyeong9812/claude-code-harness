# playbook: 프로세스·엔티티 맵 (JIT 프로젝트 구조 캐시)

> 트리거: **L1(구현) 진입 시** 대상 프로젝트에 `docs/process-map.md` 부재 → 생성. **기록 단계(§3.5)**에서 이번 작업이 맵 노드를 바꿨으면 → 갱신. L0(대화·리서치)에서는 만들지 않는다.
> 목적: "규칙·메모리를 알면서도 재위반"(recall 실패)을 **recall이 아니라 작업 맥락의 구조로** 보완한다. 메모리는 얇게 두고([[memory-thin-jit-graph-direction]]), 프로젝트 이해를 그때그때(JIT) 그린다. **훅 강제 없음 — 절차 규칙**(Opus 쓰기는 훅이 관찰 불가, core §0.6).

## 1. 무엇을 그리나 (docs/process-map.md — 프로젝트당 1파일)

세 가지만. 장식·전수 목록 금지 — **작업에 실제로 필요한 구조**만.

1. **프로세스 흐름**: 주요 실행 경로 — 진입점 → 핵심 단계 → 산출. (요청·잡·마이그레이션 등 이 프로젝트의 핵심 플로우 1~3개)
2. **엔티티·의존 그래프**: 핵심 모듈/객체와 **방향성 의존**(A→B = A가 B에 의존). mermaid `graph`.
3. **경계 객체의 역할**: 마지막 단(외부 계약·DB·큐·API)이 무엇을 보장/책임지나 — 한 줄씩.

> 스키마·상세 형식은 `templates/process-map.md`. 코드 인용은 실파일 복사(core §3.5 인용 규칙).

## 2. 생성 (부재 시 — L1 진입 직후, 정의 게이트와 병행 가능)

- **Opus 서브에이전트에 위임**(메인 아님 — 대량 코드베이스 탐색 = §5 워커 원칙). 브리핑 5요소 + "경로를 주고 실파일을 읽게 하라".
- 워커 산출 = 위 3항의 초안. 메인은 핵심 1~2개 교차 확인(러버스탬프 금지) 후 `docs/process-map.md`로 커밋.
- **사용자와 대화로 좁힌다**: 의존 방향·경계 책임이 애매하면 단정 말고 open question으로 남기고 물어본다. 전수 완벽보다 **작업에 걸린 부분 우선**.
- 부재라고 무조건 그리진 않는다 — 이번 작업이 그 구조를 실제로 건드릴 때만(자명·격리된 변경은 skip 가능, task-process에 "맵 생략(사유)" 1줄).

## 3. 갱신 (기록 단계 §3.5 — 이번 작업이 맵을 stale하게 만들었으면)

- 판정: 이번 diff가 **새 모듈/의존/경계**를 추가했거나 **프로세스 흐름을 바꿨나**. 그렇다면 그 노드만 갱신(전체 재작성 X).
- **Opus 서브에이전트에 위임** — 변경분을 실파일에서 재확인해 반영(메인 기억으로 전달 금지). 변경 없으면 갱신 없음.
- 갱신 diff는 해당 작업 커밋과 분리(docs 커밋) — 코드 커밋에 섞지 않는다(§6.4 scope-guard).

## 4. 경계 (과설계 방지 — 이 playbook의 헌법)

- **훅으로 강제하지 않는다.** 그리는 걸 잊어도 훅이 막지 않는다 — 절차 규칙이다. 강제하려다 무거워지면 취지(얇게)에 반한다.
- **계약(C-표) 만들지 않는다.** 이 3항 스키마가 전부. 상태·검증·enum 추가 금지.
- **전수 문서화 아님.** 프로젝트 전체를 그리려 들면 stale·비용 폭발. 작업에 필요한 서브그래프만.
- MCP(claude-workbench) 승격은 유용성·규모 증명 후(별도 — second-system 회피).
