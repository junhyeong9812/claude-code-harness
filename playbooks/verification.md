# playbook: 검증

> 트리거: 파이프라인 검증 단계(core §3.4) 진입 시. 원칙: **"테스트 통과" ≠ "검증 완료"** — 정적 테스트가 못 보는 것(실행 플로우·서비스 경계·데이터 의미)을 stakes에 맞게 직접 확인한다.

## 1. 테스트

- **회귀 범위는 stakes 비례**: 낮음 = 변경 파일·호출 경로의 기존 테스트(최소 안전선과 동일) / 중간 = + 변경이 닿는 모듈의 영향권 회귀 / 높음 = 전체 회귀(또는 master-plan에 명시한 회귀 범위). 그 다음 신규 테스트.
- **예외 경로 의무**: happy-path만으로 통과 처리 금지. 정의(칸 2)의 실패 의미론마다 그 경로를 재현하는 테스트 최소 1개 — 테스트가 실패모드를 재현하는지, happy-path를 따라갔는지 자문한다 (최소 안전선의 반증 질문).
- 실패 시: 에러 메시지를 **실제로 읽고** 원인 파악 → 수정 → 재실행. 같은 접근 2회 실패면 3번째 전에 사용자 확인 (core §3.4).

## 2. 플로우 디버깅 (중간↑ stakes) ★

> 실행체: verify/run 스킬(Claude Code 내장) — 앱을 실제로 띄워 관찰한다. 스킬이 없거나 실행 불가면 **수동 실행(로컬 기동·curl·로그 추적)으로 같은 항목을 확인** — 환경상 불가하면 사유 기록 + 사용자 보고.

- **API 작업**: 변경된 엔드포인트를 **실제 호출**로 추적한다 — 성공 경로 1회 + 예외 경로(잘못된 입력·권한 없음·의존 실패) 각 1회. 응답 코드·바디·로그로 코드 플로우가 의도와 일치하는지 확인.
- **서비스 간 경계**: 의존 서비스가 느릴 때 / 죽었을 때 / 이상 응답일 때 **예외가 어디서 발생하고 어떻게 전파되는지** 직접 확인한다 — 타임아웃 동작·재시도(중복 부작용?)·에러 변환·부분 실패 시 상태.
- **비동기·백그라운드 경로**: queue consumer·scheduler·webhook 수신·background job은 API 호출로 관찰되지 않는다 — trigger 입력 주입, 재시도와 중복 처리(idempotency), 실패 전파(DLQ·보류 상태), 순서·ack 동작을 직접 확인.
- 목적은 망라가 아니라 **예외 발생 지점의 실측**: 정의에서 적은 실패 의미론이 런타임에서 실제로 그렇게 동작하는가.
- 확인 결과는 gate.md(페이즈) 또는 task.md §4에 기록 — "무엇을 호출했고 무엇을 관찰했나".

## 3. 데이터 특칙 — "에러 없이 돌았다" ≠ 완료

- **마이그레이션·write** (stakes 높음 고정): source/target count 비교 · 실패/스킵/중복 분리 보고 · 100건+ field-by-field sample · orphan/mislink count · 검증 쿼리를 기록에 남김.
- **조회 의미 변경** (read·query·report — 중간↑): before/after 결과 diff · edge sample(null·중복·stale·timezone) · 권한별 결과 확인.

## 4. 독립 검증 배선 (core §5 매핑의 실행)

- 리뷰·codex는 절단 계약(playbooks/orchestration.md §4)대로 — 구현자와 분리, 귀속 증명, stakes별 강도.
- 검증에서 발견된 결함·오탐은 measurement-log 해당 열에 기입 (어느 게이트가 잡았는지 명시).
