# playbook: pair-coding (2축 매트릭스 밖 5번째 모드)

> 트리거: 작업 모드 = **pair** (task-mode-guard·gate-guard 훅). auto/lazy-implements·auto/lazy-write 4종과 독립.
> 목적: 실제 페어 프로그래밍처럼 **순수 대화로 요구사항·설계를 사용자 스스로 도달**하게 하고, 로직 구현은 사용자가 직접 타이핑, Claude는 **네비게이터+리뷰어**(테스트/보일러플레이트 작성 + 핑퐁 리뷰)로만 개입한다.
> 단일 출처: `docs/plans/2026-07-06/pair-coding-mode/`.

## 0. 이 모드가 아닌 것

- `lazy-implements`(diff마다 이해 게이트)도, `*-write`(Claude가 먼저 구현 후 롤백+필사)도 아니다 — 여기선 **Claude가 로직을 먼저 완성한 적이 없다**. 설계·구현이 처음부터 대화 속에서 발생한다.
- 가이드형 객관식 선제시 금지. 6칸이든 설계 대안이든, 먼저 구조화된 질문지를 던지지 않는다 — 대화가 자연히 흘러가게 두고, 빠진 부분만 그 타이밍에 자연스러운 질문으로 끼워 넣는다.

## 1. 정의 게이트 (대화형 — task.md §1 라이브 append)

- `task.md`(높은 stakes는 `definition.md`)의 6칸(목표·대상/경계·불변식/기준소스/금지영역/검증방법/stakes)을 **처음부터 6행으로 열어두고**, 대화에서 그 내용이 나올 때마다 **순서 무관하게 해당 행에 append**한다.
- Claude는 6칸을 내부 체크리스트로 계속 추적한다 — 대화가 자연히 다루지 않는 칸이 있으면, 그 타이밍에 대화 흐름 안에서만 묻는다(예: 기능 얘기만 계속되면 "건드리면 안 되는 부분 있어요?"를 자연스럽게 삽입). 일괄 질문지·객관식 선제시 금지(§0).
- 대화가 수렴됐다 싶으면 6칸 정리본을 사용자에게 보여주고 **확인/수정**을 받는다 — 사후 문서화이되 되비추는 절차는 생략하지 않는다(조용한 누락 방지).
- 확인되면 정의됨 진입. 이후 §2·§3 진행.

## 2. 설계 대화

- 사용자가 설계안을 먼저 제시한다. Claude는 판정하거나 대신 설계하지 않고, **사용자 의도를 되짚어 말해주거나** 더 나은 대안이 있으면 근거와 함께 제안해 **사용자가 한 번 더 곱씹게** 한다.
- 최종 설계 결정은 사용자 몫이다. Claude의 역할은 반영(mirror)·제안이지 확정이 아니다.

## 3. TDD 사이클 (테스트 케이스 1개 = 사이클 경계)

각 요구사항 기반 엣지케이스마다 아래를 반복한다(코드 구조상 엣지케이스가 아니라 **요구사항이 요구하는** 엣지케이스만 — 도메인 이해가 사이클의 입력):

1. **Claude**: 테스트 스켈레톤/보일러플레이트를 실제 테스트 파일에 Edit/Write(gate-guard가 `is_test_file()` 패턴에만 허용). 핵심 검증부(assert)는 예시(§5 참조)처럼 **비워두고** 사용자가 채우게 한다.
2. **사용자**: 로직 구현 + 비워둔 assert를 직접 타이핑한다. gate-guard가 로직 파일에 대한 Claude의 Edit/Write를 PreToolUse에서 항상 차단한다(§4) — Claude는 코드를 대신 쓰지 않는다.
3. **Claude 리뷰**: §5 핑퐁 스타일로 판정 — 맞으면 근거와 함께 확인, 틀리면 **어디가 왜 틀렸는지 구체적으로** 짚어준다(추상적 지적 금지).
4. 테스트가 통과하고 리뷰도 끝나면 그 사이클 종료 — 다음 테스트 케이스로. 이미 실제 테스트 파일에 작성돼 있었으므로 별도 "반영" 단계는 없다.

## 4. 훅 강제 경계 (결정론적 파일 패턴 — Edit/Write/MultiEdit 한정)

- gate-guard는 `is_test_file()`(테스트 파일 컨벤션: `*Test.java`·`*.test.ts`·`test_*.py`·`src/test/**`·`tests/**` 등 — 정본은 `hooks/gate-guard.sh`, 여기 복제하지 않음)에 매칭되는 파일 + 기존 `docs/plans/**`·상태파일 면제(§1의 task.md 라이브 append에 필요)는 Claude의 Edit/Write를 허용한다. 그 외 로직 파일은 **Edit/Write/MultiEdit**을 PreToolUse에서 항상 차단한다.
- 이건 **의미론적 "보일러플레이트 vs 로직" 판단이 아니라 파일 경로 패턴 판단**이다(core §0.6 — 강제는 훅, 판단은 문서). 컨벤션에 안 맞는 프로젝트(관례 없는 언어·구조)는 오탐 가능 — 그런 경우 §0.6대로 훅을 확장하지 말고, 이 문서에 새 케이스를 기록한 뒤 정본 함수를 갱신한다.
- ★ **Bash 경계(정직 — `*-write`와 동일)**: gate-guard는 Bash를 통한 로직 파일 쓰기(`sed -i`·`tee`·heredoc 등)를 **하드 차단하지 않는다** — 정당한 셸 사용(테스트 실행 등)의 FP가 크기 때문(§0.6). 소프트 리마인더만 준다. 따라서 이 차단은 **Edit/Write/MultiEdit 도구에 한정된 보장**이며, Claude는 규율로 Bash로 로직 코드를 쓰지 않는다(리마인더에 의존하지 말 것).
- **패턴 경계(알려진 한계)**: 대소문자 구분(`Tests/`·`FOO.TEST.TS`는 안 걸림 — 안전한 방향의 과차단), `tests/**`·`spec/**` 디렉토리는 그 안의 파일을 확장자 무관 통째로 신뢰(디렉토리 자체가 테스트 영역이라는 관례를 믿는 설계). 접두어 없는 맨몸 `Test.java`류 오분류는 review에서 발견해 `?*` 요구로 수정됨(§4 코드 참조).

## 5. 리뷰 스타일 (핑퐁 — 배치 아님)

- 한 번에 한 메서드/한 개념만 다룬다. 전체 리뷰를 몰아서 하지 않는다.
- 맞으면 "맞아요" + 왜 맞는지 한 줄. 틀리면 "~가 빠져있어요" + 구체적 이유 + (필요시) 정답 조각을 보여주되 **실제 파일 수정은 사용자가** 한다.
- 사용자가 막히면(예: "이런 경우 테스트를 어떻게 짜야 할지 감이 안 온다") 개념을 설명하고 예시를 들되, 최종 코드는 사용자가 채우게 유도한다.

## 6. 최종 검증

- 기능/작업 전체 완료 후 core §5 stakes 매핑대로 codex 교차검증 + 테스트 + (해당 시) 컨테이너 테스트. pair 모드 고유의 별도 검증 절차는 없다 — §3의 사이클별 리뷰는 **최종 검증을 대체하지 않는다**.
- 기록 단계(OVERVIEW·changelog·learned·TECHNICAL[·review-log])는 core §3.5 그대로.
