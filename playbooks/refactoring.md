# playbook: refactoring (모드 refactor)

> 트리거: 구현 모드 = **refactor** (task-mode-guard·gate-guard 훅 — core §1 구현 모드 5종 표). auto/lazy/pair/fast와 독립한 완결 프로토콜.
> 목적: 외부 관찰 동작을 **보존**한 채 내부 구조만 바꾼다. 안전망(특성테스트)을 먼저 깔고, Claude가 소단위로 변환하며 매 단위 green을 유지한다.
> 단일 출처: `docs/plans/2026-07-19/harness-v3-restructure/` (D6·D1-14). 그룹핑·경계 카탈로그는 `playbooks/design-taste.md`.

## 0. 이 모드가 아닌 것

- **기능 변경이 아니다**: 외부 관찰 가능한 행위(반환값·부작용·예외·계약 표면)가 바뀌면 리팩토링이 아니다 — 멈추고 §5로.
- 동작 보존이 **칸2 불변식**이다. 정의 게이트의 "경계·불변식"이 곧 "보존할 동작"의 스펙이 된다.

## 1. 고정 순서 (core §1 구현 모드 5종 refactor 행 — 건너뛰기 금지)

refactor는 자율도가 아니라 **순서가 고정된** 프로토콜이다. ①~⑤를 순서대로 밟는다.

### ① 보존 동작 합의 (칸2 = 스펙)
- 무엇을 "동작"으로 보존하는지 사용자와 합의해 master-plan 칸2에 적는다 — 공개 시그니처·API·스키마·이벤트·관찰 가능한 부작용의 목록.
- 이 목록이 ②의 특성테스트가 고정할 대상이자 ⑤의 종료 증명 기준이다.

### ② 특성테스트 baseline green 선행 (변환 착수 전) ★
- **변환에 손대기 전에** 현재 동작을 고정하는 특성테스트(characterization test)를 깔고 **전건 green**을 확인한다. 안전망 없이 변환을 시작하지 않는다.
- **그린 위장 점검** (2개월 실측 최대 결함군): 이 baseline이 진짜 계약을 검증하나 —
  - fail-open 골든(스냅샷이 비었거나 어떤 출력이든 통과),
  - 자기참조(현재 구현 출력을 그대로 기대값으로 박아 회귀를 못 잡음),
  - 계약 미검증(assert가 없거나 타입·존재만 보고 값을 안 봄),
  - exit 마스킹(`| tail`·`|| true`로 실패를 삼킴) 이 없나를 능동 반증한다.
- 위장이 발견되면 baseline이 아니다 — 실계약을 검증하도록 고쳐 다시 green을 세운 뒤 진행.

### ③ 그룹핑·경계 대화 (design-taste 연결)
- 무엇을 어떻게 묶고 가를지 사용자와 대화한다 — `design-taste.md`의 8앵커·Fowler 코드냄새(Long Method·Feature Envy·Data Clumps 등)·DDD(용어 일관성·Bounded Context·Aggregate)를 판단 렌즈로.
- 취향은 finding이 아니다 — 단정 가능한 냄새·경계 위반만 변환 대상, 순수 선호는 open question으로 사용자에게.

### ④ Claude 소단위 변환 (매 단위 green 유지)
- 한 번에 하나의 변환(추출·이동·이름변경·중복 제거)씩. **매 소단위마다 특성테스트 재실행 → green 유지**를 확인하고 다음으로.
- 한 단위가 red를 내면 즉시 되돌리고 원인 파악 — red 위에 다음 변환을 쌓지 않는다.
- 변환 커밋은 기능 변경과 섞지 않는다(core §3.2 — task/변경 단위 커밋 diff 격리).

### ⑤ 종료 증명 (조작적 정의)
- "동작 diff 없음" = **합의된 특성테스트 전건 green** + **계약 표면(공개 시그니처·API·스키마) diff 0**. 둘 다 실측으로 보인다(주장 아님).
- 계약 표면에 diff가 생겼다면 그것은 리팩토링이 아니라 기능 변경이다 → §5.

## 2. 검증·리뷰

- 검증·codex·리뷰는 모드 무관 **stakes 비례**(core §5). refactor 고유의 검증 생략은 없다 — ②·⑤의 green은 최소선이지 상한이 아니다.
- 중간↑ stakes면 듀얼 리뷰(Opus 워커 ∥ codex) — 리뷰 렌즈로 "동작 보존이 진짜 성립했나"를 별도 신호로 확인.

## 3. 문서

- master-plan(칸2 = 보존 동작 목록) + task-process 라이브. 기록은 core §3.5 그대로.

## 4. 동작 변경이 필요해지면 (전환·종료)

- 리팩토링 도중 "동작을 바꿔야 겠다"가 드러나면 **그 자리에서 변환을 멈추고 보고**한다 — refactor 프로토콜 안에서 몰래 동작을 바꾸지 않는다(core §1 표 전환 열).
- 보고 후 모드를 재질문한다 — 기능 변경은 auto/lazy/pair/fast 중 사용자가 고른 모드로, 별도 태스크로 분리해 진행한다.
